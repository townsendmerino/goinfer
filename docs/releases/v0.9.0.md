# goinfer v0.9.0 — two GPU backends, no cgo

goinfer is an LLM inference runtime written entirely in Go. No cgo, no C toolchain, no
vendor SDK at build time — `go build` and you have a binary. This release adds **GPU decode
on NVIDIA and Apple Silicon while keeping that property**, which as far as we know hasn't
been done before on either platform.

The GPU paths reach the hardware through `dlopen` and runtime shader compilation:
`libcuda` + NVRTC on Linux, `Metal.framework` + MSL 3.1 on macOS. `CGO_ENABLED=0` throughout.
No CUDA toolkit to install. No Xcode.

**Both backends are opt-in.** The default build is unchanged from v0.8.0. You choose a build
tag and a `--backend` flag, and if the device or a required kernel isn't there, the runtime
**declines to CPU rather than running something subtly different**.

```bash
go build -tags cuda  ./cmd/serve   # Linux + NVIDIA
go build -tags metal ./cmd/serve   # macOS + Apple Silicon
go build              ./cmd/serve   # pure Go, unchanged
```

> **Note (post-v0.10.0):** these were the correct commands *at v0.9.0*. Since v0.10.0 (M-19) the
> backends moved to submodule entrypoints and `-tags cuda|metal` on the root `./cmd/serve` no
> longer builds a backend (it now fails the build). For current commands see the README build
> section. Left here unedited as the historical v0.9.0 record.

## Reproducible by contract

Most inference releases are a list of speedups. This one is too — but the part we'd rather
be judged on is that **every GPU path is byte-reproducible against the CPU reference, and
there are tests that fail when it isn't.**

Bit-identity at this level is harder than it sounds, because the things that break it are
invisible to ordinary testing. A compiler fusing a multiply-add in one kernel and not another
shifts a result by one unit in the last place — enough, after compounding through a forward
pass, to flip a token at a near-tie and send the whole generation somewhere else. It doesn't
show up on random-weight fixtures, because uniform data rounds the same way in both orders;
it only appears on real weights, whose group scales span orders of magnitude.

So this release ships machinery aimed specifically at that class:

- an **FMA lint** that fails the *build* on any bare float multiply-add in a contracted
  kernel, rather than a test that might not exercise the right data
- a **Metal snapshot golden** — a machine-and-OS-pinned hash of Metal's own output past both
  reduction widths — because every other Metal gate compares two things that move together,
  and is therefore blind to anything that moves both
- **reduction widths pinned as named constants** with a contract comment, because on Metal
  threadgroup width is simultaneously the main performance knob and a bit-identity dependency
- **committed tiny fixtures** for families whose gates would otherwise skip, so a green CI run
  means the gate ran, not that its checkpoint was absent

If you care about reproducible inference — regression-testing a pipeline, auditing an
output, comparing quantization schemes — that machinery is the reason to look at this project.

## Highlights

### cgo-free CUDA backend

Resident decode and prefill on NVIDIA through gocudrv (`dlopen libcuda`) and NVRTC PTX JIT.

Measured on an RTX 2070 SUPER, real q4_K_M weights: **1.5B at 218.6 tok/s, 0.5B at
507.5 tok/s**. Getting there: coalesced W4A8 GEMV with ILP unroll, a launch diet from 18 to
13 dispatches per layer, f16 group scales, on-device greedy argmax, and rmsnorm folded into
the QKV and gate-up GEMVs (+21.3% on 0.5B).

### cgo-free Metal backend

Resident decode and prefill on Apple Silicon through purego-objc — `dlopen Metal.framework`,
`objc_msgSend`, MSL 3.1 compiled at runtime. **No Xcode, no toolchain**, and the first
`CGO_ENABLED=0` GPU path on the platform.

Decode went from ~20 to **73.6 tok/s**, which is the practical batch-1 ceiling on an M1 without
DP4A. Against Ollama-Metal v0.32.5, server-to-server: **0.96× on 0.5B, 0.74× on 1.5B.**
Metal's value here is the cgo-free property and correctness parity — **not** a speed multiple,
and we don't quote one.

### Speculative decoding — opt-in, lossless

Not "approximately the same output." **Byte-identical to plain greedy**, verified by test.

| mode | win | notes |
|---|---|---|
| CPU n-gram (`--spec ngram`) | 1.55–1.59× on 0.5B | prompt-lookup drafter; wins on copy-heavy traffic — code edits, RAG, agent loops |
| grammar-fused | modest | the grammar's forced bytes are drafted for free on constrained/tool requests |
| resident CUDA | 1.23× @128, **1.86× @512**, 1.18× @2048 | batched verify through the prefill path |

Recurrent families (Mamba-2, Gated DeltaNet) are **guarded out** of speculation and fall back
to plain decode, because their state can't be rolled back.

### Batched prefill and long-context decode

**Time to first token, 2048-token prompt: 13.1 s → 2.1 s (6.17×).** Default-on for CUDA,
bit-identical to the sequential path, covering 7 of 23 validated families (llama, mistral,
phi3, qwen2, qwen2.5-VL, qwen3, gemma3) — **at int4 only**. The batched GEMV reads
group-scaled int4 weights, so an otherwise-covered family loaded at `--quant int8int8` still
takes the sequential prefill (see Known limitations).

**Split-KV attention** takes 2048-context decode from 133 to 160 tok/s, and 1.61× over the
pre-campaign baseline together with attention coalescing. It splits the independent key and
value axes without reordering the softmax sum — flash attention's online rescale is *not*
bit-exact, so it is deliberately not on the default path.

On Metal, attention coalescing gives **1.37× at 2048 context, 1.40× at 4000** — the first
Metal decode speed win, and it's a long-context one.

### A 26B MoE, fully GPU-resident on an 8 GB card

Gemma-4 26B-A4B (~15 GB at int4) decodes **fully GPU-resident at 16.98 tok/s** on an 8 GB
RTX 2070 SUPER, by streaming routed experts host→VRAM into an LRU slot cache — 81.6% hit rate
at 30% residency, auto-capping slots to available VRAM, never OOMing.

Fully GPU-resident is the specific claim: no layer offload, no CPU compute in the loop. The
ceiling here is **capacity, not kernels** — a model that fits would decode faster than a
dense 7B.

### More families, and admission that declines instead of guessing

Resident on both backends: Qwen2/Llama, **Qwen3** (QK-norm), **Gemma-3** (sandwich norm,
gated-GELU, embed scale, per-layer RoPE), and **MoE** (Mixtral, Qwen2-MoE, Qwen3-MoE,
GLM-4.5/4.6). Metal adds **Mistral** and **Phi-3**. **Cohere / Command-R v1 and v2** land
CPU-correct at cosine 1.0 against HuggingFace.

Admission is one shared feature taxonomy: a backend declares a feature only when it ships the
kernel, and a family needing a feature the backend lacks **declines to CPU** instead of running
with that feature silently dropped.

## Measured performance

All peer comparisons in this release are measured against **current Ollama v0.32.5**, on the
same hardware, same quantization, server-to-server wall clock. Earlier figures in the repo are
retained with their peer version and date attached.

**Decode, CUDA, 1.5B, by KV depth** (best-of-3, interleaved, first run dropped):

| context | goinfer | Ollama v0.32.5 | |
|---|---|---|---|
| 128 | **226.6 tok/s** | 197.5 | goinfer 1.15× |
| 512 | **207.3 tok/s** | 191.7 | goinfer 1.08× |
| 2048 | 160.1 tok/s | 186.6 | Ollama 1.17× |
| 3900 | 123.5 tok/s | 180.7 | Ollama 1.46× |

**Ahead below roughly 1000 tokens of context; behind above it, and the gap widens with depth.**
The mechanism is visible in the curve: Ollama's flash attention holds nearly flat across the
range (197 → 181), while goinfer degrades (227 → 124). Flash attention's online rescale is not
bit-exact, so the default path doesn't use it — a bit-identical flash-style decode is the
remaining long-context lever, and it isn't built yet.

**Prefill is behind**, largely for an architectural reason: llama.cpp runs prefill GEMMs on
tensor cores through cuBLAS, and our group-scaled int4 format forces a float accumulation every
eight values, which no tensor-core tiling reproduces bit-for-bit. Closing it means changing the
quantization format — a trade we measured and declined for this release, with the analysis in
`docs/ollama-chase.md` §7.

On **Metal**, server-to-server against Ollama-Metal v0.32.5: **0.96× on 0.5B, 0.74× on 1.5B.**

**Read the absolute tok/s and the cgo-free property, not a peer multiple.** The ratio is
size-, depth- and platform-dependent, and it moves whenever either side ships.

## Known limitations

- **Batched prefill covers 7 of 23 validated families, and only at int4.** The other 16 fall
  back to sequential prefill — MoE, gemma4, MLA, sandwich-norm and qk-norm families among
  them. **Family is not the only axis**: the batched GEMV is int4-only, so a covered family
  loaded at `--quant int8int8` also falls back, while still building a full resident *decode*
  path — so it looks healthy and decodes normally. Measured cost on a 300-token prompt:
  **TTFT 1.73 s vs 0.19 s (9×)**, 20× the CPU. serve now prints the resolved prefill path at
  load and on `GET /health`, and `--require-backend` refuses to start on a decline.
- **Metal batched prefill is off by default**, because it is not bit-identical to the
  sequential path. Opt in with `GOINFER_METAL_BATCHED_PREFILL=1` if you want the TTFT and can
  accept the divergence.
- **Speculative decoding declines on recurrent families** (Mamba-2, Gated DeltaNet) and on the
  staged sliding-window path.
- **Long-context decode is behind above ~1000 tokens of context**, widening to 1.46× at 3900.
  Prefill is behind across the board. See above.
- **Pre-1.0.** A family counts as *supported* only with a CI-runnable T1 golden and a current
  T3 parity record. Families short of that ship **experimental**; the per-family backfill is
  the 1.0 gate.
- **Metal bit-identity is within-machine, not across-machine.** Metal shaders are compiled by
  the user's OS toolchain, which varies by macOS version — so identical output is guaranteed
  for a given machine and OS, not between them.

## Upgrading

Nothing changes unless you opt in. The default pure-Go build behaves as it did in v0.8.0.

- **New build tags:** `-tags cuda`, `-tags metal`. Backend selected with `--backend`.
- **New flags:** `--spec ngram` for speculative decoding.
- **New env toggles:** `GOINFER_SPLITKV_ATTN=0` disables split-KV attention;
  `GOINFER_METAL_BATCHED_PREFILL=1` opts into the non-bit-identical Metal prefill;
  `GOINFER_PRECISE_MATH=1` opts into precise Metal math (~4–7% slower, no accuracy gain on the
  default path — the snapshot golden already detects the drift it would prevent).
- **`--addr` now defaults to loopback.** If you relied on the previous all-interfaces default,
  pass `--addr :8080` explicitly.
- **This is pre-1.0.** The loader and architecture-descriptor surface may still change; the
  forward-pass and quantization numerics are the stable contract and are parity-gated against
  HuggingFace.

## Verify it yourself

```bash
go test ./...                       # pure-Go: parity, matrix freshness, coverage
python3 scripts/skip_census.py      # pass/skip/fail bucketed by reason
go test -tags metal ./metal/        # Apple Silicon — run as the sole GPU user
go test -tags cuda  ./cuda/         # NVIDIA
```

The census matters: with per-machine fixtures, a green run tells you little without knowing how
much of it ran. On our Mac this release is **415 pass / 0 fail / 167 skip** pure-Go and
**59 / 0 / 30** on Metal, with every skip asset-, GPU- or heavy-model-gated and none silent.
