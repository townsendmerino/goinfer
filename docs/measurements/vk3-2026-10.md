The record for VK3 ([`docs/tasks/task-subsystems-2026-10.md`](../tasks/task-subsystems-2026-10.md) §5.6), graded
against gates R1–R4, registered there before the code. Tier 0 apart from the goldens-gated refreshes. Measured on the
MacBook (M1 Pro, arm64) at goinfer main `4a135d91` plus this branch. Outputs are in [`vk3-2026-10/`](vk3-2026-10/).

## 1. The layout

- **`testdata/parity/shared_sets.json`** holds the shared sets.
- **`testdata/parity/<family>.json`** holds one family's row: the same fields, same order, same values.
- **`testdata/parity_manifest.json`** is gone.
- **The decoder's writer (`writeManifest`) wrote the records,** from the manifest as it stood; it writes a record only
  when its bytes change. `-update`, the `-merge-rows` merge and `scripts/refresh_parity_hashes.sh` therefore touch only
  the families they change.
- **Every reader goes through `paritykey.ManifestJSON`:**
  - the decoder's parity, census and capability-matrix tests;
  - `gate quick`'s golden-file map, `gate parity`'s qualifying paths and its release row, and `gate identity`'s
    families;
  - `gate shadow`.

  It assembles the records into the old single-object shape. At a commit from before them it returns the old file
  instead, so `gate shadow`, and the VK0 replay through the same function, compare across the change.
- **A tree with neither layout is an error.** `gate quick`'s golden-file map used to return an empty map when the
  manifest file was missing, which would have silently selected no golden after a move like this one.
