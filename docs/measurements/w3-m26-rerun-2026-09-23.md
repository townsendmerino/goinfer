# W3 M26 wall-clock re-run — the P20 shipped win, credited on the flagship page

**Purpose.** `docs/tasks/red-october.md`'s own R11(b) record names this exact follow-up as not yet
done: *"P20: `queue-performance.md` P20 closed or redirected, `benchmarks.md` W3 wall-clock column
re-run."* `GOINFER_CUDA_MOE_EXPERT_MAJOR` (P20's expert-major MoE prefill restructuring) shipped
default-on 2026-09-21 (`84d113b8`) with a real 2.26–2.66× per-token win on M26
(`docs/measurements/p20-expert-major-m26-2026-09-21.md`), but `docs/benchmarks.md`'s own W3 table
— the page this repo calls "evaluator-facing" and "provenance-gated" — still carried the number
from the PRIOR, smaller fix (4.1%, 2026-09-04/05). This re-runs the exact cell the W3 table
quotes, against the current default state, to close that gap.

## Method

`scripts/bench_peer.py`, goinfer-only (no peer re-run needed — Ollama/llama.cpp's own columns are
untouched by this change and were not re-measured), matching the harness/cell the existing W3 row
was produced by:

```
GOINFER_SERVE_CUDA=/tmp/serve-cuda-current \
BENCH_ENGINES=goinfer BENCH_MODELS=M26 BENCH_BACKENDS=cuda \
BENCH_DEPTHS=8000 BENCH_DEEP_CTX=8192 \
python3 scripts/bench_peer.py m26-w3-rerun-2026-09-23.json
```

`serve-cuda-current` built fresh via `go build -tags cuda ./cmd/serve` (from `cuda/`) at commit
`1f2010ff` (2026-09-23, tree clean) — includes both the P20 gemma4 expert-major fix (default on
since `84d113b8`, 2026-09-21) and, separately, this same session's own C′ decode/DMA-overlap work
(default on since `5ccba8de`, 2026-09-22) — both apply here, and the result below reflects the
tree as it currently ships, not an isolated attribution of P20 alone (see "What this does and does
not attribute" below). Model: `~/models/gemma4-26b-int4.giw` (local NVMe, matching this repo's own
storage rule), `-moe-cache-experts -ctx 8192`. Greedy, `M26:8000` calibrated prompt (8017 tokens,
`scripts/prompts.json`), 128 generated tokens × 2 completions × 2 runs (the harness's own deep-cell
default). Idle box (load 0.64/0.29/0.21 at preflight, gated to <1.0 before the cell itself ran —
one 20s wait), RTX 2070 SUPER, driver 595.91.07. Raw output: `m26-w3-rerun-2026-09-23.json`.

## Result

| | prior recorded (2026-09-04/05, post the earlier smaller fix) | today (post P20 expert-major + C′ overlap, both default-on) | ratio |
|---|---:|---:|---:|
| **cell wall-clock (8017-token prefill + 128 tok decode, ×4 completions)** | **368.4 s** | **234.4 s** | **1.57×** |
| decode tok/s (measured AFTER the long prefill) | 15.5 | **34.9** | 2.25× |

Against the very first recorded number for this cell (384.3s, before any P20 work at all): **1.64×**.

## What this does and does not attribute

**This is a re-measurement of the current tree's real, combined state — not an isolated A/B of P20
alone.** Two independent, both-default-on changes separate this number from the 368.4s one: P20's
expert-major prefill restructuring (2026-09-21) and this session's own C′ decode/DMA-overlap work
(2026-09-22, `docs/measurements/moe-streaming-decode-overlap-ceiling-2026-09-22.md`), which acts on
decode, not prefill. The decode-tok/s jump here (15.5 → 34.9, 2.25×) is larger than either
mechanism's own isolated measurement would predict alone (P20 doesn't touch decode at all; the C′
overlap work's own real-hardware reading was 1.27× on a short-context decode cell, not this deep,
post-8000-prefill one) — the two do not simply multiply, and this cell's own instrument (an HTTP
wall-clock, end to end) is not the same instrument either isolated measurement used, so exact
reconciliation across all three is not attempted here, consistent with this repo's own standing
rule against comparing numbers produced by different instruments as if they measured the same
thing. **The one honest, directly citable claim this re-run supports is the top-line ratio itself:
today's real wall-clock for this cell is 234.4s, was 368.4s, and is 1.57× faster** — which is what
the page needs to say, not a decomposed attribution across every contributing commit.

**One methodology note, so the depth-128 companion cell in this same run isn't misread:** this
run's own Phase-A M26@128 cell (`secs: 87.8`, decode 19.2 tok/s) is NOT directly comparable to the
existing W1 table's M26@128 row (24.6 tok/s) — this run pins `-ctx 8192` globally (needed for the
depth-8000 cell in the same invocation), which reserves more VRAM for KV up front and leaves less
free for the C′ expert-slot cache than whatever ctx the original W1 row used. Not filed as a W1
regression; the W1 row is untouched here.
