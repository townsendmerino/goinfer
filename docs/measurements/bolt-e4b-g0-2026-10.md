vision and audio towers are Gemma 4 E4B's own weights. The license (OpenMDW-1.1) allows redistribution. One stop point fired: the chat
template. goinfer rendered Bolt's template, and Gemma 4 E4B's current one, wrongly: 0 of 72 prompts matched Hugging Face. It is fixed on

## License: OpenMDW-1.1, which allows redistribution

- **What the cards say.** All three Bolt repositories' cards (the 4GB GGUF, the BF16 base and the DFlash GGUF) name `openmdw-1.1`. The 4GB card adds: *"This
  model has been post-trained on the Google Gemma 4 model, and use of the Google Gemma 4 model is governed by Apache License, Version 2.0."*
- **The license text** (openmdw.ai/license/1-1, read 2026-10-24). Permission *"to deal in the Model Materials without restriction"*. A distribution
  must keep a copy of the agreement and the notices of origin. Rights terminate for anyone who sues claiming the materials infringe. Outputs are
  unrestricted. **Redistribution is allowed with the license and notices kept, so this stop point did not fire.**
- **One conflict, in the drafter's file, not the target's.** The DFlash GGUF's own metadata says
  `general.license.name = nvidia-software-and-model-evaluation-license`, while its card says OpenMDW-1.1. That evaluation license is a restrictive
  one. The target GGUF carries no license key at all. Settle this before redistributing the drafter, not the target.

## Architecture: identical to Gemma 4 E4B

**HF `config.json`, Bolt against Gemma 4 E4B, sorted-key diff:** one line, `text_config.max_position_embeddings` 131072 → **65536**.
`generation_config.json` and `processor_config.json` are byte-identical. `architectures` is `Gemma4ForConditionalGeneration` and `model_type` is `gemma4`
in both.

**GGUF metadata, Bolt's Q4_K_M against Gemma's E4B q4_0:** every `gemma4.*` key is equal except `gemma4.context_length` (65536 against 131072). The
rest of the differences are provenance: `general.name`, `general.file_type` (15 against 2), the imatrix keys, and Bolt's missing `general.license*` and
`general.base_model*`.

**Tensor names and shapes.** The BF16 checkpoint has the same 2,130 tensor names as Gemma's safetensors, with no dtype or shape mismatch. The GGUF has 720
tensors to Gemma's GGUF's 666, with no shape difference on the 666 they share. The other 54 are listed under weight-file differences below.

### Weight-file differences (not architecture). The serve run below shows whether the loader handles them.

- **54 extra tensors:** `attn_k`, `attn_v` and `attn_k_norm` on each KV-shared layer (24–41). Gemma's GGUF drops them, and Bolt's BF16 release keeps them in a
  separate `model-frozen-shared-kv.safetensors`. No forward reads them. goinfer's GGUF loader loads no K/V for a KV-shared layer
  (`decoder/gguf.go:buildWeightsFromGGUF`), so it never reads these tensors either.
- **`per_layer_model_proj` is BF16** (GGML type 30; Gemma's GGUF stores it F16). aikit's GGUF row dequantizer, which the loader reads every float table through, has a BF16 case (aikit v1.74.0, the version `go.mod` pins).
- **Mixed quants:** `token_embd` and `per_layer_token_embd` are Q8_0; the body is Q4_K, with Q6_K on 21 of the 42 `attn_v` and 21 of the 42 `ffn_down`. The file is
  6.18 GB, so the repository name's "4GB" is not the file size (the card: "8B (4B effective)").

## Vision and audio towers: present in the BF16 release, unchanged from Gemma's, absent from the GGUF

- **The BF16 checkpoint carries both towers:** `vision_tower` (334.7 MB), `audio_tower` (609.7 MB), `embed_vision` and `embed_audio`, plus the `vision_config` and
  `audio_config` blocks in `config.json`.
- **They are Gemma 4 E4B's own weights.** All 1,301 tower tensors of 4 MB or less are byte-identical to the local Gemma 4 E4B safetensors. The 110 larger ones
  (718.8 MB) are identical at three 1 MiB windows each (start, middle, end); they were sampled, not read whole. The language model differs where it should: of
  four norms sampled, two differ.
- **The Q4_K_M GGUF is text only.** It has no tower tensors, the repository has no mmproj, and the card declares "Text / text". Gemma's own E4B mmproj would be the
  matching tower, but that pairing is untested and outside this gate.

## Vocabulary: unchanged

`tokenizer.json` is byte-identical (32,169,626 B, sha256 `cc8d3a0ce364…`). `tokenizer_config.json` differs only by Bolt's embedded `chat_template` key, whose
text equals `chat_template.jinja`. In the GGUF, `tokenizer.ggml.{tokens, scores, token_type, merges}` (262,144 tokens, 514,906 merges) are equal to Gemma's, and so

## Chat template: goinfer rendered it wrongly; fixed on this branch

**Three templates are in play.** The Bolt GGUF embeds the BF16 repository's `chat_template.jinja` byte for byte (20,159 B). Against Gemma 4 E4B's
current template (18,567 B, "Published: 2026-07-09"), Bolt's adds two things:

1. **`conversational_mode`**, off by default. When on, it adds a "spoken conversation, respond briefly" instruction to the system turn. goinfer
   does not pass it, so an unset request renders as HF renders it.
2. **An assistant message's text is written before its tool calls** ("The sole intentional behavior change from HF main: preserve OpenAI
   assistant content before its tool calls"). The canonical template writes it after the calls' results.

Bolt's header also says *"matching the original Gemma 4 generation prompt when enable_thinking=false"*. Neither Bolt's template nor E4B's
current one writes the closed scaffold `<|channel>thought\n<channel|>` after a thinking-off generation prompt. The canonical Gemma 4
template that goinfer fingerprints, the one pinned from `gemma-4-26b-a4b-it` in `testdata/chat_think_goldens/think_history.json`, does
write it.

**The reasoning toggle** is unchanged from Gemma 4. `enable_thinking | default(false)`; when on, the system turn opens with `<|think|>`. The
reply's reasoning is `<|channel>thought\n…<channel|>`, and after a tool result with thinking on, the prompt reopens `<|channel>thought\n`.
**The card disagrees with the template:** it calls thinking-on "the default", but the template's default is off. An unset request renders
thinking off in HF and in goinfer alike. The card's examples pass `enable_thinking` explicitly.

**The tool-call format** is Gemma 4's own micro-language, unchanged except for the order above:
- declarations: `<|tool>declaration:NAME{description:…,parameters:…}<tool|>`, in the system turn;
- a call: `<|tool_call>call:NAME{key:<|"|>v<|"|>}<tool_call|>`;
- a result: `<|tool_response>response:NAME{value:<|"|>…<|"|>}<tool_response|>`.

The card serves it with vLLM's `--tool-call-parser gemma4 --reasoning-parser gemma4`.

**Measured on `main` (dbc546c9), before any change.** `chat.Detect` names the template `gemma4` but attaches no reasoning behaviour.
`detectGemma4Reasoning` required the scaffold literal, so both templates rendered through the generic path. That path always writes the
scaffold, never writes `<|think|>`, and uses goinfer's own tool order. The reference is HF's rendering of each real template
(`scripts/pin_chat_think_history.py`, `transformers` 5.15.0) over the history set's 23 conversations plus a new two-turn tool conversation,
in 3 thinking modes. **Result: 0 of 72 prompts byte-identical, for Bolt and for Gemma 4 E4B's current template alike.** nobara's E4B
serve log from 2026-10-14 already read `thinking: unmanaged` for the same reason.

**The fix** (four files in `chat/`, plus the pin script):
- `chat/reasoning.go:detectGemma4Reasoning` recognises a canonical template (the `enable_thinking | default(false)` default and the canonical
  history fingerprint) that lacks the scaffold, and marks it `bareOff`.
- `chat/reasoning.go:Reasoning.offScaffold` gates the scaffold in `gemma4Segments` and in both tool renderers.
- `chat/gemma4_tools.go:detectGemma4ContentBeforeCalls` recognises Bolt's order (`Template.contentBeforeCalls`), and
  `chat/gemma4_tools.go:Template.renderGemma4NativeTools` writes the text before the calls when it is set.
- The canonical template's goldens are unchanged.

**After the fix:**
- **72 of 72 prompts are byte-identical for each template**, tool declarations included (`TestGemma4BareOff_templateMatchesHuggingFace`,
  golden `testdata/chat_think_goldens/gemma4_bare_think_history.json`, pinned by
  `PIN_CKPTS=gemma-4-E4B-it,nemotron-3.5-bolt-e4b scripts/pin_chat_think_history.py`).
- The test went red under three planted mutations: content-order detection off; the scaffold written unconditionally; the bare-off template
  not recognised.
- The whole `chat` package passes.
- The two templates differ from each other on exactly the 7 text-beside-a-call conversations, in every mode (21 of 72 prompts).

## SP0 candidate: Bolt E4B with its DFlash drafter as a windowed target

Recorded here because `docs/tasks/task-forward-architecture-2026-10.md` has no §6a and no SP0 on `origin/main` (dbc546c9) or on any branch
or checkout on nobara. It stays here, with no §6a stub (owner's decision, 2026-10-24 10:22 am, relayed by the coordinator).

- **Why it is a windowed target.** 35 of 42 layers use a 512-token sliding window, and 18 layers share K/V. The full-attention KV is 7 layers
  wide, and with the shared tail, KV per token is small.
- **The drafter** (GGUF header, `general.architecture = dflash`): 5 decoder layers, hidden 2560, 32 / 8 heads, head dim 128, FFN 5120, all
  sliding (window 1024), non-causal; `block_size` 8; taps at target layers [6, 12, 18, 24, 36]; 360M parameters in BF16. It uses the
  target's token embeddings and output head (embedding scale √2560). The NVFP4 safetensors config gives the taps as
  [5, 11, 17, 23, 35], the same layers counted one lower, and says `has_own_lm_head: true`. The card's recipe drafts up to 7 tokens.
- **What loading it needs.** goinfer's DFlash loader (`decoder/dflash.go:LoadDFlashDrafter`) reads `config.json` + `model.safetensors`.
  The drafter is published only as a `dflash`-architecture GGUF and as NVFP4 safetensors, and neither loads today: one needs a GGUF
  drafter path, the other NVFP4 dequantisation. The drafter's license conflict (above) is a second open item.
