## The three changes that would most improve a new user's first hour

### 1. The feature that solves the hardest problem is invisible from the README

Scenario D put a 35B-A3B MoE on a 16 GB machine. It drove the box into 7.8 GB of swap in five
seconds with no warning. Then, reading `serve --help` — 13,583 bytes of it — I found this:

> `-stream-weights` … page model weights on demand out of an mmap'd .giw, capping resident RAM to
> `-weight-cache` instead of holding all weights: MoE expert demand-paging (**run a 35B-A3B on
> ~16-20 GB**) or dense per-layer streaming (run a model bigger than RAM).

A flag whose help text names my exact model and my exact RAM. And:

- the README never mentions `-stream-weights`, or RAM, or fit, anywhere
  (`grep -niE 'stream-weights|RAM|memory|does not fit'` on the README: **no hits about memory**);
- `goinfer-chat`, the binary the README's first code block tells you to download, **does not have
  the flag** — it is `serve`-only;
- the failing path in scenario D printed `loading + quantizing…` and then nothing. It never
  suggested the flag that exists to fix it.

A user who follows the README exactly cannot reach this feature. They conclude "goinfer can't run
big models on my laptop," which is the opposite of true.

### 2. There is no `goinfer-serve`, and the documented install command does not work

The README uses `goinfer-serve` as a runnable command three times (lines 50, 56, 70), including the
headline browser-UI example. **The v0.16.0 release ships 21 assets and none of them contain the
string "serve"** (`grep -c serve checksums.txt` → `0`). The chat binary silently swallows a `serve`
subcommand and rejects `-web`:

> `flag provided but not defined: -web`

The README's only Install section, at the very bottom, says in full:

> ```bash
> go get github.com/townsendmerino/goinfer
> ```

That is a library fetch of a module with no root package, and it is **not sufficient to build
against** — scenario C, verbatim:

> `missing go.sum entry for module providing package github.com/townsendmerino/aikit/embed
> (imported by github.com/townsendmerino/goinfer/decoder)`

…times four. I only got a server at all by **guessing URLs against pkg.go.dev** until one returned
200 (`cmd/goinfer-serve` → 404, `serve` → 404, `cmd/serve` → **200**). Nothing in the README, the
release page, or `--help` names that import path. And it installs as a binary called **`serve`** —
a generic name dropped straight onto `$PATH`.

### 3. `backend=metal` is printed while running on CPU

Scenario E, the released darwin-arm64 binary, `--backend metal`. Two consecutive lines:

> `decoder: metal backend not built in; build the submodule entrypoint (go build
> github.com/townsendmerino/goinfer/metal/cmd/serve, darwin) — not `-tags metal` on the root
> cmd/serve; **using cpu**`
> `loaded 28-layer model (hidden 1536, vocab 151936) in 2.523s [**backend=metal** quant=int4]`

The warning is correct and the status line contradicts it one line later. Anyone who scrolls, pipes,
or screenshots the second line records a false fact about their own run — and on a Mac, where this
is the difference between 37.9 and 82.3 tok/s, it is the fact that matters most. Related: `--help`
says the backends are enabled by `-tags cuda|metal`, and the error message says that is wrong.

## D — Run bigger than my hardware

**Outcome: dead end.** Stopped after two attempts per the rules. **The tool never told me it would
not fit. The machine told me.**

The README names no MoE and gives no fit guidance, so I chose the closest local match to the brief:
`Qwen3.5-35B-A3B-Q4_K_M.gguf`, 21 GB, on a 16 GB machine.

### Friction log
- **06:42:30** — **Wanted and absent:** any pre-flight check. `grep -niE 'moe|RAM|memory|does not
  fit|stream-weights|30b|27b'` over the README returns nothing about memory. There is no guidance
  anywhere on what fits in 16 GB.
- **06:42:52** — **Attempt 1.** Printed `loading + quantizing…` and began. No size check, no
  warning, no estimate of resident RAM. Within **5 seconds**:

  | | baseline | +5 s |
  |---|---|---|
  | swap used | 1,967 MB | **9,786 MB** |
  | swapouts | — | **+529,708 pages** |
  | memory pressure | — | 34% |

  Watchdog killed it. A user without a watchdog gets a beachballed Mac.
- **06:43:35** — Found `-stream-weights` in `serve --help`, saying *"run a 35B-A3B on ~16-20 GB"* —
  the exact case that had just failed. It is not in the README and not in `goinfer-chat`.
- **06:43:52** — **Attempt 2.** `serve -stream-weights` on the pre-existing `.giw`. Behaved
  **much** better: RSS peaked **8.95 GB** and *fell* to 2.7 GB; **zero swapouts for 115 seconds**.
  The mechanism works.
- **06:46:21** — But it emitted **not one byte of output in 130 seconds** — no progress, no phase,
  no "transcoding", nothing. Then swap began climbing (+127,632 pages) and the watchdog fired
  before it ever reached `goinfer serving`. I could not distinguish "working" from "hung" at any
  point, which is exactly the state the second attempt is supposed to resolve.

### Numbers
| | attempt 1 (plain) | attempt 2 (`-stream-weights`) |
|---|---|---|
| warned before loading? | **no** | **no** |
| peak RSS | 3.6 GB (killed at 5 s) | **8.95 GB, declining** |
| swap growth | **+7,819 MB in 5 s** | 0 for 115 s, then +127k pages |
| output during load | `loading + quantizing…` | **absolutely nothing, 130 s** |
| reached serving | no | no (killed at 130 s per rules) |

**Half the time if:** the loader compared required bytes against `hw.memsize` and refused with the
number — *"this model needs ~21 GB resident; you have 16 GB; re-run with -stream-weights"*. It
already knows both numbers, and it already has the fix.

## E — Control: Ollama, same model, same question

**Outcome: worked.** Recorded to the same standard, and it is not flattering to goinfer on speed.

### Friction log
- **06:46:45** — Ollama was not running, and failed usefully:
  `Error: could not connect to ollama server, run 'ollama serve' to start it`. Fix stated in the
  error. Up in **2 s**.
- **06:47:01** — `ollama pull qwen2.5-coder:1.5b`. No guessing. No version pinning needed. The name
  is the name.
- **06:47:28** — One command, `ollama run <model> "<question>"`, took the prompt as an argument —
  the thing goinfer has no flag for.
- **06:47:34** — Ollama is **worse** than goinfer at one thing: `--verbose` stats are buried in
  ~8 KB of ANSI spinner escape codes (`[?2026h[?25l[1G⠙`) when redirected. Neither tool detects a
  non-TTY.

### Numbers
| | Ollama 0.32.5 | goinfer v0.16.0 |
|---|---|---|
| cold total (T0 → answer) | 33 s | **25 s** |
| downloaded | ~986 MB | ~1,081 MB |
| model load | 0.950 s | 3.314 s |
| **decode rate** | **82.32 tok/s** | **37.9 tok/s** (337 tok / 8.90 s) |
| prefill rate | 444.64 tok/s | not reported |
| compute path | Metal GPU | **CPU** (Metal not in the released binary) |
| answer quality | identical — same rune-based idiom | identical |

**goinfer wins cold start** (25 s vs 33 s, from a standing start with an 8 MB binary and no daemon).
**Ollama wins steady state by 2.2×** on decode and 3.5× on load, because it uses the GPU on this
machine and the released goinfer binary cannot. That gap is not an algorithmic verdict — it is the
`-tags metal` packaging gap from finding #3, showing up as the number a user will actually feel.

**Half the time if:** nothing. This was the frictionless leg, and that is the bar.
