# KV7 first slice, prefix snapshots in host memory: tier 0 and tier 1 (2026-10-16)

The build of `docs/tasks/task-kv7-prefix-snapshot-2026-10.md`, as the owner approved it: budget 10% of physical RAM capped at 8 GiB
(`-kv-host-bytes`, `0` off), pinned only while a snapshot is held, first-touch admission, no wait for the preamble marker, and the
count of first prompts that do not qualify reported here.

## Tier 0 (seconds, by day)

**Restored KV is the computed KV, on the real resident** (`TestKV7_restoreWindowed`, `TestKV7_restoreFull`; the three windowed
fixtures with the slack lowered so every ring base is past 0, and the whole-context fixture at f32 and f16). Slot 0 computes a prompt
and a snapshot is taken of its first 256 rows; the slot is then overwritten by another conversation, and the rows are restored into
it and into a second slot that held other rows. A third slot computes the prefix cold. For every K and V buffer of every layer that has
one, the restored rows are the computed rows byte for byte (a windowed layer from the first row its window reads, with the ring base
the copy rule sets), the destination had differed before the restore (so a restore that did nothing would be seen), and a 200-position
continuation gives the computed slot's logits bit for bit. All pass.

**The end-to-end option test** (`TestKV7_optionKVHostBytes_resident`, through `decoder.Generate` on a one-slot load): conversation A, an
unrelated one that takes the slot, then B starting with A's prefix. With a budget B restores 2,432 rows and its reply is the reply of the
same load with no budget; with 0 nothing is held. Five fixtures, all pass. **The decoder-level policy** (`decoder/kvsnap_test.go`, a hash
fake resident): the restore is the computed prefix; namespaces do not cross and `-kv-share off` turns it off; the budget holds, the least
recently used goes first, a longer prompt of a held prefix replaces the shorter, a covered prefix is not taken twice, a request that
restored a prefix does not take its family again; unqualified restores are counted; a refusing or failing backend is counted, never fatal.

**The five planted defects, each turning a gate red** (the production code changed, the named gates run, then restored):

| # | defect | gate that went red |
|---|---|---|
| 1 | a stale ring: the snapshot reads the ring through a base of 0 | `TestKV7_restoreWindowed` and `_declines` on all three windowed fixtures |
| 2 | the destination's ring base is not set on a restore | `TestKV7_restoreWindowed`, all three |
| 3 | a snapshot taken after a decode step (the ring check removed) | `TestKV7_declines`, all three (after the test was made to require the ring's reason: before, two fixtures declined for an unrelated reason and passed) |
| 4 | a key without the namespace | `TestKVSnapshot_namespaceIsolation` |
| 5 | a restore past the rollback (`Serves` ignoring the window) | `TestKV7_declines`, all three |
| + | a restored request takes its family again (the admission rule removed) | `TestKVSnapshot_aRestoreDoesNotHoldTheFamilyTwice` |

The decoder fake also shows a restore that writes nothing (`noop`), one block short (`short`) or one position off (`shift`) changes
the reply. `go vet` (cuda and realckpt tags) and the CI-pinned staticcheck are clean; the staticcheck canary (an unused field in a package
that imports the standard library) went red first. It caught an unused field in the test fake, removed.

## Tier 1 (by day, under the timing lock, nobody else on the card)

Binary: `serve-cuda-kv7`, `CGO_ENABLED=0 -tags cuda`, driver 595.91.07, RTX 2070 SUPER; the Mellum2.1 run on `c3c5342d`, the Claude Code
runs on `18c922fa` (the admission fix below; its only effect on the Mellum run's sessions is a decline already made as `held`, so that run
is cited, not repeated). The replays send recorded request bytes with only `stream`, `temperature` (0) and the output limit (24) rewritten
by splicing (`replay.py`), because a re-serialized body renders another prompt. Replies are compared with the response ids and the signing
key's two fields (key id, MAC), which are random per request and per server start, set aside (`compare.py`); the generated token ids, from
`--log-token-ids`, are compared as they are.

- **Cost of the mechanism.** Taking a snapshot: 205 ms for 323 MiB and 185 ms for 287 MiB, once, before the first token. Restoring: 28.9 ms

- **First prompts that do not qualify** (the part after the shared prefix past the rollback): **0**. In the replay `unqualified` stayed 0,

### What the runs found before this configuration was right

1. **Two sessions in different working directories share only 659 ids** of a Claude Code prompt: it writes the directory early. The first
   Claude Code run recorded its two sessions in two directories and restored nothing (`out-qwen3-cc`). Real sessions of one project
   share it, and the recorded pair now does.
2. **Without the title request between them, a model with no window needs no snapshot.** The second run (`out-qwen3-cc-2`) had the
   second session start at 5.4 s with 17,067 rows reused from the slot itself, the existing resident reuse, because nothing had taken
   the slot. A session's title request does take it (it is a different conversation on the one slot), and with the title in the sequence
   the second session is cold without the snapshot (28.4 s) and 5.6 s with it. On Mellum2.1, whose ring serves only 448 positions
   behind the newest, the snapshot is needed with or without a title.
3. **A defect in the admission rule, found by the third Claude Code run** (`out-qwen3-cc-3`): the second session, which had restored
   from the held snapshot, took a second 2,709 MiB snapshot of the same prefix (5.4 of 6.4 GiB held), because a model with no window has
   no rollback to measure "covered" against. A request that restored from a snapshot now takes another only if its prompt runs on past
   the held rows by more than a rollback, when it replaces it. The final run holds one.
4. **Taking a snapshot costs more than the copy itself.** The design estimated the take at the restore's milliseconds. Measured, it is
   6 to 7 times that: 185 to 205 ms for 287 to 323 MiB and 1.66 s for 2,709 MiB, the cost of allocating a pinned buffer and copying each
   layer into it. It is paid once per snapshot, before the first token of the cold request that makes it, against 60 to 80 s saved by each
   restore on this card.

### Against the estimates in the design

| | estimated | measured |
|---|---|---|
| restore, Mellum2.1, 325 and 285 MiB | 31 and 27 ms | 28.9 and 26.3 ms |
| restore, Qwen3-4B f16, 17,024 rows | about 230 ms | 198.6 ms |
| opencode session start | about 7 s (with its title) | 0.3 s (the replay omits the title) |
| Codex session start | about 1.2 s | 0.3 s |
| Claude Code on Qwen3-4B | not estimated | 28.4 s to 5.6 s |

The remainder after a restore prefills faster than the 95 ids/s the estimate used, which was the rate of a whole cold prompt.

## Not done, and where it stands

- **The preamble marker is not built.** A first prompt whose part after the shared prefix is longer than the ring's rollback is counted
  and not served. None in the recorded sessions, but a session that opens with a long, different first message would be one.
- **CUDA only.** A resident without `ResidentKVSnapshotter` (Metal, WebGPU, the CPU path) keeps none and the banner says so.
- **Mellum2.1 and Qwen3-4B only.** A windowed f16 family declines (as `CopyKV` does), and a recurrent family declines.
- **The Mellum run was not repeated on the final build.** Its restored sessions were declined as `held` under both admission rules.
