## 1. What KV2 is, and the choices made before the code

KV2 lets a request take rows another sequence computed. On slot storage that is a device copy from the slot that holds
them into the slot the request will use, followed by a prefill of the rest. No kernel that computes attention changes.

1. **The copy seam (owner decision, 2026-10-14).** One optional resident interface, `ResidentKVCopier`, with one method
   `CopyKV(src, dst, start, end int) error`: rows `[start, end)` of every layer, from slot `src` to slot `dst`. `start`
   and `end` are multiples of 64. The backend handles its own groups and windowed views. When it cannot copy (a window
   no longer holds the rows the requester needs, a layout it does not support) it returns a named decline
   (`KVCopyDecline`, with a reason) before writing anything, and the decoder prefills those rows instead. Any other
   error is treated the same way: the request prefills from `start`, so a failed copy can cost time but never a wrong
   row. Which rows a slot still holds stays `ResidentReusableKV`'s answer; a resident with windowed layers also answers
   it for a slot that is not bound (`ResidentReusableKVSlot`, CUDA's half). Experimental tier. The interface changes
   the `cuda`, `metal` and `gpu` modules, so the next release needs `RELEASING.md`'s two-step tag.
2. **A prompt's blocks are published when its prefill ends**, not when its generation completes (KV1 published at
   completion). Decode writes only past the prompt, so the prompt's full blocks are final from that point. Without this
   a conversation that arrives while another is generating could not take its preamble, and that is the case that pays
   (G5).
3. **A request takes another sequence's slot in place only when it gives up less than one block of it.** Main gives a
   request any slot it shares at least half of (`kvmgr.PickSlot`). With a 16K preamble and a context of 32K or less
   that is always true, so on main a new Claude Code conversation already reuses an idle conversation's preamble, by
   cutting that conversation back to the preamble, which it re-prefills on its next turn. Under KV2 a request that
   would discard a block or more of another sequence copies its hit into a free slot. A continuation (its own reply
   re-sent, plus a new turn) discards less than a block and stays in place, as today.
   - **With no free slot** (owner, 2026-10-14): the least recently used slot is evicted, as today, and the hit is
     copied into it.
   - If that slot is the one holding the hit, the request takes it in place: the copy would be from a slot to itself.
4. **The namespace (D4) comes from serve:** one on loopback; one per API key when keys are configured; and when serve
   binds beyond loopback without keys, no sharing between requests. `-kv-share off` gives that same behaviour anywhere.
   "No sharing" means a request reuses rows only from a slot whose whole sequence it extends, giving up less than one
   block: a continuation. That is a change from main for a server beyond loopback without keys, which today hands any
   request the slot it half-matches.
   - **A known limit** (owner, 2026-10-14; the task doc's §5.15 and `docs/server.md` state it): under "off", a request
     that knows all but the last 63 tokens of another conversation can still learn from its time to first token how
     far its guess matched.
5. **A sequence a drafter with its own KV serves takes no hit from another sequence.** The target's rows would be
   copied and the drafter's would not. An `-spec ngram` model (no drafter KV) shares as any other.
6. **Recurrent and hybrid families take no hit from another sequence** (one slot, state not copied: KV8).
7. **Rows written by an image prefill stay class unknown**, so they match nothing (KV1's state). That is safe and loses
   the reuse.
8. **Slot choice moves to the block LRU** for the victim when no slot is free.
9. **The CPU joins last** (D2; owner, 2026-10-14). A CPU session takes a hit by copying rows from another session's
   `KVCache`. If it would delay the GPU work, it lands as a separate commit after them.
10. **An open defect outside KV2's scope.** On the night of 2026-10-13, nobara saw prefix reuse missing on 13 of 16
    identical-prefix repeats from Codex (about 68 s each). It is diagnosing the cause. KV2 rewrites the code that
    reuse runs through, so KV2 does not change that behaviour on its own. The owner routes the fix once the cause is
    known. KV2's identity gate (G1) holds today's reuse behaviour fixed, so a fix on `main` merges into this branch as
    its own change.

## 2. The gates

Every gate except G5 and G6: fixed cases, run to completion, no sampling, no early stop. A skip is not a pass: every
run is read with `-v` for `--- PASS`, and skips are listed with their reasons. Every planted defect is shown red once,
removed, and its red output kept beside this record. The CUDA arm of each gate is nobara's (§4).

### G0. Split invariance on the Mac's backends (day, before any of them shares a row)

KV0 measured CUDA and WebGPU on nobara (`docs/measurements/kv0-invariance-2026-10-13.md`).
`TestMC5_prefillChunkInvariance` measured Metal's chunks inside one call. Nobody has measured a prompt prefilled in two
calls on Metal, on the Mac's WebGPU (a different shader compiler from nobara's), or on the CPU, which is what a copy
followed by a suffix prefill is.
- **Arms**, KV0's, each against the prompt in one call: splits at 512, 768 and 984 of a 1,000-token prompt (block
  aligned); chunk widths of 64 and 448. Fixtures: the tiny fixture KV0 used and Qwen2.5-Coder-1.5B q4_k_m, on Metal
  (int4 and int8int8), WebGPU and the CPU.
- **Rule** (KV0's): every layer's K and V rows and the last logits are compared; 0 elements differ. KV0's control (one
  token changed at position 300 shows from 300 on and nowhere before) runs first.
- **What it decides:** a backend whose aligned splits are not invariant keeps its rows class unknown and does not share,
  and that is reported to the owner. It is not a KV2 failure.
- Prediction (0.8): all invariant on Metal (its class is judged on where a pass ends, and the chunked prefill already
  measured invariant) and on WebGPU (no class depends on the prompt). The CPU: no prediction.

### G1. Identity (day on the Mac; the Metal device gate at night)

- **Rule:** KV1's G1, with test files byte-identical to `main` at the branch point, over the same test patterns, plus
  `internal/serveapp`'s session and reuse tests.
- **Exception:** a test that asserts main's in-place take of another conversation's slot (choice 3) may change. It is
  named in an amendment to this record, with the reason, before it changes.
- **Plus the Metal device gate,** `go run ./cmd/gate gpu`, verdict PASS for the merge candidate (night;
  `docs/measurements/release-v0.23.0/run-metal-gate.sh`).
- **Void:** a test file changed that no amendment names; a listed test absent from the run.

### G2. The copy is exact, per backend (day)

- **What runs:** for each backend, fill two slots with different prompts. Then `CopyKV(src, dst, start, end)` at three
  ranges: `[0, 64)`; `[0, 1024)`; and `[256, 1024)` into a slot that already holds rows below 256. Read back every
  layer's K and V.
- **Rule:**
  - dst's rows in the range equal src's, byte for byte;
  - dst's rows outside the range are unchanged;
  - src is unchanged.
- **Fixtures:** the tiny fixtures and the 1.5B (int4, and int8int8 on Metal); on Metal also a windowed model and an
  f16-KV and an i8-KV load.
- **A decline is a decline:** a resident asked for a range it cannot serve returns `KVCopyDecline` and leaves dst
  untouched.
- **Planted:** a copy one block short; a copy whose layer stride is off by one layer. Each must turn the rule red.

### G3. Schedule independence (hard; day)

The sketch named "the MC4 harness". No such harness exists: MC4 is parked broadening. The owner accepted this
replacement on 2026-10-14. The instrument is MC3's identity design (`TestMC3_concurrentGenerationsMatchAlone` on a fake resident, `metal/mc3_step_test.go` on the device), extended
to conversations that share a preamble.

- **Conversations:** three of them, A, B and C, share a preamble of 1,000 tokens: above Metal's floor and CUDA's
  512-token floor, so the preamble is fast class everywhere. Each has its own first message and two turns. Greedy,
  plus one sampled arm with fixed seeds.
- **Schedules:** with 2 slots, and on the fake resident also with 1 and 4:
  - (a) A1, B1, C1 in order;
  - (b) C1, B1, A1;
  - (c) A1, B1, A2, C1, B2, A3, C2. Three conversations on two slots, so slots are taken and lost;
  - (d) B1 sent while A1 is generating (MC3 on Metal; slots on WebGPU; `-max-concurrent` on the CPU);
  - (e) A1 and B1 started together.
  - On the fake resident only, every order of the three first turns and 20 seeded random interleavings of the turns.
- **Reference:** each turn alone, on a fresh load. The server reports where each turn's reuse came from:
  - a continuation of its own slot: the reference is the conversation's turns run alone, continuing;
  - a hit from another sequence, or no reuse: the reference is that turn's whole prompt prefilled cold.
  Continuation rows are decode class and are not bit-identical to a cold prefill; that is the task doc's §5.6
  property 3, as today.
- **Rule:** every emitted token is equal, and every step's logits are bit-identical (float32 bits) to the reference.
  For every copy, the requester's copied rows equal the rows its own cold prefill writes, read back through a test
  hook: the task doc's §5.6 property 2.
- **Backends:** the fake resident (decoder); Metal and WebGPU, on the tiny fixture and the 1.5B int4; Metal also at
  int8int8 and with `-spec ngram`; the CPU on the 0.5B and the 1.5B (G0 permitting).
- **Planted:**
  - a copy that claims a hit one block longer than it copied;
  - a copy from the wrong slot;
  - a backend that returns success without copying.
  Each must turn the rule red, the third in the copied-rows check.

### G4. KV1's carry-overs (day)

Each is a test that passes as built and goes red on its planted defect.
- **(a) The class recorded per row is the class that ran.**
  - On Metal, a test hook records which kernel class each prefill call ran. A prefill of a long prompt that exceeds the
    floor in its last call only must record each call's rows by the kernel that ran them.
  - Planted: the decoder judges a call on its own rows instead of where it ends.
  - The CUDA arm is KV0's launch-count test, nobara's.
- **(b) A hit leaves the requester the rows its cold prefill needs.** `Manager.Admit` caps a hit with the requester's
  class map: a requester whose cold prefill is fast class keeps a suffix of at least the class's minimum rows (16 on
  CUDA), and the hit shrinks by a block until it does.
  - The test runs `internal/kvmgr` with CUDA's and Metal's class maps.
  - Planted: the cap at n − 1 only. It must fail on CUDA's class map.
  - The device arm (KV0's `split@985` shape) is nobara's.
- **(c) A hit never crosses a namespace.** serve tests:
  - two API keys share nothing;
  - loopback without keys shares;
  - a bind beyond loopback without keys shares nothing between conversations and keeps a continuation;
  - `-kv-share off` the same;
  - each checked through `usage.prefill_reused_tokens` and the vendor extension naming the reuse's source.
  - Planted: serve does not pass the namespace through.
- **(d) An image span with no content hash matches nothing,** through the copy path. Planted: the lookup steps over such
  a span.
- **(e) Fast rows on a windowed layer from a pass that started off a block boundary match nothing,** through the copy
  path. Planted: `ClassMap.PassAt` ignores `Windowed`.

### G5. The sharing gate (night, both boxes; the result decides KV2, Q3)

**The premise, stated:** Claude Code shares nothing across conversations while its attribution header is on (22
tokens; `docs/measurements/kv0-traffic-2026-10/header-probe.txt`). With `CLAUDE_CODE_ATTRIBUTION_HEADER=0`, which
`connect claude-code` writes (Q1), the first requests of different conversations share 18,213 of about 20,154 tokens.
The gate's prompts are built to that shape and say so:
- a synthetic system preamble of 18,213 tokens;
- then each conversation's own first message;
- then a fixed tail of about 1,940 tokens (the environment block and date line), which follows the divergence and
  cannot be shared.

They are generated deterministically by `kv2_share.py` (beside this record). The real captured requests are not
committed. The server's own token counts are recorded.

- **Model:** Qwen2.5-Coder-1.5B-Instruct q4_k_m, the model KV0's projection is for, at `-ctx 24576` and 2 slots (Metal's
  default) on every arm.
- **Arms:**
  - `main`: the merge base, the do-nothing arm;
  - `off`: this branch with `-kv-share off`;
  - `kv2`: this branch at default flags.
  - Each block is one fresh server per arm and script, the arms in a rotating order (ABC, BCA, CAB, twice).
- **Scripts:**
  - **T-busy, the graded case.**
    - A1 (the preamble, A's message, the tail; `max_tokens` 128, greedy).
    - When A1's first content token arrives, B1 (the same preamble, B's message, the tail).
    - Timed: B1's time to first token.
    - On `main` and `off`, A's slot is busy, so B1 prefills cold in the second slot. On `kv2` it copies the 18,176
      block-aligned rows from A's slot and prefills the rest.
  - **T-idle.**
    - A1, then B1 after A1 completes, then A2 (A1's messages, A1's reply, a short new turn).
    - Timed: B1 and A2.
    - On `main`, B1 takes A's slot in place and A2 takes it back, re-prefilling A's tail. On `kv2`, B1 copies into
      the free slot and A2 continues in its own.
  - **The control:** T-busy with the header on: each conversation's preamble carries its own three-hex token at
    token 22, as Claude Code's does.
- **Statistic, T-busy:**
  - Per block, the saving s = B1(main) − B1(kv2).
  - The projection p = B1(main) × hit ÷ B1's prompt tokens. That is KV0's projection (tokens skipped ÷ the box's
    long-prompt rate), with the rate taken from this block's own main arm. KV0's 29.7 s for the Mac is reported beside
    it.
  - The cell's value is the median over blocks of s ÷ p.
- **Rule, T-busy, per box:**
  - **DELIVERS** when the median is in [0.80, 1.05]. Below 1 is expected: the suffix's rows attend to more keys than
    the average row, and the copy costs time.
  - **UNDER** when it is in [0.50, 0.80). The owner decides.
  - **FAILS** when it is under 0.50.
  - Above 1.05 the saving is larger than skipping those tokens can explain. The cell is held, not graded, until the
    cause is found.
  - KV2 goes ahead when the Mac DELIVERS and its median saving is at least 5 s (KV0's bar, §2.4: "on either box").
    nobara's cell is graded against its own band and reported; with KV3's long-prompt fix its saving may be under
    5 s, which the rule allows.
- **Rule, T-idle:**
  - Per block, r = (B1 + A2)(main) ÷ (B1 + A2)(kv2). **PASS** when the median r ≥ 1.00. **FAIL** when the median is
    under 0.97 and every block is under 1. **PARKED** otherwise.
  - B1 alone, kv2 ÷ main, is reported with the copy cost beside it: here the copy replaces an in-place take and can
    only add time.
- **Controls; void if either fails:**
  - T-busy's median B1(off) ÷ B1(main) must be in [0.95, 1.05];
  - the header-on control's median B1(kv2) ÷ B1(main) must be in [0.95, 1.05], with `usage.prefill_reused_tokens`
    under 64 in every block;
  - `kv2`'s T-busy B1 must report 18,176 reused tokens (or the hit the server's own token count implies, block
    aligned) in every block, and `main` and `off` none past the template header.
- **Identity, hard, free with the run:** B1's reply text in T-busy and T-idle equal across the three arms, every block.
  A2's is not compared: on `kv2` it continues decode-class rows (property 3).
- **N:** 6 blocks, fixed, no early stop.
  - `power.py served-ttft mac/metal/1.5B/d128 --bar 2.0 --expect 5 --paired` gives N = 2 (power 1.000); the effect is
    a large multiple of any spread on record.
  - The 6 blocks are two rotations of the arm order, and cover the variation in when B1 arrives against A1's decode.
- **Reported, not graded:** T-busy, `main` and `kv2` only, 2 blocks, on the Mac's WebGPU and CPU (the CPU at
  `-max-concurrent 2`).
- **Void, beyond the controls:**
  - an arm not resident on the named backend (`-require-backend`);
  - an errored request;
  - a block missing an arm;
  - in T-busy, A1 completing before B1 was admitted (the script records both times).
- Prediction (0.7): the Mac DELIVERS at about 0.9, saving about 27 s; T-idle PASSES at about 1.5.
- **Cost on the Mac:**
  - the graded cells: about 630 s a block (three servers an arm, A1's cold 20K prefill about 33 s at KV0's 613
    tok/s), so 6 blocks is about 65 minutes;
  - the WebGPU and CPU cells: about 30 minutes, the CPU's cold prefill not on record and assumed about 150 tok/s.
  - Queued as `kv2-share-metal`, `--est 110`, behind `op1-g2r-metal`.

### G6. A lone request against main (night, both boxes)

KV2 changes no decode step. What a lone request runs that main does not is admission: the index lookup that finds no
other sequence, and the slot choice.

- **Cells and instrument:** KV1's G5b unchanged: `scripts/bench_peer.py` for decode at depth 128 and KV1's
  `kv1_ttft.py` for time to first token at about 3,070 tokens. Two arms (`goinfer` = the merge candidate,
  `goinfer_old` = the merge base), on the 1.5B and the 7B, Metal on the Mac and CUDA on nobara.
- **Noise:** the registry's entries for these cells (Metal decode sd 0.0129, `metal-r17-e2e-control-crossbuild`,
  cross-build A/A, n = 2; Metal time to first token sd 0.0112, `metal-ttft-chunked-solo`, n = 18; CUDA decode sd
  0.0081, `seed-nobara-cuda-goinfer-all-S`, n = 20; CUDA time to first token has no entry). KV1's G5b readings are this
  exact instrument on a change that moved nothing, and their block ratios' sd is smaller: Metal decode 0.0070,
  Metal time to first token 0.0019, CUDA decode 0.0014, CUDA time to first token 0.0047 (each the larger of the two
  models; `docs/measurements/kv1-2026-10-13.md`, §3, G5b).
- **power.py, run before this registration, bar 0.99, paired:**

  | cell | registry sd | N at the registry sd | KV1's measured sd | N at KV1's sd |
  |---|---|---|---|---|
  | Metal decode, 1.5B and 7B | 0.0129 | cannot resolve at N ≤ 12 (power 0.69 at 12) | 0.0070 | 6 (power 0.801) |
  | Metal time to first token | 0.0112 (1.5B) | 12 (power 0.809) | 0.0019 | 3 (power 0.984) |
  | CUDA decode, 1.5B and 7B | 0.0081 | 8 (power 0.855) | 0.0014 | 3 (power 0.999) |
  | CUDA time to first token | none | (KV1 borrowed the Mac's: 12) | 0.0047 | 4 (power 0.803) |

  At 0.98 the Metal decode cells resolve at N = 6 on the registry's sd. The bar stays 0.99: it resolves at KV1's
  measured sd, which is the better-founded figure for this instrument (n = 12 blocks against n = 2).
- **The CPU and WebGPU get no served cell:**
  - `power.py served-decode mac/cpu/1.5B/d128` cannot resolve 0.99 at any N (its 0.0165 floor), nor 0.98 or 0.97
    at N ≤ 12;
  - the registry has no served entry for WebGPU;
  - either cell would spend a night and decide nothing.
  - Their lone request is covered instead by G7's admission cost, which is the only thing KV2 adds to it, and by
    G1's identity.
- **Blocks:** 12 per cell, fixed, no early stop: KV1's design and cost. That is at or above every N in the table, and
  the margin covers the uncertainty in an sd estimated from 12 blocks.
- **Statistic:** per block d = ln(new ÷ old) of the rate for decode and ln(old ÷ new) of the time for time to first
  token, so above 0 is faster in both.
- **Rule, per cell,** with the interval mean(d) ± t(0.975, N − 1) · sd(d)/√N:
  - **PASS** when the lower end is at or above ln(0.99) and the median ratio is at most 1.01;
  - **FAIL** when the upper end is below ln(0.99);
  - **PARKED** otherwise (unresolved, or a median above 1.01, which KV2 has no mechanism for). The owner decides.
  - KV1's median-in-[0.99, 1.01] reading is reported beside it.
  - Graded by `grade_kv2_speed.py`, beside this record.
- **Void:** KV1's: an arm not resident on the named backend; an errored cell; a block missing an arm.
- Prediction (0.85): every cell PASSES.
- **Cost:** KV1's measured wall, 62 minutes on the Mac and 31 on nobara. Queued as `kv2-speed-metal`, `--est 80`.

### G7. The copy's cost, and admission's (reported, not graded)

- **The copy:** the server logs each copy's rows, bytes and wall time. G5's T-busy and T-idle blocks give it on the 1.5B
  for 18,176 rows on every backend that ran, and the median per box is reported. An in-process benchmark of
  `CopyKV` for 18,176 rows of the 1.5B and the 7B runs in the same night job on each box. The task doc's estimate to
  hold it against: about 2.2 GB in about 10 ms for the 7B at f32 on the 8 GB card.
- **Admission:** KV1's G5a benchmark (acquire, publish, forget on a 20,000-token and a 512-token prompt), extended
  with a lookup that finds another sequence's blocks and one that finds none, in process, on each box. KV1's bar is
  kept as a check: at most 1 ms per request at 20,000 tokens.
- A copy that costs more than a tenth of G5's projected saving is reported to the owner as a design question, not graded.
