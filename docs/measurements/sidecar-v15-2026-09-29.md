# Sidecar load: do the 2026-09-24 figures hold on the format that ships? (nobara, 2026-09-29)

**Status: PRE-REGISTERED 2026-09-29, before the run.** Queued on nobara's night queue; the result section is added below
after the run.

**Question.** [`cpu-giw-vs-direct-2026-09-24.md`](cpu-giw-vs-direct-2026-09-24.md) measured a `.giw` sidecar load against a direct
`.gguf` load: load time 0.00 s / 0.01 s against 5.61 s / 16.49 s, Go heap +0 / +1 MB against +1262 / +4961 MB, decode 1.0007 /
1.0016 of direct. It ran on **weights format v12** with the **embedding table int8-pinned**. Two things have changed since:
1. **v15** (unreleased): every target now stores int4 group scales as binary16, so the reader aliases them as the weight
   matrix's own storage. v13 and v14 are **Metal-target-only** (`decoder/serialize.go`, `giwVersion`): on nobara a CPU or CUDA load
   went v12, then v15, so v15 is the only later format a nobara run can touch. A Metal run would cover v13 and v14 (not queued).
2. **`--embed-int4` has been default ON since 2026-09-28**, so a default load now reads a different sidecar (`.e4h.` in its
   name) with a smaller head.
A writeup on the site (`site/different/18-starts-in-a-hundredth.md`) quotes the 09-24 figures. This run says whether they
still describe what ships.

**Design.** One job, [`run-sidecar-v15.sh`](sidecar-v15-2026-09-29/run-sidecar-v15.sh), from a git worktree pinned to `dc0699d4`
(the box's own checkout carries someone's uncommitted edit and is not touched). Sidecars are built **fresh** in a scratch
`HOME` holding symlinks to the same two `.gguf` files, so no old sidecar can be reused: a v15 reader converts an older file's
scales at load, which would time the wrong thing. The script reads each sidecar's format version from its header and stops
unless the CPU ones are 15.
- **CPU:** the same test as 09-24, `TestCPURoofline_giwVsDirect` (`decoder/cpu_roofline_ab_test.go`), unchanged: `direct`,
  `giw`, and a second `direct'` as the do-nothing arm, ABBA, 7 pairs, 128-token prompt, 24 greedy tokens, both models.
- **CUDA:** the same harness as 09-24, `scripts/bench_sidecar_cuda.py`: sidecar default vs `-direct-load`, a fresh server per
  arm, ABBA x2 per model, 3 greedy 256-token decodes each. The first sidecar start, which converts, is timed separately.

**Hard gate.** Every greedy token stream is identical across arms, on both models, CPU and CUDA. A difference is a defect; the
speed result is then not read.

**Decision rule** (bands fixed now; the 09-24 numbers are the reference, not the target):
- **HOLDS** — on both models, the CPU `giw` load is at most 0.05 s, its Go heap growth at most +10 MB, and decode `giw`/`direct`
  median is within 0.98–1.02; the CUDA sidecar loads no slower than `-direct-load`. The site keeps its claim, with the
  new figures and the format named.
- **CHANGED** — the gate passes but any of those bounds fails. The new figures replace the old ones on the site, whatever they
  are, and the writeup's title is reworded if 0.01 s no longer holds.
- **BROKEN** — the hard gate fails. Reported as a defect first.
Nothing here can pass by moving a bound after the fact.

**Reported, not decided on.** Load wall time per arm, Go heap in use and `RssAnon`/`RssFile` after each load, sidecar size,
transcode time (CPU and the first CUDA start), the CUDA load and decode per arm, the format version of every sidecar built.

**Not measured.** A cold page cache (the warm-up runs first, as on 09-24); Metal and WebGPU; any model above 7B; the v13/v14
Metal formats.

**Cost.** About 45 minutes on nobara: two builds, two CPU transcodes (about 2 minutes), the CPU test (about 10), the CUDA
harness (about 20).
