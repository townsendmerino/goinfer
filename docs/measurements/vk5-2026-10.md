## 1. What runs

- **`internal/paritykey`** computes today's key (`freshDepsHash` as a library) and the shadow key from a working tree or
  from any commit's git objects. The shadow key is the same hash with `aikit_version=<pin>` replaced by
  `kernelprint=<digest>`. The digest (`kernelprint.Report.Digest`) is one SHA-256 over the dispatch configuration and
  every kernel's VK1 fingerprint. VK4's program fingerprint will narrow it to the kernels each family uses.
- **`go run ./cmd/gate shadow [-json FILE] <before> <after>`** builds this tree's kernelprint suite against each side's
  aikit pin, through a temporary modfile, on the machine it runs on. It then classes every family across the push:
  agree-stale, agree-fresh, old-only, new-only, added or removed. An old-only verdict is explained when the aikit pin is
  the only input that moved. A new-only verdict is never explained by the tool. Exit 1 on an unexplained
  disagreement. A push with no before commit, an unknown commit, or a pin the suite cannot build is VOID: it exits 0
  and says VOID.
- **`.github/workflows/vk-shadow.yml`** runs it on every push to main. It is not required and has no concurrency group,
  so collapsed pushes are not skipped. It writes the markdown to the job summary and uploads `shadow.json` as
  `vk-shadow-<sha>`.

## 3. Limits

- The digest covers every kernel at once, so a change to any kernel re-stales every family in the shadow key until VK4
  narrows it.
- Both sides use this tree's suite and this machine's toolchain. A Go toolchain change between the sides is invisible to
  both keys, as it is today.
- CI's runner pool mixes AVX2 and AVX-512 machines. Both sides of one push are fingerprinted on the same runner, so a
  push compares like with like; digests from two runs are not comparable to each other.
- The suite builds against aikit v1.70.0 and later only (VK1 §4). A push from an older pin would be VOID; main is long
  past it.

moved only for configurations other than the runner's own, and names them. A move in the runner's own entry without a
move in its fingerprints stays unexplained. `TestCompare_classes` covers both cases, along with the change of definition.

hand, so it passed whatever `Key` did with the pin (§7, Gemini's finding 3). S3 was the evidence for that property, and

**What the switch leaves for week 2.** The table's digest covers every kernel, so a change to any kernel re-stales every
family. VK4's program fingerprints narrow that to the kernels each family runs, and week 2 shadows that key, with the
forward source files out of it.
