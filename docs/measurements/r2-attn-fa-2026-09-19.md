# R2 Build — attention_fa: kernel correctness proven, real-generation divergence found, PARKED

`docs/tasks/red-october.md` R2's Build phase: a new Metal decode-attention kernel gridded by
(kvHead, split) instead of by query head, cooperatively coalescing the group's K/V reads instead
of re-reading them per head. This record covers the attempt through where it stopped.

**Status: PARKED 2026-09-19 — same shape as R1's outcome (`w4f16-decode-investigation-2026-09-19.md`).
The kernel is proven correct in exhaustive isolation (16/16 adversarial cases, cosine 1.0000000
throughout) and shows a real, if modest, speed win in isolation (up to 1.26× at the registered
decision depth). Wired into the real production dispatch path, it diverges starting at the third
decode token past the depth floor — a discrete, stable, fully deterministic wrong answer, not a
growing numerical drift. The root cause was not found. `GOINFER_METAL_ATTN_FA` stays off by
default; the code is kept, not shipped, per this repo's own convention for a parked kernel.**

## Background — why this design, given four prior negative results

`docs/ollama-chase.md` §A2-Metal records four independent, carefully measured attempts at sharing
K/V reads across a GQA group on Metal, all losses: split-KV (0.95-0.98×, dispatch tax), grouped
dedup (0.45-0.92×), threadgroup-staged dedup (0.23×, occupancy crater — only 2 threadgroups for 2
KV heads on a ~14-core GPU), and a cooperative-staged K-read probe closed one week before this
session (`docs/audit-metal-2026-09-12.md` M-09, 2.3× slower). That section's own conclusion:
*"Stop proposing dedup layouts; the lever is elsewhere... or accept the floor."*

This attempt is a genuinely different combination — not a naive repeat — informed by why each
prior one failed: grid by (kvHead × split) specifically to counter the occupancy crater (split
count chosen so `kvHead × S ≥ 2× core count`), and cooperative loads read straight into registers
(never staged into a separate buffer with an idle-during-stage phase, the mechanism M-09's own
closure blamed for its 2.3× loss). The user was shown this history and chose to proceed with full
awareness of the risk before any code was written.

## What was built

- `metal/kernels.go`: `attention_fa` + `attention_fa_combine`, a two-dispatch FlashAttention-style
  kernel pair. `attention_fa`: 128 threads (4 simdgroups) per (kvHead, split) threadgroup; each
  simdgroup walks its own key sub-range, running online softmax for all `G=nH/nKV` group heads at
  once off one shared cooperative K/V read (32 lanes × half4 = hd=128); the 4 simdgroups' partials
  combine (fixed sg0→sg1→sg2→sg3 order) into one (m, l, acc) triple per group head, written to a
  scratch buffer. `attention_fa_combine`: merges the `nSplit` per-kvHead partials (split-ascending
  order) into the final output. hd=128-only (the cooperative-load tiling is fixed to 32×half4);
  dense-GQA-only (no window/sinks/f32-KV — explicitly deferred by the brief's own text pending a
  band-clearing result on the dense case first).
- `metal/attn_fa_test.go`: gate (1), the amended 2026-09-19 spec — not just the diffuse
  random-hot-key case the original `runAttnCase` pattern used, but the hot key driven at the
  first split, the last split, and both sides of a split boundary, plus a rising-score ramp that
  moves the running max at every step, at S ∈ {1, 2, 4, 8, 14}. **16/16 pass, cosine 1.0000000,
  maxAbs ~1e-6–1e-7 throughout** — no case found a defect.
- `metal/attn_fa_speed_test.go`: an isolated kernel-vs-kernel A/B (not end-to-end served tok/s).
- `metal/model.go`: production wiring — `canUseAttnFA`/`attnFASplitFor`, a `curNKeys` CPU-side
  depth tracker (set by `setPos`, explicitly reset to 0 by `ForwardBatch` so a stale value can
  never cause the kernel to engage during batched prefill — see that fix's own comment), scratch
  buffers sized once at `BuildResident`, and the dispatch-site branch in
  `encodeAttentionResidualWith`. Gated off by default (`GOINFER_METAL_ATTN_FA=1` to enable);
  confirmed a true no-op when disabled (`TestMetalSnapshotGolden` byte-identical, every existing
  Metal correctness gate unaffected).
- `metal/attn_fa_e2e_test.go`: `TestAttentionFA_endToEndReproduction`, the keeper reproducer for
  the open bug (see below) — gated `GOINFER_HEAVY_TESTS=1`, quiet in ordinary CI.

## Gate (1): correctness in isolation — fully clear

| case | cosine | maxAbs |
|---|---|---|
| K=24..3900, S=1..14 (the base sweep) | 1.0000000 | 2e-7–6e-6 |
| hot key at first split, last split, each side of a split boundary (S=4, S=8) | 1.0000000 | 2e-7–4e-6 |
| rising score ramp, S ∈ {1, 2, 4} | 1.0000000 | 1e-6–2e-6 |

Every adversarial input this session's own amended gate (1) spec called for — precisely the class
of input the original `runAttnCase`'s own header says a diffuse random test cannot see — passes at
essentially f32-rounding-noise precision. The mechanism (cooperative load, per-group online
softmax, cross-simdgroup combine, cross-split combine) is correct.

## Speed in isolation — real, but modest, and depth-gated

Isolated kernel-pair vs shipped kernel, tight-interleaved min-of-40, same synthetic K/V, qwen2.5-
1.5b shape (nH=12, nKV=2, hd=128), this machine (M1 Pro, 14 GPU cores):

| K | S=1 | best S found | ratio at best S |
|---|---|---|---|
| 128 | 0.51-0.53× | — | S=1 always worse; no S tried wins here |
| 512 | 0.39-0.46× | S=14: 0.91× | still a loss |
| 1024 | 0.38× | S=14: 0.98× | just under parity |
| 1536 | — | S=14: 1.07× | first depth to clear parity |
| 2048 | 0.67× (S=4) | S=14: 1.09×, S=20: 1.07× | modest win |
| 3900 | — | S=28: 1.26×, S=14: 1.21× | best measured |

**S=1 is uniformly worse than the shipped kernel at every depth tried (0.38-0.53×), not just
"below a measured crossover" as the brief's own Build text first framed it.** This is the one
correction the speed probe made to the brief's own design: the occupancy crater (only `nKV`
threadgroups active at S=1 — the exact mechanism `ollama-chase.md`'s "staged" attempt crashed on,
0.23×) is a property of threadgroup *count*, independent of depth, so there is no shallow-depth
regime where S=1 is competitive. The production wiring reflects this: `attnFADepthFloor=1536`
declines to the shipped kernel entirely below that depth, rather than dispatching `attention_fa`
at S=1 as the brief's original text proposed.

The wins that do exist (1.07-1.26× on the isolated attention term) are real but modest, and — per
this session's own Amdahl-style finding on the CPU side (`docs/measurements/r13-attn-category-
split-2026-09-19.md`) — should be expected to shrink further once diluted across a full token's
other costs in an end-to-end served-tok/s measurement. That measurement was never reached.

## Real-generation divergence — found, localized precisely, root cause NOT found

`TestAttentionFA_endToEndReproduction`: a real qwen2.5-1.5b checkpoint, batch-prefilled to depth
1600 (past `attnFADepthFloor`), then decoded one token at a time, `attention_fa` enabled vs
disabled, comparing logits:

| decode step | position | cosine | maxAbs |
|---|---|---|---|
| 0 | 1600 | 1.0000000 | 2.86e-06 |
| 1 | 1601 | 1.0000000 | 2.86e-06 |
| 2 | 1602 | **0.9995727** | **0.588** |
| 3 | 1603 | **0.9995052** | **0.623** |
| 4 | 1604 | **0.9995974** | **0.569** |

The first two decode steps past the floor are bit-perfect (the same ~1e-6 noise floor the isolated
kernel gate shows). The third jumps to a stable, clearly-wrong result and stays there — not a
compounding drift, a discrete state change. **Fully deterministic**: reproduced byte-for-byte
across independent full test executions (fresh GPU state, fresh buffer allocations, the shipped
and `attention_fa` runs executed fully sequentially with no two residents alive at once — both
ruled out as the cause).

**Ruled out**, via a per-dispatch debug print (`GOINFER_ATTNFA_DEBUG=1`, kept in the source) at
the `canUseAttnFA` call site: the dispatch parameters themselves. `curNKeys`, `nSplit`, `G`, `hd`
are correct and exactly constant across every layer and every decode step, matching what this
uniform-architecture model should produce — the divergence is not a parameter-computation bug, not
a stale-value bug, and not cross-instance GPU state.

**Not yet investigated** (the search stopped here, time-boxed rather than exhausted): whether
Metal's automatic hazard tracking correctly serializes the `attention_fa` → `attention_fa_combine`
buffer dependency under this kernel pair's specific reuse pattern (a single shared scratch buffer
written and read by 28 layers' worth of dispatches per token, across multiple consecutive command
buffers) — a genuine open question, not a hypothesis already tested and rejected. Also
uninvestigated: whether the third-and-later command buffer specifically (as opposed to the first
two) interacts differently with the shared `r.attnFAPartial`/`r.uAttnFAG`/`r.uAttnFANSplit`
buffers this kernel reuses call-to-call, in a way the shipped kernel's own buffer usage does not
trigger.

## What is and isn't established

**Established:** the core algorithmic mechanism (grouped cooperative loads, per-group online
softmax, cross-simdgroup and cross-split combine) is correct — proven across every adversarial
shape this session's own amended gate specifies. A real, if modest and depth-gated, isolated-
kernel speed win exists past K≈1536. **Not established:** why the identical, individually-correct
mechanism produces a stable wrong answer starting at the third real decode call past the depth
floor. Not reached: end-to-end served tok/s against the brief's own registered ship/park/kill band
(≥60 tok/s at 4000, ≥58 at 2048, no regression beyond 3% at 128) — the real-generation bug blocks
a trustworthy measurement of it.

## Next step, for whoever picks this up

Start from `TestAttentionFA_endToEndReproduction` — it is a known-good, minimal, fully
deterministic repro, not something to rebuild. The two open hypotheses above (Metal hazard-
tracking under this specific buffer-reuse pattern; a first-two-command-buffers-vs-later
distinction) are the most promising next lines, in that order — the "2 correct, then stably
wrong" shape argues for a state-carried-across-calls mechanism specifically, not a per-call
computation bug (which this investigation's parameter-print already rules out). A narrower,
single-layer-in-isolation repro (comparable to `attn_fa_test.go`'s harness, but chaining several
`Dispatch` calls across separately-submitted command buffers instead of one) would isolate the
mechanism without needing a full 28-layer real model.
