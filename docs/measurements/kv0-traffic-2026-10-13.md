## 1. Registration (written and committed before the first study session)

**The question.** For real multi-turn harness sessions: per request, how many of its prompt tokens are a prefix that an earlier
request already computed, within the same session and across sessions; where does the first difference sit and what is there; and
how much prefill time would a KV manager that shares such prefixes save, per new conversation and per turn, on both boxes.

**Instrument.** `kv0_proxy.py` sits between the sandbox and `serve` (an extension of I3's `wire_proxy.py`): it forwards bytes as
received, logs one line per request (route, status, the server's own usage including `prefill_reused_tokens`, start time,
duration, time to first byte) and writes each POST body whole to a directory **outside the repository**. The bodies carry each
harness's own prompts and are not committed. The tokenizer test renders every body with the served model's own tokenizer and
chat template through the same calls its route makes (chat completions with and without tools, Responses, Messages), so the
ids are the ones the server prefilled. **Validity check, per request: the rendered token count must equal the `prompt_tokens`
the server reported.** A request where it does not is excluded from every statistic and listed. What is committed is
`analyze.py`'s output: counts, positions and categories, never ids or text.

**Definitions** (also the header of `analyze.py`).
- *request*: a POST to a generation route. *Thread*: requests of one session whose first 200 tokens are identical (the main
  loop, a title request, a subagent each have their own).
- *lcp_prev*: longest common token prefix with the same session's previous request; *lcp_prev_thread* with the previous request
  of the same thread. *Strictly extends*: the request is longer and its first `len(prev)` tokens equal prev.
- *lcp_other*: longest common prefix with any earlier request of **another session** against the same served model.
- *First divergence* from the previous thread request: its position, and the message (index and role) and offset it falls in.
- *Overlap*: two requests of one session whose [start, start + duration] intervals intersect.
- *reusable(B)* = min(max LCP with any earlier request against the same model, n − 1) rounded down to a multiple of B, for
  B = 64 and 256. *today* = the `prefill_reused_tokens` the server reported. *gain(B)* = max(0, reusable(B) − today): the
  tokens a block-sharing manager would skip beyond what the single-slot server already skipped. The n − 1 cap is rule 3 (the
  last token is always recomputed).
- A *turn* is a request on the session's main thread (the one that carries the tool list). A session counts only if it reaches
  **5 or more turns**.

**Models** (the most capable that holds each harness's context on this card today, recorded per session).
- opencode and Codex: **Qwen2.5-7B-Instruct q4_k_m** at `-ctx 20480 --kv-sessions 1`, CUDA, KV f32. The brief names
  Qwen2.5-Coder-7B; it is not on this box or in the archive. The two share the architecture, tokenizer and chat template, and
  the study measures request structure, so the substitution is disclosed and kept.
- Claude Code (20,199-token first request): **Qwen2.5-Coder-1.5B-Instruct q4_k_m** at `-ctx 32768 --kv-sessions 1`. The
  brief's first choice, gpt-oss-20b with `--moe-cache-experts` and `-ctx 32768`, loads and serves at that context (weights 11.0
  GB paged, KV 1.5 GB), but a 24,371-token prompt is declined by the batched prefill ("layer 1 attention at 12288 attended keys
  needs 49664 B of shared memory, past this device's 49152 B limit") and falls to the per-token path with expert paging; one
  such request had not answered after 10 minutes and was stopped (exploratory, one request, not a rate). So it does not
  resolve for a 20k-token first request on this card. The 7B cannot hold 32,768 positions at f32 KV (112 KB a position), and
  no 3–4B model on this box has a KV small enough (the 1.5B has 2 KV heads, 57 KB a position).
- The serve binary is built from this branch's root at the commit named in `serve-cuda-kv0.rev` of the run directory.

**Sessions.** One session is one headless harness invocation in the I3 sandbox (fresh fixture copy and HOME, `connect -write`
configuration, the harness's own defaults, permissions bypassed inside the sandbox). The server stays up across a
configuration's sessions with one KV slot, so a session's first request meets what the previous session left, as a user's next
conversation would.
- opencode and Codex: tasks `fix` and `edit` (`matrix/tasks.py`), 2 repetitions each, per harness: 4 sessions each, 8 on the 7B.
- Claude Code: the same two tasks × 2 repetitions on the 1.5B, plus two sessions that ask for a subagent (the Task tool) for
  one of two reads: 6 sessions.
- **Stopping rule.** The plan above is fixed. A harness needs at least 3 sessions of 5 turns or more on two tasks, and Claude
  Code one subagent session. If a harness falls short, **the task changes, not the instrument**: add sessions on `write`
  ("add a test for `Reverse` and make it pass") and `search`, then stop at the first set that meets the minimum. A session
  whose server returned 503 `halted` (the swap guard) is void and re-run. No sampling, no early stop on a result.
- **Cost basis.** About 14 sessions at 1–5 minutes each (the I3 smoke: an opencode `edit` session was 14 s and 5 requests; a
  Claude Code first request is about 20k tokens, a few seconds at the 1.5B's measured prefill rate); estimated 30–50 minutes
  of wall time, run detached with the driver's 30-second heartbeat. Timings it incidentally records are exploratory and are
  not quoted as prefill rates.

**The KV4 bar (§6 KV0's decision rule), registered here as the owner's starting point to adjust.** KV1–KV3 go ahead regardless

1. sharing saves **5 s or more of prefill per new conversation** for a Claude Code-class preamble on **either box**, where the

### 1b. Amendment, registered before the study sessions: the model, and the `chain` task

**Plan** (`plan-kv0-traffic.json`; the first plan is `plan-kv0-traffic-v1-coder7b.json`): opencode and Codex, each: `chain` ×2,

**Reading the tables.**
- **Inside a conversation, a request is its previous request plus more.** Strictly extending the previous request of its own thread:
  opencode 40 of 41, Codex 26 of 26. The exception is opencode's one context compaction: a 15,280-token history replaced by a
  7,996-token request that keeps the first 7,151 tokens (the system prompt and tool list) and diverges inside the first user message.
- **Every conversation of a harness begins with the same preamble.** The first main request of a new opencode conversation
  shares 7,151 to 7,216 of its 7,167 to 7,216 tokens (99.7% to 100%) with an earlier conversation's; Codex's, 5,795 to 5,859 of
  5,810 to 5,859. What differs is the task text at the very end. The preamble is the request.
- **What today's single KV slot does with that preamble depends on the harness.** opencode sends a title request first (its own
  system prompt, 543 to 594 tokens, concurrent with the first main request in 5 of 5 sessions) and the title request takes the
  slot, so the server reused **0** of the next conversation's first 7,170 tokens in every session. Codex sends no side request, so
  back to back its preamble is still in the slot (the Responses route reports no reuse; the table's estimate is the overlap with
  the previous request, 5,795 to 5,859 tokens), and the gain is 0 to 29 tokens. **A second conversation, a title request or a
  subagent between two Codex conversations would take that away too.**
- **A compaction is a shared-lead miss.** opencode's request 24 shared 7,151 tokens with the slot's content and the server reused 0
  of them and prefilled all 7,996: the shared-lead rule §1.2 describes, measured.
- **Claude Code's per-conversation header ends the shared prefix at token 22.** Its system prompt opens with
  `x-anthropic-billing-header: cc_version=2.1.296.<3 hex>; cc_entrypoint=sdk-cli;`, and the three hex digits are a function of the
  conversation's first user message (the same prompt twice gives the same digits, a different prompt a different one:
  `header-probe.txt`). The next 17,700 tokens are identical, but they follow a differing token, so no prefix match reaches them: two
  Claude Code conversations share **22 tokens**, and so do the main thread and a subagent or compaction thread of one conversation
  (their digits, and `cc_is_subagent=true`, differ). **With `CLAUDE_CODE_ATTRIBUTION_HEADER=0` the first requests of three different
  conversations share 18,213 of about 20,154 tokens (90.4%)**, up to the user's own first message (`header-probe.txt`: capture
  only, three prompts per arm).
- **Thread switches cost a full re-prefill of the preamble.** Claude Code's two sessions spent 2,240 of 2,861 seconds of request
  time (78%) waiting for first tokens; 13 of 17 requests waited more than 20 s. In the subagent session, three requests that
  returned to the main thread or resumed a subagent re-prefilled 15,531, 8,363 and 17,376 tokens that an earlier request of the same
  session had already computed (41,270 tokens; 15.6% of Claude Code's prompt tokens in the study; the `gain` column).
- **The date question the task doc left open is answered.** The date line is not a per-turn message at the tail of a growing
  conversation: it is at token 17,734 of the first request's 17,755 (21 tokens before its end, just ahead of the user's own
  message in this rendering) and stays at that absolute position in every later request of the conversation. A date change would
  diverge at the end of the 17.7k preamble, not inside it. (A day rollover inside one conversation was not observed.)
- **A card limit, found on the way.** The batched prefill declines past 12,288 attended keys (a 49,664 B shared-memory need
  against 49,152 B), so a Claude Code first request (17,751 to 17,755 tokens here) prefills on the per-token path: **268.7 s to
  its first token, about 66 tokens a second** (exploratory: the chain session's first request; 256.5 s for a 17,134-token one).
  Every re-prefill above costs that, unless it is the small delta after a slot hit (356 to 672 tokens a second).

### 2.4 The KV4 bar, read as registered

1. **Sharing saves 5 s or more of prefill per new conversation for a Claude Code-class preamble on either box.**
   - **As shipped: no.** Claude Code conversations share 22 tokens: 0 s on both boxes.
   - **With the attribution header off: yes on the Mac** (29.7 s at its measured 21k rate, about 6 times the bar). **On nobara it
     depends on the rate**: 4.5 s at the 1.5B's batched rate at 3,900 tokens, just under 5 and the optimistic rate for a deep
     prompt; about 275 s on the per-token path the card takes at that depth.
2. **The capacity arithmetic shows at least twice the single-conversation context on the 8 GB card at the default slot count: yes.**
   With no flags the 7B (Qwen2.5-7B-Instruct q4_k_m) loads as **4 conversations x 11,784 positions** at f16 KV (7,511 MiB used;
   `capacity-banners.txt`); with `--ctx 32768` (the model's maximum) it gives **1 conversation x 32,768** (6,751 MiB). A pool
   holding the same 47,136 positions could give one conversation the model's maximum: 32,768 / 11,784 = **2.78 x**, and still
   leave 14,368 positions for others (the pool alone would allow 4.0 x; the model stops at 32,768). At `--kv-sessions 1` the default
   context is 16,384, and Claude Code's first request (20,199 tokens in the I4 census) fits neither default.
3. **Read against §6's rule as registered ("KV4 goes ahead when either clears"): the capacity arm clears; the sharing arm clears
   conditionally.** Two cautions belong beside the verdict, and whether they change it is the owner's call:
   - the sharing saving is delivered by KV2 (a device copy between slots, no paged attention), so arm 1 is evidence for KV1 to
     KV3, and it needs the Claude Code header gone (a `connect` setting or a server-side normalisation) before it exists at all;
   - arm 2's 2.78 x is what paging gives that flags do not: a user can already reach 32,768 with `--ctx 32768 --kv-sessions 1`,
     at the price of the other three conversations.

### 2.5 What this study does not show

- One model family (the Qwen3 tokenizer and template), one box, harness versions as pinned (Claude Code 2.1.296; Codex and opencode
  as in the I4 census), scripted tasks in a sandbox with a fixed directory and HOME. A real user's directory, HOME and git state add
  variation to Claude Code's first request: the probe fixed both, and with a random HOME the header-off conversations diverged at
  token 588, at a memory path under HOME.
- Short sessions (at most 22 turns): long-session compaction and day rollover are not covered. No hybrid model was driven, so
  nothing here measures recurrent-state reuse; it is FreeToken Lead 1's data only in the sense of the prefix structure real
  sessions have.
- The Mac was not run (no Mac in this session): its column is a projection from the one measured long-prompt rate.
- No pilot session (8 on Qwen2.5-7B-Instruct, 14 on the Coder-7B, 20 in model selection) is in any statistic above.
