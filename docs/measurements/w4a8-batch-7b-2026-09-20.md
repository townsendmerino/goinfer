# R-06 follow-up — `GOINFER_W4A8_BATCH` at 7B: an even cleaner null than the 1.5B result

**Result: at 7B, batched q/k/v and gate/up W4A8 matmuls show NO measurable effect — OFF 58.98
ms/token (stdev 2.10), ON 59.0 ms/token (stdev 1.60), a 0.017 ms difference against stdevs of
1.6-2.1 ms.** This is a cleaner (more decisively null) result than R-06's own original 1.5B
measurement (1.071×/1.066×, ambiguous), not a size-dependent win. Confirms the fixed-cost
reasoning below rather than the naive "MLP dominates more at 7B, so its fix should help more"
read of R9 step 1's own table.

## Why this was run

R9 step 1 ([`cpu-decode-attribution-2026-09-20.md`](cpu-decode-attribution-2026-09-20.md)) found
MLP's share of the decode token grows with model size (56.7% → 61.5% → 70.1% from 0.5B to 1.5B to
7B). R-06 ([`docs/tasks/task-recompute-audit.md`](../tasks/task-recompute-audit.md)) already
built, wired (`GOINFER_W4A8_BATCH`, default off) and measured `MatmulBTW4A8Batch`'s q‖k‖v and
gate‖up fork-join fusion — but only on the 1.5B, where it landed ambiguous (1.05-1.15× band) on
two independent architectures. The open question: does R-06's remedy do *better* at 7B, where MLP
now dominates the token more heavily?

**The mechanism says no, and this measurement checks that reasoning rather than trusting it.**
R-06's win comes from amortizing a roughly *fixed* per-barrier cost (aikit S-02's own measured
goroutine-wake-stagger, ~92.6 µs start-spread per fork/join) across fewer, larger fork/joins (3→1
for q/k/v, 2→1 for gate/up). That fixed cost doesn't scale with model size; the matmuls it's
amortized against do. A bigger model's individual matmul calls take proportionally longer, so the
same ~93 µs fixed saving is a *smaller* fraction of a *slower* token — the opposite of "MLP
dominates more, so batching MLP helps more." Growing MLP *share* is about MLP's own compute cost,
not about the fork/join overhead R-06 targets; the two are different axes.

## Method

Box: `apple-m1pro` (M1 Pro, 6P+2E, 16 GB). goinfer `e22c771b`. Model:
`qwen2.5-7b` (int4, Backend:"cpu"), same checkpoint and 128-token prompt as R9 step 1. New test
`TestR9_w4a8BatchAt7B` (`decoder/r9_decode_attribution_test.go`) — no core-file changes, uses only
the public `decoder.Load`/`Generate` API and the already-shipped `GOINFER_DECODE_TIMING`.

`w4a8BatchEnabled` (`decoder/weightmat.go`) is a package-level var read once from
`GOINFER_W4A8_BATCH` at process start — it cannot be toggled mid-process, so this required **two
separate process runs** (one per env setting), each loading the model once and running 6 repeated
decode windows (fresh KV cache each, no reload between repeats) for a within-arm mean/stdev.

**This is a real limitation next to R-06's own design**, which alternated arms within one
interleaved session specifically to guard against session/thermal drift (this repo's own measured
~3.5% drift risk between sessions). Two back-to-back process blocks, run within minutes of each
other on this session, is the best available compromise given the constraint — not equivalent to
R-06's own rigor, but the two means landing 0.017 ms apart (an order of magnitude below either
arm's own stdev) makes drift an implausible explanation for *this particular* result: a drift
large enough to manufacture that level of agreement by coincidence would be a remarkable one.

Both runs used `GOINFER_NO_FIT_GUARD=1` (needed for 7B on this machine) with the same external
(outside the test process) RSS/swap monitor discipline as the rest of this session's memory-heavy
work. **Swap never grew in either run** — no near-incident.

## Data

| arm | n | mean ms/token | stdev | individual samples (ms) |
|---|---:|---:|---:|---|
| OFF (`GOINFER_W4A8_BATCH=0`) | 6 | 58.98 | 2.10 | 62.1, 60.9, 56.7, 58.6, 57.3, 58.3 |
| ON (`GOINFER_W4A8_BATCH=1`) | 6 | 59.0 | 1.60 | 59.0, 58.2, 57.6, 58.9, 58.2, 62.1 |

Ratio (OFF/ON, >1 = ON faster): **0.9997× — indistinguishable from 1.0**, well inside the noise
band either arm shows on its own (both stdevs are ~3% of the mean; the between-arm difference is
0.03%). This is not "ambiguous" in R-06's own registered sense (1.05-1.15×, needing more data to
resolve) — it is a value close enough to exactly 1.0 that more samples would be very unlikely to
move it into either the park or ship band.

## What this establishes, and what it doesn't

**Established:** R-06's fork/join-amortization remedy shows no measurable benefit at 7B on this
box — if anything a marginally *worse* central estimate than the 1.5B's already-ambiguous 1.07×,
consistent with (not proof of) the fixed-cost-amortized-over-a-larger-matmul reasoning above.

**Not established:**
- A rigorous, R-06-quality interleaved measurement — this used two blocks, not alternating
  single-window arms, for the reason given above (the var can't be toggled mid-process without a
  code change this follow-up didn't make).
- Whether a *lower-level* MLP-specific remedy (S-05's SDOT centering fold, or the fan-out shape
  changes R9 step 2 also names — S-03/S-06, "built and gate-checked in aikit, unmeasured end to
  end on the Mac") would do better. This result only closes the fork/join-fusion avenue at 7B; it
  says nothing about MLP's own compute-level levers.
- 0.5B — R-06's own two measured architectures didn't cover it either; if the fixed-cost
  reasoning is right, 0.5B (the smallest matmuls, so the largest *relative* fixed-cost share)
  should be R-06's best case, not its worst — untested, and the natural next check if this avenue
  is revisited.

## Decision

**R-06 stays parked, now with 7B evidence supporting the same disposition the 1.5B measurement
already reached — not reopened.** No code change from this follow-up; it is a confirmatory
negative result, recorded with the same care as a win per this repo's own measurement discipline.
If R9 step 2 wants a real MLP lever, the fixed-cost-amortization avenue (R-06) is now checked at
two sizes and closed at both; the next candidates are compute-level (S-05 and friends), a
different question from fan-out.
