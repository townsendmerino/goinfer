## 1. What the CUDA half is, and the choices made before the code

The decoder side is built (the record's §1): `decoder.ResidentKVCopier`, `decoder.KVCopyDecline` and
`decoder.ResidentReusableKVSlot` are on this branch, in `decoder/resident_reuse.go`, and `Model.residentShare` calls
them. The CUDA half implements the two interfaces on `cudaResident`, and runs the CUDA arm of every gate. No kernel that
computes attention changes, and nothing is allocated.

1. **`CopyKV(src, dst, start, end)` is a device-to-device copy on the executor's stream.** It runs as one executor job
   (`cudaResident.do`), with the existing exact copy launch (`copyF32`, a `kv_store` at position 0, no arithmetic) per
   layer and per buffer. Buffers are addressed in bytes from the layer's element size: an f16 layer (`kvHalf`) copies
   `(end − start) · kvDim / 2` 32-bit words from byte `start · kvDim · 2` (kvDim is even for every geometry); an f32
   layer `(end − start) · kvDim` words from byte `start · kvDim · 4`. CUDA has no int8 KV, so there are no scales.
2. **Per layer kind:**
   - a full-attention layer copies rows `[start, end)` of K and V;
   - an MLA latent layer copies rows `[start, end)` of its latent buffer (`kc`; it has no `vc`);
   - a layer that reads another layer's KV (`kvShared`, the Gemma 4 E-models) copies nothing: it aliases its source,
     which is copied;
   - a windowed layer (`kvWin`) copies src's rows `[lo, end)`, `lo = max(0, end − (window − 1))`, which is exactly what
     dst attends to when it continues at `end`, reading through src's shifted view and writing dst at physical slot 0, and
     sets dst's base (`kvBases[dst]`, and `kvBase` when dst is bound) to `lo`. Rows of `[lo, start)` that dst already held
     are rewritten with src's bytes of the same published blocks, which the index promises are bit-identical (the class is
     in the key). All windowed layers share one window and so one base per slot, so the base is set once.
3. **Declines, before anything is written** (`*decoder.KVCopyDecline`, reason named):
   - a windowed src whose base is past `lo` (the rows dst needs were compacted away), naming the layer and src's base;
   - a windowed layer held at f16 (the policy keeps every sliding-window family at f32 today, and the shifted view
     assumes 4-byte elements, so a copy must not assume more than the view does);
   - a recurrent family (`dnet != nil`; the decoder never asks, this is defence);
   - one KV slot, or `end` past the context.
   Malformed arguments (`src == dst`, a slot out of range, `start` or `end` not a multiple of 64, `start > end`) are a
   plain error, as on Metal. The check of src's base runs **inside the same executor job as the copy**, so a compaction
   of a running src cannot fall between the check and the read.
4. **A busy source** (the record's choice 2): the decoder may copy the prompt rows of a slot whose generation is decoding
   under MC3. One executor goroutine and one stream order everything: the copy job is posted after the source's prefill
   (which returned before its rows were published) and runs between MC3 steps, never during one. The source's decode
   writes only rows past its prompt, and the copy reads only full blocks of the prompt, so the ranges are disjoint; on
   a windowed source, a step that compacts it runs before or after the copy job, and the in-job base check sees which.
5. **`ReusableKVSlot(slot, prefix)`** is `ReusableKV`'s rule (`kvWindowReusable`) on `kvBases[slot]`, read on the
   executor, for any slot bound or not.
6. **Nothing is allocated, and the build is unchanged.** src and dst are different buffers, so no staging buffer is
   needed (the compaction scratch is not used). The plan, the KV slot count, the context, the expert cache and the
   windowed rollback grant (`kvGrantRollback` on `main`, which takes only VRAM nothing else will use) are all decided
   before any copy and are not touched by KV2. A paged-experts (C′) load allocates one KV slot, so the decoder never
   copies on it: KV2 is inert there by construction, and GV-C checks that it stays so.
7. **Where the CUDA half is built:** a new file in `cuda/` (the copy, the slot question, their compile-time assertions)
   and its tests; no change to `decoder/`, `internal/kvmgr` or serve. A decoder or serve defect found by a CUDA gate is
   reported to the Mac session, not fixed here.
8. **The base for G5 and G6 (a deviation from the brief, registered).** The brief names `BASE = 1cc385ef`, the Mac's
   branch point. nobara's `REV` will contain `main` at `4d393367` or later (KV3's CUDA chunker and long-prompt prefill,
   the windowed rollback grant), none of which is at `1cc385ef`. Against `1cc385ef` both gates would measure KV3 and the
   grant together with KV2. **nobara's `BASE` is the `main` commit merged into `REV`** (the merge's second parent),
   named in the provenance block, so the two arms differ by KV2 alone.

## 2. The gates, CUDA arm

Every gate except G5-C and G6-C: fixed cases, run to completion, no sampling, no early stop. A skip is not a pass: every
`go test` runs `-v` with an explicit `-timeout`, its log is read for `--- PASS`, and each skip is listed with its reason.
Every planted defect is shown red once, removed, and its red output kept beside the record
(`kv2-2026-10-14/planted-cuda.txt`). Every GPU command opens with the timing-lock guard. **Void for every gate:** a fit
guard refusal or a clamped slot count where the test needs more (void and re-run, not a failure); a test the gate lists
absent from the run; a run on a tree whose test files differ from the commit named.

Day costs below are estimates for this box; any arm over about 10 minutes moves to the night job instead.

### G0-C. Split invariance at f16, and KV0 re-read after KV3 (day)

KV0 measured CUDA's aligned splits at f32 only (its rig asserts f32 caches), and before KV3 changed the chunker. G5 runs
at f16, the CUDA default for the 1.5B.
- **Arms:** KV0's (splits at 512, 768 and 984 of a 1,000-token prompt; chunk widths 64 and 448) and the record's short
  suffix (960 of 965), each against the prompt in one call; on `llama-attnfa-tiny` and Qwen2.5-Coder-1.5B q4_k_m, at
  f32 (`TestKV0_prefillInvariance_*` as on `main`) and at f16 (a new arm reading the f16 caches as raw halves).
- **Rule:** KV0's: every layer's K and V rows and the last logits, 0 elements differ, after KV0's control (a token
  changed at 300 shows from 300 and nowhere before). The 965 arm on CUDA is expected to differ (a 5-row pass is exact
  class) and is reported as the class rule, not a failure: the hit cap (G4-C(b)) keeps such a suffix from existing.
- **Decides:** an f16 arm that is not invariant means CUDA does not share at f16. That is reported to the owner, and
  CUDA's sharing is held to f32 loads until it is resolved; it is not a KV2 failure.
- Prediction (0.85): invariant at f16 as at f32 (the `_kv16` twins only change the load and store).
- Cost: about 2 minutes.

### G1-C. Identity (day)

- **Rule:** the record's G1 on CUDA: `TestWindowedKV_*`, and every `cuda` test matching `Reuse|Slot|MC3|MC4|Lead|Resident`,
  run with `-tags 'cuda goinfer_testhooks'`, pass, with their test files byte-identical to `main` at the commit merged

- **Exception:** the record's (a test asserting `main`'s in-place take of another conversation's slot may change, named

- Cost: about 5 minutes; if it runs longer, the real-checkpoint tests move to the night job, by name.

### G2-C. The copy is exact (day)

**(a) The copy.** Fill two slots with different prompts, then `CopyKV(src, dst, start, end)` at `[0, 64)`, `[0, 1024)`,
and `[256, 1024)` into a slot that already holds rows below 256; read back every layer's K and V of both slots.
- **Rule (full and latent layers):** dst's rows in the range equal src's byte for byte; dst's rows outside the range are
  unchanged; src is unchanged.
- **Rule (windowed layers):** dst's base is `lo`; dst's held rows `[lo, end)` equal src's byte for byte; src and its
  base are unchanged.
- **Fixtures:** `llama-attnfa-tiny` and the 1.5B at f32 and f16; the three windowed fixtures (`mistral-tiny-window`,
  `gemma3-vl-tiny`, `cohere2-tiny`) with the slack lowered so src's base is past 0 (the copy reads through a shifted
  view); `deepseek-tiny` (MLA latent); `gemma4-emodel-tiny` (shared-KV layers).
- **Decline:** a windowed src compacted past `lo` returns `KVCopyDecline` naming the layer and src's base, and every
  byte of dst, and dst's base, is unchanged. A recurrent fixture declines.

**(b) A copied prefix is the prefix computed (the owner's identity question).** Slot A prefills a 1,000-token preamble
plus its own message. Slot B's prompt shares the preamble: B copies the block-aligned hit from A, then prefills the rest.
- **Rule:** B's K and V rows for its whole prompt, and its last logits, are bit-identical to B's prompt prefilled cold
  in a fresh slot. On a windowed fixture, B continues 300 decode steps past the copy, and every step's logits equal the
  cold reference's.
- **Fixtures:** as (a), at f32 and f16 where the fixture is f16-eligible.

**Planted** (each must turn its rule red):
1. a copy one block short;
2. a copy whose layer index is off by one (the next layer's buffers);
3. an f16 layer copied with the f32 element count (writes past the range: "outside unchanged" goes red at f16);
4. a windowed copy that does not set dst's base;
5. a windowed copy that reads src through the unshifted view (red only where src's base is past 0, which is why the
   fixtures lower the slack);
6. the in-job base check removed (the decline case writes dst).

Prediction (0.9): all pass. Cost: about 3 minutes.

### G3-C. Schedule independence (hard; day)

- **The record's design unchanged:** conversations A, B and C share a 1,000-token preamble (above CUDA's 512-token
  floor); schedules (a) to (f) with 2 slots; greedy plus one sampled arm with fixed seeds; reference = each turn alone on
  a fresh load (a continuation's reference continues alone). Through `Generate` on the CUDA resident; (d) and (e) under
  MC3 (`EnableResidentConcurrency(2)`).
- **Models:** `llama-attnfa-tiny`; the 1.5B int4 (`-kv auto`, so f16); one windowed fixture with a schedule in which a
  copy declines (src compacted past the hit), where the declined turn's reference is its cold prefill.
- **Rule:** every emitted token equal and every step's logits bit-identical (float32 bits) to the reference; for every
  copy, the requester's copied rows equal the rows its own cold prefill writes (the task doc's §5.6 property 2), read
  back through a test hook.
- **Choice 5 on CUDA:** a block-drafter load (serve's `-drafter`; in process, the Qwen3-4B target with its DFlash drafter
  from `~/models`) reports `PrefillShared` 0 on every turn of schedule (a), and its replies equal its replies with
  sharing off. Void, and reported, if the drafter assets are absent.
- **Planted:** a copy that reports success without copying (red in the copied-rows check); a busy-source copy whose
  range ends one block past the source prompt's full blocks (it reads decode-written rows; red in (d)).
- Prediction (0.85): all pass. Cost: about 6 minutes (the 1.5B's references are most of it).

### G4-C. KV1's carry-overs on the device (day)

- **(a) The recorded class is the class that ran.** For prompts of 985, 1,030 and 4,000 tokens, and a hit followed by a
  suffix, the class `KVBoundClassesForTest` records for each row equals the class KV0's launch counts show ran it
  (`attn_fused` launches per pass against passes of 16 rows or more starting at or past the floor).
  - Planted: the decoder records a whole call as one pass. KV3's chunker no longer cuts a short tail, so a test hook
    restores one (a chunk width that leaves a 15-row last pass). If the plant cannot be made to go red, the gate says so
    and is not counted as proven.
- **(b) A hit leaves the requester the rows its cold prefill needs.** A 975-token prompt whose first 970 another slot
  holds: the block-aligned hit is 960, which leaves 15 rows; the cap shrinks it to 896, leaving 79. The reply and every
  step's logits equal the prompt prefilled alone.
  - Planted: the cap at n − 1. The rows then differ from 960 on, as KV0's `split@985` arm did.
- **(e) Fast rows on a windowed layer from a pass that started off a block boundary are never copied.** KV1's G2b
  instrument (a window set on the 1.5B, the fused kernels): a continuation whose pass starts at 600 records those rows
  with no producer, and another conversation sharing them copies only up to the last block before 600.
  - Planted: `ClassMap.PassAt` ignoring `Windowed` (red: the copy takes rows from 640 on, which differ).
- (c) and (d) are serve and decoder tests with no backend in them; they are read on the Mac and re-run here inside G1-C.
- Cost: about 4 minutes.

## 3. Sharing keys on token ids (owner, 2026-10-15)

Cross-conversation sharing keys on **token ids**, never text (the task doc's §2, rule 1). Under the id round trip's
proposal 2, a reply's generated ids come back in a signed opaque field and are used instead of re-tokenizing the echoed
text (PR #24's step-0 record, on branch `id-roundtrip-step0-2026-10`). Two conversations whose prompts carry the same
text but different ids, one carrying a reply's non-canonical generated ids and the other re-tokenizing that text, hash
differently from the first differing id, so a copy stops at the block before it.

**That is acceptable, and KV2's gates need no change for it.**
- What crosses conversations is the prefill-class preamble (system prompt, tools, environment), which no carried id
  touches and which both tokenize identically.
- A reply's rows are decode class, and property 3 (§5.6) never shares those across conversations, whatever the ids.
- Matching on text would mean treating two different id sequences as the same input, which they are not: their KV
  differs, so it would break property 2.

The same note is in the task doc's KV2 section.
