# R-15: the int8-KV widen runs on all cores, bit-identical (Qwen2.5 1.5B 1.234x at depth 2000), 2026-10-05

Audit entry: `docs/tasks/task-recompute-audit.md` section 5, R-15. Code: `decoder/kvdequant_parallel.go` (`dequantKVRows`), used by `dequantGlobalLayer` and the int8 ring window read in `batchReadLocal` (`decoder/kvcache.go`).

## What changed, and what did not

With `--kv i8` an int8-KV decode token widens every stored K and V row of every global layer back to f32 (`dequantGlobalLayer`), and a ring layer's whole window the same way, directly in front of the attention. That is O(context) per token per layer, and it ran on ONE thread. It is elementwise (`float32(q) * scale` per row, no shared state), so it is now split by rows across the process's usual fan-out width (`fusedWorkers`), above a size where a fork/join pays (128 Ki floats of K and V together). No bit moves, and memory is unchanged: the int8 cache is still the only copy; the f32 scratch is the same scratch as before.

**Not done:** the widen itself is still O(context) per token (a persistent f32 shadow would cost 4.5 bytes per element on top of the 1.125 of the int8 cache, worse than f32 KV; a fused int8 attention would not be bit-identical to the f32 path decode, prefill and verify share). And the ring's "new row quantized twice" (the round trip, then `ring.write`) is left alone: it is `kvDim` elements per layer per token, microseconds, and the two quantizations are of the same data, so a reuse would save nothing measurable.

## 1. Size, by instrument (throwaway timer around the `dequantGlobalLayer` call, since removed)

Qwen2.5 1.5B, depth 2000, one run each: f32 KV forward 59.51 ms/token; int8 KV forward 80.53 ms/token, of which the widen is **17.41 ms/token** (417.9 ms over 24 tokens). The int8 token was 21 ms slower than the f32 token and the widen is 17 of those 21.

## 2. Bit identity

- `TestDequantKVRows_bitIdenticalToTheSerialWiden`: random int8 rows and scales, nine shapes (one row up to 4096, rows not divisible by the worker count, below and above the real threshold), compared bit for bit with two serial `linalg.DequantizeRowsInt8Into` calls, with the destination poisoned with NaN, and a non-vacuity check that some case really forked.
- `TestKVI8_parallelWidenBitIdenticalOnWholeDecodes`: cohere2-tiny and gemma2-tiny (int8 RINGS) and llama-tiny (global), 40 steps each, threshold forced to 1 so the tiny sizes fork, every logit equal bit for bit.
- Real Qwen2.5 1.5B, int8 KV, depth 2000, 48 decode steps, full logits through the sampler's `LogitProcessor`: **48 x 151936 logits compared, 0 differ** (`TestCPUKVI8_parallelWidenLogitsBitIdentical`).
- Each shown red by planting a bug: the last worker's chunk dropped, the caller's chunk one row short, V widened with K's scales.

Qwen2.5 1.5B, every layer global, depth 2000:

Means 66.55 ON, 81.87 OFF ms/token; paired median **1.234x**, range 1.218 to 1.238, 4 of 4 pairs faster. The int8 token is now 7 ms over the f32 token (59.5) instead of 22.

Gemma 3 1B (int8 rings of 512 rows plus global layers), depth 900: means 39.51 ON, 40.17 OFF, paired median **1.017x**, range 1.009 to 1.026, 5 of 5 pairs faster. Small because its widen is small (a 512-row window) and the rest of its token is unchanged.

By TE5(b) these are resolved directions from whole-token in-process A/Bs (every pair above 1), so the change is kept by day. No pre-registered band; not a served or peer claim, and not timed at other depths.
