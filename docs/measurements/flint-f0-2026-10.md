## 2. F0.2 — Tokenizer and chat template

### 2.1 Tokenizer family and pre-tokenizer

- **Family:** Byte-level BPE (`model.type = "BPE"` in `tokenizer.json`; `tokenizer.ggml.model = "gpt2"` and `tokenizer.ggml.pre = "flint"` in GGUF).
- **Vocabulary:** `150,144` tokens (`0..149999` base BPE vocabulary + `144` added tokens `150000..150143`; `149,744` merge rules; `normalizer: null`; `add_bos_token: false`, `add_eos_token: false`).
- **Added tokens (`150000..150143`) and `special` flag:**
  - `150000` `<|begin_of_text|>`, `150001` `<|end_of_text|>`, `150002` `<|system|>`, `150003` `<|user|>`, `150004` `<|assistant|>`, `150005` `<|observation|>`, `150018` `<|developer|>`, and `150019..150143` `<|reserved_*|>` have `special: true` (`normalized: false`).
  - `150006` `<think>`, `150007` `</think>`, `150008` `<tools>`, `150009` `</tools>`, `150010` `<tool_call>`, `150011` `</tool_call>`, `150012` `<arg_key>`, `150013` `</arg_key>`, `150014` `<arg_value>`, `150015` `</arg_value>`, `150016` `<tool_response>`, `150017` `</tool_response>` have **`special: false`** (`normalized: true`).
  - Because `tokenizer/tokenizer.go:Load` registers all `added_tokens` into `addedTrie` and `chat/chat.go:Template.RenderSegments` marks template-emitted structural markers (`<think>`, `</think>`, `<tool_call>`, `<arg_key>`, etc.) as `Special: true`, `EncodeSegments` matches `150006..150017` on template-rendered structural spans while keeping untrusted user/tool content non-special.
- **Pre-tokenizer (`tokenizer.json` and `llama.cpp` `LLAMA_VOCAB_PRE_TYPE_FLINT`):**
  A `Sequence` of three `Split` passes (`behavior: "Isolated"`, `invert: false`) followed by `ByteLevel` (`add_prefix_space: false`, `trim_offsets: true`, `use_regex: false`):
  1. `\p{N}{1,3}` — isolates 1-to-3 digit runs.
  2. `[一-龥\u3040-\u309f\u30a0-\u30ff]+` — isolates contiguous runs of CJK Unified Ideographs (`U+4E00..U+9FA5`), Hiragana (`U+3040..U+309F`), and Katakana (`U+30A0..U+30FF`).
  3. `[^\r\n\p{L}\p{N}]?[\p{Lu}\p{Lt}\p{Lm}\p{Lo}\p{M}]*[\p{Ll}\p{Lm}\p{Lo}\p{M}]+(?i:'s|'t|'re|'ve|'m|'ll|'d)?|[^\r\n\p{L}\p{N}]?[\p{Lu}\p{Lt}\p{Lm}\p{Lo}\p{M}]+[\p{Ll}\p{Lm}\p{Lo}\p{M}]*(?i:'s|'t|'re|'ve|'m|'ll|'d)?| ?[\p{P}\p{S}]+[\r\n]*|\s*[\r\n]+|\s+(?!\S)|\s+` — the `o200k` regex (`tokenizer/split_o200k.go:splitO200K`, without its `\p{N}{1,3}` branch since step 1 already isolated digits).
- **Current `goinfer` behavior on `tokenizer.Load`:**
  - `tokenizer/splitshape.go:splitRegex` inspects only the first `Split` step (`\p{N}{1,3}`), which `classifySplit` classifies as `shapeUnknown`, and `tokenizer/gguf.go:byteLevelKnobs` does not yet recognize `"flint"`. Both set `PreTokenizerDecline` (`"pre-tokenizer regex is the unknown alternation, which this build does not walk; this model's token ids differ from HF"`) and fall back to `splitGPT2` (`cl100k`).
  - Why step 2 (`[一-龥\u3040-\u309f\u30a0-\u30ff]+`) + step 3 (`o200k`) both matter:
    - Versus `splitGPT2` (`cl100k`): `o200k` keeps English contractions attached to the word (`"don't"` → `[40634]`, `"I'll"` → `[27961]`, `"user's"` → `[22339]`), whereas `splitGPT2` splits before the apostrophe (`"don"` + `"'t"` → `[16062, 750]`).
    - Versus `splitO200K` alone: isolating CJK/Kana in step 2 before step 3 prevents the last space of a multi-space run (`"   东京"`) from attaching to the CJK run via `[^\r\n\p{L}\p{N}]?` (`flint` produces `['ĠĠĠ', 'ä¸ľäº¬']` → `[279, 16871, 20680]`, whereas `o200k` alone produces `['ĠĠ', 'Ġä¸ľäº¬']` → `[256, 220, 16871, 20680]`).
  - **F1 fix:** Add `shapeFlint` (`splitFlint`), which isolates `\p{N}{1,3}` and `[一-龥\u3040-\u309f\u30a0-\u30ff]+` spans first and runs `splitO200K` on the spans between them, wired from both `tokenizer/splitshape.go:splitRegex` (matching the 3-step `Sequence`) and `tokenizer/gguf.go:byteLevelKnobs` (`case "flint":`).

### 2.2 Chat template (`chat_template.jinja`)

- **Role markers and turn structure:**
  - Leading `system` or `developer` messages render as `<|system|>\n{text}` or `<|developer|>\n{text}` (a newline is inserted after the role token only if `text` does not already start with `\n`).
  - Subsequent turns render with **no newline after the role token** and **no end-of-turn suffix token**:
    - `user`: `<|user|>{text}`
    - `system` / `developer` mid-conversation: `<|system|>{text}` / `<|developer|>{text}`
    - `assistant`: `<|assistant|>{%- if m.reasoning_content %}<think>{{ m.reasoning_content }}</think>{% endif -%}{{ text }}{tool_calls}`
    - `tool` / `observation`: `<|observation|><tool_response>{{ text }}</tool_response>` (consecutive `tool` messages coalesce under a single `<|observation|>` with one `<tool_response>...</tool_response>` per message).
    - Generation prompt (`add_generation_prompt=True`): appends `<|assistant|>`.
  - **Stop tokens:** Because turns have no closing marker (`<|im_end|>` or `<|eot_id|>`), a turn ends when the model generates `<|end_of_text|>` (`150001`), `<|user|>` (`150003`), `<|observation|>` (`150005`), or `<|developer|>` (`150018`), matching `eos_token_id` in `config.json`.
- **Handling of `reasoning_content`:**
  - There is **no** `enable_thinking` template switch: the generation prompt always ends with bare `<|assistant|>`, and the model decides whether to open `<think>...</think>`.
  - In history, `<|assistant|>{%- if m.reasoning_content %}<think>{{ m.reasoning_content }}</think>{% endif -%}` preserves `reasoning_content` on **every** prior assistant turn (`histAll`), not only after the last user turn (`histLastUser`).
- **Handling of tool calls:**
  - Uses the GLM-4.7 XML tool format (`<tools>`, `<tool_call>`, `<arg_key>`, `<arg_value>`, `<tool_response>`):
    - Tools preamble (injected after leading `system`/`developer` messages and before the first user turn):
      ```text
      <|system|>
      # Tools

      You may call one or more functions to assist with the user query.

      You are provided with function signatures within <tools></tools> XML tags:
      <tools>
      {"type": "function", "function": ...}
      </tools>

      For each function call, output the function name and arguments within the following XML format:
      <tool_call>{function-name}<arg_key>{arg-key-1}</arg_key><arg_value>{arg-value-1}</arg_value><arg_key>{arg-key-2}</arg_key><arg_value>{arg-value-2}</arg_value>...</tool_call>
      ```
    - Assistant tool call: `<tool_call>{{ fn.name }}<arg_key>{{ k }}</arg_key><arg_value>{{ v | tojson(ensure_ascii=False) if v is not string else v }}</arg_value></tool_call>`
    - Tool result: `<|observation|><tool_response>{{ content }}</tool_response>`
- **Comparison through `goinfer`'s template and tokenizer path today:**
  1. `chat/chat.go:Detect` returns `ErrUnknownTemplate` (`chat: unrecognized chat template (raw-completion fallback)`) because Flint's `<|user|>`/`<|assistant|>`/`<|observation|>` template has neither `[gMASK]<sop>` (GLM) nor `<|end|>` (Phi-3).
  2. Feeding the reference-rendered two-turn tool conversation (system + `get_weather` tool declaration + user turn 1 + assistant `<think>` & `<tool_call>` + `<|observation|><tool_response>` + assistant `<think>` & summary + user turn 2 + `<|assistant|>`) through `tokenizer.Load`:
     - **Case A (no English contractions or multi-space CJK prefixes):** Both HF `tokenizers` and `goinfer` (`tok.Encode(prompt, false)`) produce **275 identical token IDs** (`[150002, 198, 2356, ..., 150006, ..., 150007, 150010, ..., 150011, 150005, 150016, ..., 150017, 150004, ..., 150003, ..., 150004]`), because `addedTrie` matches all role and XML tool/think tokens (`150002..150017`) and `splitGPT2` shares `\p{N}{1,3}`.
     - **Case B (with realistic English contractions `"What's"`, `"I'll"`, `"user's"`, `"It's"`, `"don't"` and `"   东京"`):** Reference HF `tokenizers` emits **261 tokens** whereas `goinfer`'s declined `splitGPT2` fallback emits **268 tokens**, differing at the 6 contractions (`[20638]` vs `[2387, 503]` for `"What's"`, `[27961]` vs `[40, 2926]` for `"I'll"`, `[22339]` vs `[1464, 503]` for `"user's"`, `[7614]` vs `[331, 2926]` for `" I'll"`, `[6430]` vs `[1304, 503]` for `"It's"`, `[1827]` vs `[1376, 750]` for `" don't"`) and at `"   "` before `"东京"` (`[279]` vs `[256, 220]`). Implementing `splitFlint` + `chat.Flint()` in F1 eliminates all 7 diffs.

### Parity-tier options for the owner's choice (F0.3 stop point)

Because **(a) `transformers` mainline (`FlintForCausalLM`)** now exists and runs on CPU in pure PyTorch, we do not need to fall back to (b). However, the full 49-layer BF16 checkpoint is `79.57 GB` (`74.11 GiB`), which exceeds `nobara`'s `62 GiB` physical RAM (`60 GiB` available) if loaded whole in BF16. Three parity-tier options are available:

1. **Option 1 (Recommended — Tier T2 tiny-oracle + real-slice BF16 oracle from (a) `transformers`, plus GGUF parity against (c) `llama.cpp`):**
   - **Committed CI gate (`testdata/flint-tiny/`):** A 4-layer tiny synthetic checkpoint (layers `0, 1` dense full-attention/NoPE; layer `2` MoE sliding-attention/RoPE; layer `3` MoE full-attention/NoPE; `256` or `8` experts, top-6 sigmoid normalized router, ungated shared expert, learned `softmax_offset` sinks) generated and golden-pinned against `transformers` `FlintForCausalLM` (`1e-4` logits & hidden states in `cmd/gate`), plus the F2 window-boundary golden (`512, 513, 514, ~1,100` tokens) against `transformers` `FlintForCausalLM`.
   - **Real-weight BF16 layer-slice gate (no 80 GB download or RAM needed):** Extract layers `0, 1, 2` (the 2 dense full/NoPE lead layers + the first MoE sliding/RoPE layer with real trained `softmax_offset` sinks and router) plus `embed_tokens`, `norm`, and `lm_head` (`~4.1 GB` in BF16 via HTTP Range requests from `ggml-org/Flint-GGUF`'s `Flint-BF16.gguf` or `RecursiveSI/flint`), and verify `1e-4` real-weight logit parity against `transformers` `FlintForCausalLM` on CPU.
   - **Full-model GGUF check on `nobara`:** Compare full 49-layer `Flint-Q4_K_M.gguf` (`23.39 GB`) against `llama.cpp` mainline on `nobara`.
2. **Option 2 (Tier T2 tiny-oracle from (a) `transformers` + full-model GGUF parity against (c) `llama.cpp` only):**
   - Skip the 3-layer real-BF16 slice and rely on the `transformers` tiny-oracle (`testdata/flint-tiny/` + window-boundary golden) for `1e-4` operator/math parity, and `Flint-Q4_K_M.gguf` vs `llama.cpp` mainline on `nobara` for full 49-layer real weights.
3. **Option 3 (Full 49-layer BF16 real-oracle on `nobara` via mmap/swap):**
   - Download `79.6 GB` `RecursiveSI/flint` (or `Flint-BF16.gguf`) to `/srv/models` on `nobara` and run 49-layer BF16 through `transformers` using `nobara`'s `62 GiB` RAM + `77 GiB` swap. *(Not recommended: every token touches ~5 GB of active + paged BF16 weights and will thrash swap).*

### 4.2 Evaluation: putting NVFP4 and MLX format in scope

Inspecting the raw bytes of `RecursiveSI/flint-nvfp4-gguf/flint-nvfp4.gguf`, `RecursiveSI/flint-int4/model-00000.safetensors`, and `RecursiveSI/flint-int4-gguf/flint-int4-q4_1.gguf` against `Flint-BF16.gguf` established three concrete facts:

1. **`RecursiveSI/flint-int4` (MLX) and `RecursiveSI/flint-int4-gguf` (`Q4_1` GGUF) hold the exact same quantized weights:**
   - In `RecursiveSI/flint-int4/model-00000.safetensors`, each quantized projection `p` is stored as three tensors: `p.weight` (`U8`, 2 nibbles/byte for group-64 affine INT4; 1 byte/element for group-64 affine INT8 on `model.embed_tokens.weight`), `p.scales` (`BF16`, group size 64), and `p.biases` (`BF16`, group size 64), reconstructed as `w = q * scale + bias`. Routed experts are stacked 3D as `model.layers.{L}.mlp.switch_mlp.{gate,up,down}_proj.{weight,scales,biases}` (`[256, out, in/2]` and `[256, out, in/64]`).
   - In `RecursiveSI/flint-int4-gguf/flint-int4-q4_1.gguf`, each 64-element MLX group was exported directly as two consecutive 32-element `GGML_TYPE_Q4_1` (`type 3`) blocks with identical `(d, m) = (scale, bias)` (e.g., on `blk.0.attn_k.weight`, both block 0 and block 1 have `d = 0.000171661, m = -0.00114441`, producing the exact same first 16 values `[-0.0008, -0.00029, 0.00057, -0.00063, ...]` as MLX `model.layers.0.self_attn.k_proj`).
2. **GGUF `NVFP4` (`RecursiveSI/flint-nvfp4-gguf`) answers LB0c of `docs/tasks/task-lowbit-formats-2026-11.md` and has a two-level scale:**
   - In `llama.cpp` (`ggml/src/ggml-common.h` and `ggml/src/ggml-quants.c`), `GGML_TYPE_NVFP4 = 40` has `QK_NVFP4 = 64` and `QK_NVFP4_SUB = 16`: each 36-byte `block_nvfp4` holds `uint8_t d[4]` (one `UE4M3` scale per 16-element sub-block, decoded by `ggml_ue4m3_to_fp32` with a `0.5` factor to pair with the doubled `kvalues_fp4` table) and `uint8_t qs[32]` (four 8-byte sub-blocks, where byte `j` of sub-block `s` packs element `16*s + j` in the low nibble and `16*s + j + 8` in the high nibble).
   - **Critical finding for LB1b/LB2b:** In `flint-nvfp4.gguf` (and `llama.cpp`'s `src/llama-model.cpp` generic `.scale` pass), every `GGML_TYPE_NVFP4` tensor `<name>.weight` has a companion `F32` tensor `<name>.scale` (`dims = [1]` for 2D projections; `dims = [256]` per-expert for 3D `ffn_{gate,up,down}_exps.weight`, e.g., `blk.0.attn_k.scale = 1.22615e-5`). The true weight is `kvalues_fp4[nibble] * ggml_ue4m3_to_fp32(d[s]) * scale2`. Verified against `Flint-BF16.gguf` on `blk.0.attn_k.weight[:16]`: BF16 `[-0.00072, -0.00022, 0.00049, -0.00061, ...]` vs NVFP4 `[-0.00066, -0.00022, 0.00044, -0.00066, ...]`.
3. **Recommendation on scoping NVFP4 and MLX format:**
   - **Put read-only loader support in scope as an optional track (`F1b`, coordinated with `docs/tasks/task-lowbit-formats-2026-11.md` LB0c/LB1b/LB2b/LB5c), decoupled from F1–F3:**
     - **Why read-only makes sense:** Adding `Q4_1` (`type 3`, LB5c) and `NVFP4` (`type 40` + companion `.scale`, LB1b/LB2b) in `aikit/embed` + `decoder/gguf.go`, and a streaming MLX safetensors reader (`decoder/flint_mlx_safetensors.go` + `fit.SafetensorsWeightBytes` auxiliary/pack-factor rules) lets `goinfer` load **all three official RecursiveSI repositories** (`RecursiveSI/flint-int4`, `RecursiveSI/flint-int4-gguf`, `RecursiveSI/flint-nvfp4-gguf`) without requiring users to hunt down third-party conversions.
     - **Why F3 benchmarks should still use `Flint-Q4_K_M.gguf` (`ggml-org/Flint-GGUF`):** As documented in `docs/tasks/task-lowbit-formats-2026-11.md` §0, read-only formats dequantize 4-bit weights to `f32` and re-quantize them into `goinfer`'s symmetric `int4`/`int8` (double quantization), whereas `Flint-Q4_K_M.gguf` (`23.39 GB`) loads today with zero format work and uses `goinfer`'s native `q4k` lane for its `Q4_K` projections. Native GPU kernels for NVFP4 or affine-INT4 (LB7) remain out of scope for Flint bring-up.
