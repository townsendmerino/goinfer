## 1. What is built, in order (each step is its own commit; a step merges only when its gates below read)

KV4a keeps the decoder seam as it is: the decoder still binds slots (`ResidentKVSlotter`), copies between them (`ResidentKVCopier`)
and asks what a slot holds (`ResidentReusableKV`, `ResidentReusableKVSlot`). Paging happens behind that seam, inside `cuda/`: a slot
becomes a sequence's block tables over shared pools, which is §5.13's "slot adapter" with paged storage under it. The `SeqView`
seam of §5.13 is not needed for any KV4 gate and is left to KV5/KV7, which need it.

- **KV4a-1, storage (bit-identical).**
  - Pools per group (§5.2, option A): the *full* group (every layer that keeps all positions, MLA latent layers included, a latent row
    being `kv_lora_rank + qk_rope_head_dim` wide), and the *window* group (the sliding-window layers windowed KV engages today).
    Storage per layer is `[numBlocks][64][kvDim]`, one allocation per layer and K or V; a block id names the same block in every layer
    of its group. **Block 0 is the zero-filled null block** of every pool.
  - Per slot and group, an int32 table of block ids, mirrored to the device (one buffer per slot and group, a stable pointer).
  - Every CUDA KV kernel reads and writes through the table: the 8 writers and the KV readers of `kv0-tile-census-2026-10-13.md` §4
    (the drafter's own cache and the vision towers' scratch excepted, §5.12, §5.17). Key `k` is at row
    `(int64)table[k >> 6] * 64 + (k & 63)`, computed **per key**, every tile, partition and thread-to-key map still defined in absolute
    key units (§5.3's bit-identity argument), the row offset in 64-bit arithmetic everywhere (the census's `attention` and `mla_attn`).
  - KV-shared layers (Gemma 4 E-models) read their source layer's pool with their source's group table.
  - The window group replaces `cuda/kvwindow.go`'s shifted view and compaction. Its retention keeps today's base arithmetic
    (`kvWindowNextBase`): a slot holds the blocks covering `[base rounded down to 64, end)`, so `ReusableKV` and `ReusableKVSlot`
    answer exactly as on `main` and the rollback budget (§5.12: 448 at the planned slack, up to 1,024 from free VRAM) is unchanged.
    Blocks behind the base return to the window pool, their entries to the null block.
  - **Capacity semantics unchanged at this step:** the full pool holds `slots × ceil(ctxCap/64)` blocks plus the null block, the
    window pool `slots × ceil((window + slack)/64 + 1)` plus the null block, and every slot keeps today's `ctxCap`. The VRAM a load
    takes is today's within the null blocks and the tables (priced, §4).
  - `CopyKV` copies rows between slots through both tables (device copies, as today). KV7's snapshots (`cuda/kvsnap.go`) and KV8a's
    checkpoints read and write rows through the table.
- **KV4a-2, sharing by reference.** `CopyKV` maps the source's full blocks `[start, end)` into the destination's full-group table and
  takes a reference on each, instead of copying them; the window group still copies (its blocks are recycled behind the window). A
  write into a block with more than one reference copies it first (copy on write: the rows below the write position, then the
  write), so a slot only ever writes blocks it owns (§5.4). A block returns to the free list when its last reference goes.
- **KV4a-3, capacity.** A slot's position cap becomes `min(model window, -ctx when given, the full pool's tokens)`; the pool stays the
  VRAM `main` gives KV at the same flags (decision D-KV4-1 below). Blocks are taken on demand. Each slot keeps a guaranteed share,
  `ceil(ctxCap_main / 64)` blocks of the full group, where `ctxCap_main` is the per-slot context `main` would plan at the same flags:
  a sequence within its share always gets its block, so every request that fits on `main` fits here. Beyond its share a sequence
  borrows free blocks. Under pressure, in D5's order: (1) blocks of idle slots (not bound, not running) are released, least recently
  used slot first, and that slot answers 0 to `ReusableKVSlot` from then on; (2) demotion is KV7's; (3) when a borrowing sequence still
  finds no block, it is the one stopped: its generation ends as at the context cap (`finish_reason: length`) and serve's log names the
  pool. Releasing another running sequence to keep a borrower going (D5's literal step 3) is not built in KV4a; see D-KV4-2.
- **KV4a-4, measured bonus, not a gate:** CUDA graphs for windowed models, which today decline when windowed KV engages. With no
  shifted view the only thing a captured segment would need is a stable table pointer. Built only if the decode-depth cells show it
  pays; recorded either way.
- **KV4b, f16 pools.** The pools take `KV_T` per layer as today's slots do. Precision phase 1's family groups, in its order: MoE and the
  paged-experts build; sliding-window layers (the window group); pairwise RoPE (Cohere); m-RoPE and the image prefill kernels; the
  hybrids' attention layers (Qwen3.5, Qwen3-Next, Gemma 4, Nemotron-H; LFM2 if CUDA runs it resident); MLA's latent pool last, after its
  range survey. Each group lifts its line in `decoder/kvresolve.go:CUDAKVF16Decline`, so `--kv f16` is delivered for it. **`auto` moves
  to f16 for a group only when that group's G4 reads PASS** (D7 decided the rule in advance; the precision doc's §1.2 rule is met by
  it), one commit per group.

## 2. Gates

### G1, storage identity (hard; KV4a-1, re-read after KV4a-2 and KV4a-3)

- **G1a, tier 0, scrambled tables.** A test seam hands the pool's free blocks out in a fixed scrambled order (reversed, then
  interleaved across slots), so logically consecutive blocks are physically far apart and out of order. On every CUDA tiny fixture
  that loads resident (dense llama and qwen2, phi3, the MoE fixtures, the sliding-window fixtures with windowed KV on, Cohere's
  pairwise RoPE, m-RoPE text and an image turn, the MLA fixture, a Gated-DeltaNet hybrid's attention layers, a Gemma 4 E-model's
  KV-shared layers): a prompt, then 64 decoded tokens, then a second turn that continues the first, then a 4-row verify, with 2 slots
  bound in turn; and an MC3 step of 3 sequences. **Pass: every logit of every step bit-identical between the scrambled pool and the
  in-order pool** (block `i` of slot `s` at physical block `1 + s·n + i`, which is today's slot layout plus the null block).
  - **Control (the gate can go red):** the same comparison with the table lookup planted wrong in one reader (row offset off by one
    block in `attention`, then in `fa_partial`) must fail. Both plants are run once and recorded; neither ships.
- **G1b, tier 1, across builds.** `go run ./cmd/gate identity -backend cuda <main> <this build>` on the tiny and real asset sets it
  defaults to (int4; f16 KV where the family takes it): **byte-identical full logits per family**, every cell IDENTICAL or NOT RUN for a
  reason that also holds on `main`. Wall time stated from the tool's own plan before the run.
- **G1c, flash-decode and split-KV through a windowed table** (the coverage the archived windowed-KV doc found missing: both lanes need
  at least 2,048 and 3,072 attended keys, which a 1,024-position window never reaches). A tiny windowed fixture copied with its window
  raised to 4,096 and `max_position_embeddings` to 16,384, windowed KV on with the slack at its planned 512, a prompt of 9,000 tokens
  and 64 decoded tokens, so the window group has dropped blocks behind the base and both lanes engage (asserted by their launch
  counters, which must be non-zero, or the case is VOID): **pass, every decoded logit bit-identical to the same build with windowed KV
  off** (every position kept, the full table). A sliding-window layer reads `[p − W + 1, p]` either way, so any difference is a table
  defect. Run on f32 KV and, after KV4b's sliding-window group, on f16.
- **G1d, the existing suites.** `TestWindowedKV_*` stay as oracles: a test that asserts on the shifted view's internals (a base, a
  compaction count) is rewritten to the same statement about the window group's tables, each rewrite listed in §3 with what it asserted
  before and after. The tagged CUDA suite (`cuda goinfer_testhooks`) passes with `GOINFER_HEAVY_TESTS=1`, in the two partitions KV3
  used (`^Test[A-L]`, `^Test[M-Z]`, each about 85 minutes, so **the night queue**, case (b)); a failure that also fails on `main` at the
  merge base is recorded and does not block, and every other failure blocks.

### G2, speed (KV4a; decided on the KV4a-3 build, read once on KV4a-1 to apply the kill rule early)

Two arms, `goinfer_old` = a `serve-cuda` built from the merge base, `goinfer` = this branch, interleaved A B B A in one session on
nobara under the timing lock, with the void rule of `CLAUDE.md` ("Run budget"): a cell started with load1 above 8.0 or free memory
below the fit need plus 2 GB is void and re-run in place. Both arms at serve's defaults (`-kv-sessions 4`, f16 KV where the family
takes it, windowed KV on), models from `~/models`.
- **Decode at depth:** `scripts/bench_peer.py`, `BENCH_ENGINES=goinfer,goinfer_old BENCH_BACKENDS=cuda BENCH_DEPTHS=128,2048,3900,8000`,
  `BENCH_MODELS=1.5B,7B`, plus `gemma3-1b` at 128, 2,048 and 3,900 (a sliding-window family on the window group; it has no 8,000
  prompt). Per cell the ratio new/old of decode tok/s, the median of the paired blocks. **Pass: at least 0.98 at every depth on every
  model. Ambiguous (parked, not shipped on this evidence): 0.97 to 0.98. Fail: under 0.97.** Cost basis: 3 models × up to 4 depths × 2
  arms × 2 passes = 44 cells at about 45 s each (load, prefill, 3 timed runs), about 35 minutes plus idle-gate waits.
- **Prefill time to first token at K = 512 and K = 3,900:** KV3's `ttft_ab.py` (`scripts/bench_peer_prefill.py`'s `ttft()`), the 1.5B
  and the 7B, three alternating pairs. **Pass: old/new at least 0.97 at both depths on both models**; 0.96 to 0.97 ambiguous; under 0.96
  fail. About 6 minutes (KV3's 1.5B job took 2).
- **MC3 aggregate at 4 clients:** `scripts/bench_w7_plain.py --engines goinfer --backend cuda --fixed-nonce --server-log` as MC3's
  record ran it (6 turns × 128 greedy tokens per client), the 1.5B, cells old new new old old new. **Pass: new/old aggregate at least
  0.98, median of 3 pairs, and every turn's `content_sha` equal between arms.** About 6 minutes.
- **Kill (§6):** if decode at depth 2,048 or more reads under 0.98 on the KV4a-1 build, the tuning budget is **two rounds**, each one
  kernel-side change and a re-run of only the failing cells, within one working day. Still under 0.98 after the second: KV4 parks with
  its measurement, the branch is not merged, and KV2's copies stay.
- Never-swap (G4 below) is read from the same runs.

### G3, capacity (KV4a; decides KV4 by Q3)

- **G3a, one sequence uses the pool, tier 0.** On a tiny fixture with 4 slots and a pool of P full blocks, one conversation prefills and
  decodes until it stops: **pass, it reaches at least 90% of the pool's tokens** (`0.9 × 64 × P` positions) with the other three slots
  idle and empty, and it stops with `finish_reason: length`, not an error.
- **G3b, a shared preamble is stored once, tier 0 then tier 1.** Four conversations whose prompts share a 16,384-token preamble (tier 0:
  the tiny fixture with `max_position_embeddings` raised; tier 1: the 1.5B at serve's defaults, by day, about 2 minutes): **pass, the full
  pool's blocks in use after all four have prefilled are at most `256 + 4 × (ceil(tail/64) + 1)`** (the preamble's 256 blocks once, each
  conversation's own tail and its headroom), read from the pool's own counter; on `main` the same reading is `4 × 256` or more. The four
  replies are each byte-identical to that conversation run alone on the same build (KV2's G3, schedule independence).
  **Amended 2026-10-22, before any graded tier-1 reading:** the first tier-1 run (four conversations sent one after another) logged no
  copy on this build or on `main`: serve copies only from a busy holder and reuses an idle one in place, so that design never shares. It
  also found that on `main` a conversation reusing the 16,000-token preamble in place replies differently from the same conversation on a
  fresh server (reported in §3, not KV4's). Tier 1 now sends each conversation once the one before it is streaming (128 generated tokens),
  so 1 to 3 each copy; the block bound adds each conversation's generated tokens to its tail; and each reply's reference is, on a fresh
  server of the same build, conversation 0 and then that conversation (in-place reuse, solo decode; MC3's batched step is per-row
  identical to decode). Copies are counted from serve's `kv share: copied` line, the block count from KV4's own copy line. The same cell
  on `main` is the control: it must log three copies and pass the reply check (`main` logs no block count).
- **G3c, the 8 GB card's single-conversation context at least doubles at the default slot count.** Qwen2.5-7B-Instruct Q4_K_M at serve's
  defaults (`-kv-sessions 4`, unpinned context): `main` plans 4 slots of about 11,784 positions (KV0). **Pass: this build's banner names a
  per-conversation cap of at least twice `main`'s planned per-slot context at the same flags, read from both banners in the same session,
  and a single request of that length (prompt plus 64 generated tokens) completes on the GPU path** with no CPU fallback and no 413.
  Repeated on the 1.5B (`main`: 4 × 16,384) for the record; its cap is the model's 32,768, so its ratio is 2.0 by the window, not the pool.
- **G3d, pressure follows D5, tier 0.** Four slots; three idle slots hold conversations; the fourth borrows past its share until the pool
  is full: **pass, the idle slots are released least recently used first, each then scores 0 for its old prompt (`ReusableKVSlot`) and a
  re-sent prompt prefills cold with the reply it had alone; a request within its share never fails while others borrow; and a borrower
  that finds no block stops with `finish_reason: length`.** A planted defect (release the bound slot's blocks instead of an idle one's)
  must fail it.

### G4, never-swap (every timed run above)

The serve process's own `VmHWM` and peak `VmSwap` (`/proc/<pid>/status`, sampled until it exits) on every speed cell, both arms. **Pass:
this build's peak `VmSwap` is no more than `main`'s plus 0, and its `VmHWM` within 64 MB of `main`'s**, cell by cell, median over the
cell's runs. System-wide swap is recorded as context only. The pool takes `main`'s VRAM, so host memory is expected flat.

### G5, KV4b: f16 pools, per family group (the precision doc's §4, as registered there)

For each family group of §1, in that order, its own commit:
- **G1 exact-input identity (CI):** on K/V values exactly representable in f16, the group's f16 kernels equal its f32 kernels bit for bit,
  as the f16 build's `_kv16` identity tests do; plus G1a above on f16 pools.
- **G3 delivered bytes:** the bytes a load allocates per position for the group equal the arithmetic (f16: 2 B per element), read from the
  pool's allocation, for every fixture of the group.
- **G5 range survey, before G4 is read:** max|K| and max|V| on the gate prompts at every layer under 65504/2. A group that fails still gets
  f16 on request, stored with a per-(position, head) scale (the precision doc's §4, G5).
- **G4 quality against f32 (published; decides `auto` for the group by D7):** `docs/tasks/task-cuda-f16-kv-2026-10.md`'s instrument and its
  three criteria per cell (hard flips; paired agreement at least f32's less 1.0 point and f16 at or above f32 on half the prompts; mean KL at
  most 1.10 × f32's), with that doc's ambiguous band, on one real checkpoint per group at K = 3,900 and one long cell at K = 8,000 where the
  model's window allows: MoE, Qwen3.6-35B-A3B or gpt-oss-20b (whichever loads resident at the cell's context); sliding window, Gemma-3-4B;
  pairwise RoPE, Command-R7B; m-RoPE, Qwen2.5-VL-3B (text cells, and one image turn reported); hybrids, Qwen3.5-9B; MLA,
  DeepSeek-V2-Lite. A group whose checkpoint does not fit the card is reported NOT RUN and keeps `auto` at f32. **Pass on both cells:
  `auto` moves to f16 for that group. Ambiguous or fail: `--kv f16` is delivered on request, `auto` stays f32, and the reading is
  published in the precision matrix's reason.** Cost per group from the f16 doc's previous run: about 25 to 40 minutes, so each group's
  G4 is a day run; the whole series is over two hours and is not run as one job.
- **Speed:** G2's decode cells on one f16 model per group against the same build at `--kv f32`; the bar only forbids a regression at short
  context (128 and 2,048: at least 0.98).

## 4. Pricing (one function, §5.10)

The pools and tables are priced by `decoder/residentneed.go:Model.ResidentKVBytes`'s CUDA branch, which the planner, the fit guard and the
build already share: the null block and the tables (4 bytes per 64 positions per slot and group) are added there and to `kvBytesForCap`
in the same commit as the allocation, and `TestResidentKVBytes_matches*Allocation` holds the two together.

## 5. Decisions for the owner

**D-KV4-3 (open, 2026-10-22): G2 reads MC3 under its bar and Gemma-3-1B's decode in the ambiguous band.** MC3 (four clients on the 1.5B)
reads 0.973 to 0.983 across five measurements since KV4a-3, about 2% under `main`, every reply identical; the registered bar is 0.98 with
no ambiguous band. Gemma-3-1B reads 0.977 at depth 2,048 and 0.979 at 128, with blocks spreading 3 to 4% inside one cell, so two
blocks per cell (BENCH_ABBA=1, the N this registration used) cannot resolve a 2% question on that model. The kill rule (decode at
depth 2,048 or more under 0.98 after the tuning budget) reads on that cell, and the tuning has gone past the two registered rounds.
Every other G2 cell passes, and the capacity arm that decides KV4 (Q3) passes: 2.71× the single-conversation context on the 8 GB card.
Options: (a) re-measure the Gemma and MC3 cells with a registered larger N (BENCH_ABBA=4: eight blocks a cell, about 25 minutes) and
grade on that, keeping the bars; (b) amend MC3's bar to decode's bands (PASS 0.98, AMBIGUOUS 0.97 to 0.98) and ship on the capacity
arm, the ~2% cost at four concurrent clients recorded; (c) apply the kill rule: KV4 parks, KV2's copies stay; (d) more tuning, past the
budget. **Recommended: (a), then (b) if MC3 stays between 0.97 and 0.98**: the Gemma cell is noise-limited at this N, and a 2% aggregate
cost at four clients buys 2.7× one conversation's context.

**Both answered by the owner on 2026-10-21 (about 19:30 PDT, relayed by the coordinator session): D-KV4-1 (a), the pool is the VRAM `main`
gives KV at the same flags (`slots × ctxCap`), and growing it stays with KV5's I7; D-KV4-2 deferred, KV4 stops only the borrower past its
guaranteed share (ending as at the context cap), and release-and-re-admit is built with KV7 (its ledger row KV7-rest).** Both are the
recommendations below, so KV4a-3 proceeds as registered.

- **D-KV4-1, the pool's size.** (a) The VRAM `main` gives KV at the same flags (`slots × ctxCap`), so one conversation can use all of it and
  the fit, the never-swap figures and the other processes on the card see no change; (b) everything left after weights, scratch and the
  margin, which grows KV on cards where the 16,384-position default leaves VRAM unused. **Recommended: (a) for KV4**, and (b) as part of
  KV5's I7 (the default context toward 32,768), which the owner already placed there. KV4a-3 is built on (a).
- **D-KV4-2, D5's step 3 inside KV4.** As registered (§1, KV4a-3), every slot keeps a guaranteed share, so nothing that runs on `main` can be
  stopped, and only a sequence borrowing past its share is ever stopped (as at a context cap). D5 decided "preempt the newest by release":
  releasing another running conversation's blocks so it re-admits through the index and continues. That needs the decoder's MC3 batcher to
