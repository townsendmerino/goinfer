How each side reads a cell:

- **CPU.** A cache holds only elements of the delivered precision: f32 cells hold no f16 or int8, f16 cells no f32 or int8, i8
  cells no f32 or f16 and exactly one f32 scale per `head_dim` int8s (8 B per position, head and layer for K and V). An MLA
  family's latent counts as f32.
- **Metal, resident.** Per non-shared layer, K plus V buffers are `2 × padded positions × kv_dim × width` bytes (f16 2, f32 4,
  i8 1), and the scale buffers are `2 × padded positions × kv_heads` floats at i8 and absent otherwise. An MLA layer holds one
  latent buffer (V aliases it) of `padded positions × latent_dim × 4` bytes.
- **Metal, resident declined.** The model's CPU cache is decoded 12 positions and read back as the CPU half does, against
  `Model.KVDelivered` (what the request log reports).

Plants, each red, then reverted (the tests were committed first):

- CPU: `NewCache`'s int8 branch disabled (`if false && m.kvI8 …`), so an i8 request builds f32: 5 CPU cells red, and on Metal
  `phi3-tiny/i8: no resident; the CPU cache reports i8 and holds f32 2304, f16 0, i8 0, scales 0`.
- Metal: `r.kvI8 = false` in the resident build, so an i8 request builds f16 without scales: every resident i8 cell red
  (`llama-tiny/i8: layer 3 holds 0 scales, want 416`).

## What it found

- **`deepseek-tiny` auto and f16 on Metal hold an f32 latent; the matrix and the request log say f16.** MLA's resident latent is
  f32 whatever is asked (`metal/mla.go`), and `ResolveKV` answers for the family's attention, not MLA's. The same question P3a
  raises as D5 (draft PR #148). The test lists the two cells as `g3MetalPendingD5` and requires them to still differ, so the
  change that settles D5 turns the test red until the list is cut. No other resident cell holds anything but its delivered
  precision.
- **Eight cells build no Metal resident and run on the CPU cache, which holds what the request log says.** `phi3-tiny` at every
  value, and `lfm2-tiny` and `gemma4-moe-kv-tiny` at auto and f32 (declines outside KV); their f16 and i8 cells, and
  `deepseek-tiny/i8`, are refused at load, because the CPU path refuses those values for those families. Six of the eight
  (`phi3`, `lfm2` and `gemma4-moe-kv` at auto and f32) hold f32 where `docs/kv-precision-matrix.md`'s Metal row says f16: the
  matrix describes the family's Metal answer, and the load runs the CPU's. The request log is right and nothing is silently
  lowered. Whether the matrix should mark a family Metal never builds as running on the CPU is a matrix-shape question for
  whoever next regenerates it; no gate depends on it. The test pins both lists.
- f32 on Metal is refused on this main (until P3a merges), so no resident f32 cell is read here. When P3a lands, the f32 cells
  of the resident families are read back by this test, and the three `/f32` entries in `g3MetalMatrixDiffers` drop out (the
  matrix's Metal answer becomes f32), so P3a's merge edits the list.

Experiment-design note: a first version loaded the Metal cells with `KVPrecision` alone, as `kvMatrixOpts` does for a GPU path.
That drops the CPU request serve sets beside it, and every declined cell then read f32 on the CPU cache: a test artifact, not a
fallback, since serve and goinfer-chat set `KVQuant` from `--kv` too.

The CUDA cells (`cuda`, every family) are not run on the Mac: G3's row stays open for nobara.

**Resolved by D5 (owner, 2026-10-22; `docs/measurements/kv-precision-2026-10/d5.md`):** the resolver now reports f32 for MLA on Metal,
so `deepseek-tiny`'s auto cell reads f32 = f32 and its f16 cell is refused; the test's pending-D5 list is gone, and any resident
cell that holds other than its delivered precision is red.
