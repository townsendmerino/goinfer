# P3b-1: int8 and f32 on Metal's batched step, 2026-10-22

Gates: `docs/tasks/task-kv-precision-everywhere-2026-10.md`, "P3b-1 gates" (P3B-G), registered before the code (939f5786).
Machine: MacBook Pro, M1 Pro, 16 GB, macOS 26.6.2, Go 1.27.2. Built on D5 and P3a. Tier 0: the MC3 fixture and the tiny
fixtures, seconds.

**The build.** An int8 cache's slots are one allocation per layer, codes and scales each (`kvContig`, as f16 and f32 were), slot
s's scales at its code offset over head_dim (`kvScaleOff`). The step gains `mc3_kv_store_i8_rows` and `mc3_attention_i8_rows`,
derived from `kv_store_i8` and `attention_i8` with the same prologue the f16 rows kernels take (no attention sink: a sink family
stays off the step). It also gains `mc3_kv_store_f32_rows` and `mc3_attention_f32_rows`, the f16 rows kernels under the type
substitution `attention_f32` is made by (`metal/kv_rows.go`). `batchIneligible` no longer names int8 or f32. The step prefill
(`promptStepOK`) takes every prompt at int8 and f32, since the MMA pass declines them. `PrefillPath` reports the step.

Planted defects, each red, then reverted (the build was committed first):

- The int8 rows attention reading slot 0's scales for every row: 20,480 of 20,480 logits differ at depths 23 and 40.
- The f32 rows store rounding through half: 20,479 of 20,480 logits differ at depth 5.

P3a's `TestP3_metalF32BytesAndPaths` asserted that batched decode is ineligible under f32. P3b-1 opens that path on purpose, so the
assertion now requires the MMA pass to decline f32 and `PrefillPath` to name the step if it reports a batched path.

No timed run: every path this opens is bit-identical to the sequential one it replaces, and the step is what f16 already takes
for the same work. Left for P3b-2: the MMA prefill at int8 and f32, and the layer-major paths (Gemma 4, paged MoE, the E-model).
