# SB12-I1: the CUDA suite's I1 ledger breaks — 2026-10-29

The CUDA test suite's release check fails on main. It holds two invariants for every device a test releases:
- **I1:** nothing was ever allocated on no plan line;
- **I2:** no lease is still open after release.

The 2026-10-27 night `gate gpu` run on nobara at `655f25dd3` reported breaks in four cells. Its `cuda-parity` cell timed out
before its report; the parity figure is from this branch's L3 runs on 2026-10-28/29 (`sb12-memtests-2026-10-28.md` §5):

| cell | devices with a break |
|---|---|
| `cuda-heavy-small` | 13 |
| `cuda-parity` | 1–2 |
| `qwen25vl-3b` | 2 |
| `7b-8b` | 5 |
| `qwen3-4b` | 4 |

The report gave only "unplanned peak N bytes", with no lease ever open after release. The coordinator assigned the fix at
11:05. The work is by nobara-ci01 on nobara (RTX 2070 SUPER, driver 595.91.07, Go 1.27.3). It landed as #439, and the gate is
SB12-I1 in `docs/tasks/task-subsystems-2026-10.md`. Logs are in [`sb12-i1i2-2026-10-29/`](sb12-i1i2-2026-10-29/).

## 1. What breaks I1, and why

**Every break is I1; none is I2.** No device had a lease open after release, so nothing leaked. Some allocations were leased
on no plan line.

**The diagnostic.** `deviceLedger.Lease` now calls a test seam, `unplannedForTest`, which is nil in production, for each lease
on no line. The `cuda` test package adds each such lease to its ledger's account by call site. A breaking release prints
`LEDGER BREAK` with the test that created the device, the tests in flight, and the sites, largest first.

**The cause is the same in every break the site report named** (13: cuda-parity's 1 and cuda-heavy-small's 12). A test allocated its own inputs and outputs through `cudaResident`'s allocation
helpers (`af`, `ai`, `upu32`, `upu16`, `up32`, and the test helper `kvIdentityTab`) inside a plain `r.do` job. Those helpers
lease on the resident's current line, which only `onLine` or `doOn` sets, and inside a plain job it is empty. The site
report found no production frame in any of them; every unplanned site sat directly under a test closure or a test helper.
No product path, bound or price is involved in those 13.

**For the other three heavy groups the cause is inferred, not observed.** The 11 breaks the night printed in `qwen25vl-3b`,
`7b-8b` and `qwen3-4b` have no site report: those groups were not re-run with the diagnostic. A source sweep found the same
shape in their tests (§2), and their green runs (§3) are what will show whether the sweep found all of it. Until then, a
break there with a production frame is still possible.

**The site run is the red** (`run-sites.sh` on the tree committed as `bac9dc6d7`; its driver line prints the parent,
`e4dd3ed5a`, because the diagnostic was committed a minute after the run started):
- **cuda-parity:** 1 break, `TestRopeKVMRoPEBatched_interleavedModeMatchesCPUReference` (7,848 B).
- **cuda-heavy-small:** 12 breaks: `TestAttnFused_vsExact`, `TestAttnFused_attendsKeysBeforeStartPos`,
  `TestAttnFused_vsF16Reference`, `TestAttnFusedTile_smallMSweep`, two devices of `TestAttnFusedTile_32x64BitIdentical`
  (`tileBitIdentical`), three subtests of `TestFlashDecodeVsF64` (`runFlash`), `TestFusedQKVRowsBitIdentical`,
  `TestGluQuantBlockSizeInvariant`, and the rope test above.
- **The three other heavy groups** were not re-run red. Their breaks are the night's.

## 2. The fix (#439)

**Test-line helpers.** A test's own buffers now go through helpers in `cuda/kvpool_helpers_test.go` (`tf`, `ti`, `tup32`,
`tupu32`, `tupu16`), each of which sets the test line for its one allocation only. `kvIdentityTab` leases on the test line
itself. The jobs stay plain `r.do`, so whatever the code under test allocates in the same job keeps the job's line, and I1
still reports it when that line is none.

**Eighteen jobs changed.** Nine are the ones the site report named. Nine more were found by sweeping every `r.do` / `rf.do`
job in the package's tests that calls a resident allocation helper; they are tests of the three heavy groups, and the sweep
now finds none left. A sweep finds only jobs that call a helper directly; one that allocates through a function it calls
would be seen only on the card. `towerOps`' helpers lease on the companion line and are planned.

**Two choices from Gemini's review of #439.**
- **The first version was replaced.** It ran each whole job under `doOn(mem.LineTest, …)`, which would also have put the code
  under test on the test line.
- **One suggestion was declined:** defaulting the helpers to the test line whenever the line is empty. That would hide
  exactly the unlined production allocation I1 exists to catch.

**A file count ratchet.** The helpers went first into a new test file. That took
`TestBackendTests_decoderImportsOnlyFall`'s count of `cuda` test files that reach `decoder` to 311, against its ratchet of
310, so they moved into the existing helper file.
