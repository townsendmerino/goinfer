# Two CI flakes of 2026-10-25: causes and fixes

Francis's order of 12:30, item 1: find the cause of each, not just a retry.

## (a) root-darwin `TestHardwareCensus` (run 40211104196, on #236; green on re-run)

- **What failed:** `internal/hwcensus/census_test.go:moduleDir` runs `go mod download -json github.com/townsendmerino/aikit/gpu@v0.34.0`
  at test time, to scan the pinned aikit source. root-darwin's root module does not need `aikit/gpu`, so its module cache can lack
  it and the test fetches it from the proxy. The fetch failed with "exit status 1" and an empty message.
- **Why the message was empty:** `go mod download -json` reports its error in the JSON on stdout, and the test printed only stderr.
  The proxy's answer is therefore lost. The failure is a network fetch at test time, not a defect in what the census checks.
- **Fix:** the fetch is tried three times (0, 2 and 8 seconds apart). Each failed attempt's stdout and stderr are logged, and a
  failure that persists still fails, naming both. The census still never skips. Network flakes stop failing the job, and a real
  failure now says why.

## (b) gpu-darwin "fatal error: invalid pointer found on stack" (run 40222211743, attempt 1, on #239; green on re-run)

- **Cause, a memory-safety bug in the WebGPU binding.** `oliverbestmann/webgpu` v1.36.0 `wgpu.(*Adapter).GetInfo` declared its
  `C.WGPUAdapterInfo` on the Go stack and passed its address to `wgpuAdapterGetInfo`.
  - wgpu-native returns an empty string as a dangling pointer, 0x1 (Rust's non-null pointer for an empty slice), in the struct's
    `*C.char` fields.
  - When the GC shrinks the goroutine's stack while that frame is live, `runtime.adjustpointers` finds 0x1 in a pointer slot and
    aborts. The trace: `morestack` → `newstack` → `shrinkstack` → `copystack` → "bad pointer in frame …GetInfo … 0x1".
  - It depends on when a shrink lands, so it is intermittent.
  - It is not test-only: `gpu.New` calls `GetInfo` for every Context, in production too.
- **Reproduced on the Mac (M1 Pro, Metal).** The adapter reports vendor, architecture and description as empty strings, so the 0x1
  pointers are there. A stress of `GetInfo` from 8 goroutines with grown stacks, under continuous GC:
  - **v1.36.0:** aborted in **0.67 s** with the same error as CI.
  - **v1.37.1:** **62.9 million calls in 20 s, no abort.**
- **Fix:** bump the binding to v1.37.1 in `gpu/go.mod` and `demo/agent/go.mod`. Its `GetInfo` holds the struct in C memory, with
  upstream's comment naming this crash, and frees its members, which v1.36.0 leaked. It pins the same native-library versions as
  v1.36.0, so only the Go wrapper changes.
- **Regression test:** `gpu/internal/kernels/adapter_info_test.go:TestAdapterGetInfo_survivesStackShrink`, the same stress for 3 seconds: 10.2 million
  calls pass on v1.37.1.
- **Open risk, not fixed here.** v1.37.1 still receives `C.WGPUStringView` *by value* in five exported Go callbacks: request-adapter,
  request-device, device-lost, the error callback and queue-work-done. An empty message there would put the same 0x1 in a Go frame.
  None has been seen to crash.
- **Raised upstream on Francis's (a), 2026-10-25 (13:49, relayed):** https://github.com/oliverbestmann/webgpu/issues/18. It reports the
  `GetInfo` crash and v1.37.1's fix, with a standalone repro: v1.36.0 aborts within a second, v1.37.1 completed 46.6 million calls
  with no abort. It asks whether the five callbacks have the same hazard, saying plainly that it has not been seen and that whether
  wgpu-native passes 0x1 there is unchecked. No code or PR.
