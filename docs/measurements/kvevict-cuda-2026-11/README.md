# kvEvictIdle shielded the bound slot, which a batched step leaves stale (nobara-sb01, 2026-11-06)

`kvEvictIdle(s)` (`backend/cuda/kvpool.go`) skipped `t == s` (the slot being written) and also `t == r.kvSlot` (the bound slot). A batched decode step writes through each row's slot and restores the binding afterwards (`StepBatch`: "the bound slot's binding is restored before it returns"), so the bound slot during a step is whatever was bound before it: a stale, idle slot, shielded from eviction. That breaks D5's step 1 (idle slots released least recently written first). Found on Metal by sb11m (#711).

- **Red first** (`red.log`): `TestKV4_batchedStepEvictsTheLeastRecentlyWrittenIdleSlot` (`kv4_capacity_test.go`; the long-window llama fixture, four slots): slot 0 written first, then slot 3, then slots 1 and 2 grown so the pool is exactly full (0 free blocks, asserted); slots 1 and 2 marked running; slot 0 bound without a write; one `StepBatch` over rows on slots 1 and 2 needs a block each. Before: slot 3 (written later) was released and slot 0 (the least recently written) kept, 240 blocks held.
- **Change:** `kvEvictIdle` no longer skips the bound slot. A running generation is protected by `kvSlotBusy`, as it was; the writing slot by `t == s`.
- **Green** (`green.log`): the new test, and 149 tests in all across the KV, batch-step, windowed, MC3 and recurrent-slot families under `-tags 'cuda goinfer_testhooks'`, with `TestKV*` and `TestPlanMemory_*` under `-tags cuda`. `touched.py` and `cmd/lint` per `touched.log`, `lint.log`.
- **Left alone:** `kvCopyDroppable` (`kvdemote.go`) also skips `r.kvSlot`; its stated reason is a different one (a slot "a request is about to use" has a demoted copy it will restore), and it picks which demoted copy to drop, not which slot to evict.
