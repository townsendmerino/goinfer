# S6 — Metal aliases the .giw mapping (opt-in `GOINFER_METAL_ALIAS=1`), first measurements, 2026-09-24

Status: **built opt-in, off by default; the M26 alias arm collapsed the machine's memory 3 of 3 times — ROOT-CAUSED
2026-09-24, see [`m26-alias-fork-collapse-2026-09-24.md`](m26-alias-fork-collapse-2026-09-24.md): a `fork()` made while
Metal has any no-copy page wired copies the WHOLE mapping eagerly (XNU copy-on-wire + `vm_map_fork`), and the serving
swap guard forks every 2 s; reproduced without a model, fix (`VM_INHERIT_NONE` on the mapping + a fork-free swap guard) APPLIED and
confirmed on M26 the same day — 2 of 2 alias arms clean, swap flat.** Several numbers below are corrected there; the corrections are flagged in place. Nothing
here is a ship decision.

What was built (`metal/alias.go`, `decoder/serialize.go` v13, `decoder/model.go` `MmapAliasWindow`):
a dense int4 tensor whose nibbles live in the `.giw` mapping is bound into Metal through a no-copy
MTLBuffer over its page-aligned window instead of being copied into a second MTLBuffer. Fused
q‖k‖v and gate‖up buffers need their rows adjacent in the file, so a `-target metal` v13 file writes
each fused tuple as a **group** (kind 6, `docs/giw-bundles.md`, "fused groups for Metal"); the Metal build
detects adjacency at runtime and falls back to the copy path when it is absent. Scales are still converted
f32→f16 into a small buffer.

Provenance: MacBook (darwin/arm64, 16 GB), goinfer `27780cdc` + uncommitted S6 increment 2 · aikit gpu
v0.33.1 · `metal/cmd/serve -backend metal -ctx 512` (M26 adds `-moe-cache-experts -moe-cache-slots 8`) ·
greedy 32 tokens · harness `scripts/moe_pager_ab.py`, `footprint <pid>` after load and at token 32 · local `~/models`.
Raw data: `s6-alias-2026-09-24/`.

## Gate 3 — logits byte-identical, aliased vs copied: PASSED on the 1.5B

`metal/alias_test.go` (`TestWeightAlias_logitsByteIdentical`): the same `.giw` built into a resident twice
(aliasing off, then on), 24-token prefill + 6 decode steps, every logit's bits compared. It also asserts the
alias arm really aliased (else it would compare copy to copy). Both layouts pass, and it goes red when the
view offset is dropped (151,936 of 151,936 logits differ):

| file | aliased | copied as before | logits |
|---|---|---|---|
| 1.5B, v13 (fused groups) | 56 single tensors + 56 fused groups = 625 MB | none | **byte-identical** |
| 1.5B, v12 layout (no adjacency) | 56 single tensors = 215 MB | 56 fused groups "not adjacent" | **byte-identical** |

Not run: the same gate on the 7B, on M26, or on `TestMetalSnapshotGolden`/the resident-parity fixtures the brief
lists (the Metal package suite, with heavy tests off, passes: 134 s).

## Gate 1 — anonymous footprint: large win on the 1.5B, small on M26 (the dense term is small there)

> **CORRECTION 2026-09-24:** the 1.5B "1,005 → 354 MB" below is an accounting artefact. The 625 MB the GPU reads through
> no-copy buffers appears in NO per-process ledger (`footprint` categories, RSS, "mapped file" all flat across the
> request), because IOKit wires them as copy-on-write pages in a kernel shadow object outside the process's pmap — they
> are anonymous, wired, and invisible, not file-backed. A RAM comparison needs system-wide `vm_stat` counters, which no
> S6 run sampled. Also: the copy column's after-load figures were 1,005 / 1,011 MB (not 1,003 / 990) and 1,029 / 1,033 at
> token 32 in the v13 JSONs.

**1.5B**, interleaved copy / alias / copy / alias (`GOINFER_METAL_ALIAS` 0/1/0/1), all four `metal-resident`:

| | copy (runs 1, 3) | alias, v12 layout (singles only) | alias, **v13** (fused groups) |
|---|---|---|---|
| phys footprint after load | 1,003 / 990 MB | 788 / 790 MB | **354 / 354 MB** |
| IOAccelerator (dirty) after load | 927 MB | 712 MB | **302 MB** |
| phys footprint at token 32 | 1,026 / 1,012 MB | 812 / 815 MB | **380 / 381 MB** |

**M26 (N=8)**: the alias arm aliased **723 MB** of nibbles (60 single tensors + 55 fused groups) out of a
15 GB file — M26's dense weights are small (its bulk is paged experts, which stay in slots), so the expected
IOAccelerator drop is ~0.7 GB of the 2.4 GB, **not** 2.4 GB. The copy arm on the v13 file: 3,975 MB after load
(IOAccelerator 2,407, untagged 1,550), 4,486 MB at token 32, 7.81 tok/s, peak RSS 6.34 GB, swap flat. The
alias arm has no footprint (below).

## The M26 alias arm collapses memory at its first request — reproduced 3/3, ROOT-CAUSED

**Superseded by [`m26-alias-fork-collapse-2026-09-24.md`](m26-alias-fork-collapse-2026-09-24.md).** Kept here in
summary: three alias attempts (one on a freshly rebooted, idle machine) loaded normally, reached the forward pass, and
then were paged out wholesale within ~2 s of the first request — 2.9–3.2 GiB of task page-ins with the fault counter
flat, RSS 4.4 GB → ~15 MB, swap climbing until the external watcher's SIGKILL (exit −9). The copy arm on the same file
ran clean. What the earlier draft of this section got wrong: the after-load footprints DO exist (3,255 / 3,251 / 3,255 MB,
exactly 723 MB below the copy arm's 3,975); the copy arm's 58 s load was the one-time CRC pass, not a cold cache; the S3
tripwire did not "fire late" — its first `sysctl` fork never returned in any alias run (no `swap guard: baseline` line),
which is the mechanism showing itself; the 1.5B was not "ruled out" — its first alias run read 97% of the file's
never-touched remainder; and the wired.sh probe discriminated nothing. Mechanism, experiment and fix: the companion doc.

## MAP_SHARED — the fix for S6's premise, adopted on darwin (2026-09-24)

The root cause above showed the old mapping defeated S6 twice: under `MAP_PRIVATE`, IOKit's write-intent wire turns
every GPU-read page into a wired anonymous COW copy (so aliasing saved nothing), and marks the object so fork() copies
the whole mapping. `metal/alias_sharedprobe_test.go` (`GOINFER_ALIAS_SHARED_PROBE=1`, no model: 2 GiB uncached file,
one no-copy buffer over a 256 MiB window) compared the two modes, counting the TEST PROCESS's own COW faults from a
separate sampler (system-wide counters are swamped by the desktop's ~25k COW faults/s):

| | `MAP_PRIVATE` | `MAP_SHARED` |
|---|---|---|
| GPU reads correct values through a read-only no-copy buffer | yes (0/16,384 wrong) | yes (0/16,384 wrong) |
| COW faults from one touch of the 16,384-page window | **+15,131** | **0** |
| COW faults from 12k further dispatches | +13 (the copies persist) | +58 (noise) |
| fork+exec during continuous dispatch | 1,092–2,487 ms (earlier probes) | **4.0–5.2 ms** |

`decoder.Load` now maps a `.giw` `MAP_SHARED`, read-only, on darwin (`decoder/giwmap_darwin.go`; other platforms keep
aikit's `MAP_PRIVATE`). Verified through `Load` by the kernel's own account (`vmmap` reports the region `SM=ALI`, where
the private mapping is `SM=COW`; `TestLoad_mapsGIWSharedOnDarwin`, mutation-checked), and on the real serving path with
aliasing on — the 1.5B, one request, same reply from both builds: server COW faults **+40,430 private** (625 MB ÷ 16 KiB
= 40,000: a copy of every aliased page) vs **+132 shared**. Logits stay byte-identical aliased vs copied
(`TestWeightAlias_logitsByteIdentical`), and the decoder and Metal suites pass. `VM_INHERIT_NONE` stays on the mapping
as defence in depth. What this does NOT show: that the aliased pages are reclaimed under memory pressure while a model is
idle (they are clean file pages once unwired, so they should be, but no pressure run was made), the M26/7B footprint
with the shared mapping, or any S6 gate (depth-128/2048 bench, memory-hog arm).

## S6's registered gates, with the shared mapping — 2026-09-24

Same machine (M1 Pro, 16 GB), binary at `dd34ea24` (`MAP_SHARED` on darwin), both arms the SAME binary with only
`GOINFER_METAL_ALIAS` differing (`gates-decode/serve-alias-{on,off}.sh`). Load average 1.8–3.4 throughout — the box
never went under `bench_peer.py`'s 1.0 idle bar, so it was raised deliberately (`BENCH_MAX_LOADAVG=4`); the verdicts
below are paired, interleaved differences, which steady background load hits equally. Raw data beside this file.

**Gate 3 — logits byte-identical, aliased vs copied: PASS on the 1.5B and the 7B** (`TestWeightAlias_logitsByteIdentical`;
7B: 3,112 MB aliased, 56 single tensors + 56 fused groups).

**Gates 2 and 4 — decode within 3% at depth 128 and 2048: PASS, worst −0.35%** (`scripts/bench_peer.py`, metal,
`goinfer` = aliasing on vs `goinfer_old` = aliasing off, 3 runs per cell, pre-registered: pass ≤ 3% slower, 3–5%
ambiguous/parked, > 5% fail):

| model | depth | aliasing on | aliasing off | Δ |
|---|---|---|---|---|
| 1.5B | 128 (A) | 73.47 | 73.53 | −0.07% |
| 1.5B | 128 (B) | 73.71 | 73.81 | −0.13% |
| 1.5B | 2048 | 56.04 | 55.85 | +0.34% |
| 7B | 128 (A) | 21.95 | 22.02 | −0.31% |
| 7B | 128 (B) | 21.95 | 22.03 | −0.35% |
| 7B | 2048 | 17.13 | 17.18 | −0.27% |

M26 (N=8), alias-first interleaved, 32 tokens (`m26-v13-shared/`): 6.70 / 6.94 aliasing on vs 6.82 / 7.03 off —
paired −1.8% and −1.3%, inside the band; the rate rises run over run (warming), which an alias-first order biases
AGAINST the alias arm. All four completed, swap flat, identical text.

**Gate 1 — anonymous footprint ≤ KV + slots + scratch + 15%: NOT MET**, though the dense weights' copies are gone
(`gates-footprint/`, phys footprint at token 32; with the shared mapping these are real savings — the aliased pages are
the file's page cache, not private copies):

| model | aliasing off | aliasing on | Δ |
|---|---|---|---|
| 1.5B | 1,010 MB | 387 MB | −62% |
| 7B | 4,129 MB | 1,010 MB | −76% |
| M26 (N=8) | 4,486 MB | 3,762 MB | −724 MB (= the 723 MB aliased) |

The 7B's bar is ~60 MB of KV at ctx 512 plus scratch. By shape, most of what remains is what S6's Build step 2 has not
done yet: the f16 group scales, still converted into MTLBuffers at load (⅛ of the nibble bytes, ~390 MB on the 7B), and
the int8 embedding/LM head, which cannot alias until it is requantized at transcode time (~300 MB) — an estimate from
the model's shapes, not a per-buffer measurement. On M26 the slot pool and the non-aliased buffers dominate (Build
step 4, expert slots).

**The memory-hog arm, 7B only** (`hog-7b/`: a 6.1 GiB hog of random — incompressible — bytes, re-touched continuously,
kill-watch on the server pid; M26 under a hog deliberately not run):

| | aliasing on | aliasing off |
|---|---|---|
| decode | 21.73 tok/s | 21.81 tok/s |
| load | 6.4 s | 21.3 s |
| swap growth | 0 MB | +56 MB |
| phys footprint at token 32 | 1,014 MB | 4,128 MB |
| page-ins during the request | 3,632 (~58 MB re-faulted) | 146 |

The registered prediction ("the aliased arm loses tok/s to re-faults where the copied arm loses the machine to swap")
shows here only in miniature, because the 7B plus a 6 GB hog still fits a 16 GB machine: the copy arm swapped a
little and loaded 3.3x slower building its 3 GB of copies; the alias arm re-faulted ~58 MB and kept its speed (−1% vs
no hog). The regime the prediction is about is a model near RAM size — M26 — not measured under a hog.

An earlier hog attempt the same day is recorded because it went wrong: the first hog script built
`bytearray(os.urandom(n))`, which briefly holds TWO n-byte buffers — ~12 GB, not 6 — and pushed swap-used to 5.1 GB
before it was killed; its harness run had already failed on an argument error, so no server was running and nothing
was measured. The fixed hog (`hog-7b/hog.py`) fills one buffer in 64 MiB chunks and the driver aborts if its RSS
exceeds 6.5 GiB (it measured 6.1).

## What is not done

The 7B (declined by the live-memory guard at the time, correctly), the depth-128/2048 bench, the memory-hog arm,
M26 alias footprint and tok/s (the arm collapses before it produces any — cause known, fix not applied), gate 3 on M26/7B, the resident-parity fixtures, `Close` under the leak checker (the
no-copy buffers go through the device ledger and release before the model unmaps, and the parity test closes
in that order, but no leak-checker run was made), the page-boundary fixture beyond `TestMmapAliasWindow`, and the
banner as a user-facing line (it prints to stderr at load only when the flag is set).
