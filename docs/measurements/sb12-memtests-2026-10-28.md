Two of the failures in nobara's recorded CUDA `gate gpu` runs (`docs/measurements/sb12-2026-10.md` §14), assigned by Francis
at 05:03. By nobara-ci01 on nobara (RTX 2070 SUPER, driver 595.91.07, Go 1.27.3), from goinfer main `0e69d19f8`. Logs are

## 1. `TestBuildDemand_matchesDecoderDefault`: the test's scope, not the product

**What failed.** The rounding half of the test holds CUDA's rounding report (`planSlack`, MM2b's 2 MiB driver rounding) to
decoder's default of 0 on every checkpoint directory in `testdata/`. In all three failing cells the eight directories it
flagged are real checkpoints the night gate's worktree places there (`scripts/worktree_fixtures.sh` places every gitignored
fixture): `llama3.2-1b`, `llama3-tokenizer`, `qwen2.5-0.5b`, `qwen3-1.7b`, `tinyllama-1.1b`, `tinyllama-awq`,
`tinyllama-gptq` and `tinymistral-248m`. None is a committed fixture.

**Why the product is right.** Decoder keeps no copy of CUDA's buffer layout: `RegisterPlanSlack`'s contract is that without
the backend's report the slack is 0, "the true figure for every buffer under the allocator's quantum". A real checkpoint has
buffers far over 2 MiB (each one's embedding is 131 MB to 1.2 GB at f32), so CUDA's non-zero report is the pricing working.
Nothing in pricing changes.

**Not test order.** In a worktree of committed fixtures only, the test passes when run alone. With one real checkpoint
(`llama3.2-1b`) linked into the same worktree, it fails, alone, on that directory (1,572,864 bytes, the night run's figure).
The pass reported alone and the failure in full runs came from which directories were present, not from what ran before.

**The fix.** The rounding comparison holds only for a checkpoint whose every weight is under the quantum at f32 (the load
this half uses), read from the checkpoint's own safetensors header; a directory outside that is logged with its largest
weight, not compared. The test's other half, the build-demand comparison over every config, is unchanged.

## 2. `TestLedger_closesAgainstDevice`: two tests that never released their device

**What failed.** In the night run's `cuda-heavy-small` and `cuda-parity` cells, and in the WebGPU leg's `cuda-parity`, the
measured device delta fell below the ledger's charge. On llama-tiny it measured 4,194,304 against 4,479,240 charged; on the
0.5B, 987,758,592 against 988,562,064. The exact lower bound (#372) held the test red. The test passes when run alone.

**Not another process.** The per-process reading (nvidia-smi) and the device-wide free-memory reading moved by the same
bytes in every failing cell, and each cell is one `go test` of `./cuda/`. The cause is inside the test process.

**CUDA sub-allocates small buffers from a pool that outlives a device.** `TestSmallAllocPool_sharedAcrossDevices` (new, in
`cuda/kernels`) shows it on the card:
- **Shared:** with a first device holding four buffers of 4 KB, 64 buffers of 4 KB on a second device moved free memory by
  0 bytes, while one 2 MiB buffer moved it by exactly 2 MiB.
- **Plant:** with the first device released before the second is created, the same 64 buffers open a fresh page
  (2,097,152 bytes), and the probe goes red.

Devices share the primary context, and with it the pool. So while an earlier device stays open, a later device's small
buffers can land in pages that are already counted, and its delta reads short.

**Which earlier tests.** I replayed the parity cell's recorded order (329 tests up to the ledger test) and reproduced the
failure to the byte: 4,194,304 and 987,758,592. Bisection then named two tests that never release their device:
- **`TestKernelLocalMemoryCensus`** compiles modules on a device it never releases. From that point on, llama-tiny measured
  one page short: 6,291,456 against 8,388,608 alone.
- **`actGroupHarness`** (seven tests in `actgroup_kernel_test.go` and `kso1c_kernels_test.go`) creates a device, loads a
  module and a stream, and allocates its uploads straight from the context, then releases none of them. Its first user in
  the order, `TestKSO1C_nativeKernels`, cost the second page.

**The fix (tests only; no bound moved).**
- `TestKernelLocalMemoryCensus` releases its device.
- `actGroupHarness` releases its device, module and stream in `t.Cleanup`.
- `upload` frees each buffer in a cleanup that runs before the context's release.

## 3. For Francis: how the ledger test should hold up against a device left open

The fix in §2 restores the exact lower bound in the gate's order. The bound still depends on no earlier test in the process
leaving a device open, and nothing catches a new one: the suite's release check sees only released devices. Three ways to
make that dependence explicit. None widens the band.

- **(a) Keep the exact bound, and count open devices (recommended).**
  - What changes: the test package counts every device created through `CreateSystemDefaultDevice` against those released
    (`ReleasedForTest` already records releases). The ledger test fails at its start, naming the open count, when an
    earlier device is still open. The suite's release check reports any device never released by the end.
  - Pros: llama-tiny stays graded to its exact bound. llama-tiny probably has no buffer of 2 MiB or more (dense 102,784 B
    in all; the KV line 4,262,400 B across its buffers), so a per-buffer rule would grade little of it. The next leak reads
    as a named leak, not a byte gap, and the seven open devices of §2 would be reported wherever they run. No production
    seam.
  - Cons: it grades the whole delta, so it still needs a clean process. The check makes that a stated precondition instead
    of an assumption.
- **(b) Reconcile per buffer, as you chose for Metal at 20:51.**
  - What changes: a `gpudev` trace seam reads free memory around each allocation while a test has it set. Every buffer of
    2 MiB or more must move it by exactly its charge, to the byte. Buffers under the quantum are packed into the pool, so
    their growth is reported and not graded. The delta must stay at or under the charge plus 64 MiB.
  - Pros: immune to pages an earlier test left open. The same rule as Metal.
  - Cons: CUDA's quantum is 2 MiB (Metal's threshold is 16 KB), so on llama-tiny the graded set may be empty, and only the
    0.5B's large buffers are held exactly. Counting llama-tiny's buffers of 2 MiB or more is the first step. A cell that
    traces no large buffer would fail by Metal's rule, so that rule would need settling for llama-tiny. It also adds a
    test-only seam to `gpudev`'s allocation path.
- **(c) Run the ledger test in its own process.** The gate's drain group already does this, by marker.
  - Pros: the exact bound holds with no new code in the device.
  - Cons: a plain `go test ./cuda/` still depends on order, and nothing reports the leak itself.
