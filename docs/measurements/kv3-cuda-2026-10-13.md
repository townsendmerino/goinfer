## 2. The 12,288-key batched-prefill decline on CUDA

### 2.1 Where, why, and who it affects (read from source, before any change)

- **Where.** `cuda/prefill.go:cudaResident.checkPrefillShmem`, called from `cuda/prefill.go:cudaResident.prefillCore` for every
  batched pass that is not an MC3 step. For each layer it takes the attended span `maxNWin = startPos + M` (clamped to the
  window of a sliding-window layer), and declines with `errPrefillDeclined` when `(maxNWin + 128) * 4` bytes exceeds
  `singleBlockAttnShmemLimit`, 48 KiB: **12,160 attended keys**. (12,288 is the next multiple of 512 above it, the first pass
  that fails.) The decoder then prefills the prompt token by token (`decoder/model.go:Model.residentPrefillSeed`). `DraftBlock`
  has a twin check for the drafter.
- **Why.** The exact attention kernel (`attn_batched`; `attn_block_full`, `attn_img_batched`) keeps one score per attended key
  in dynamic shared memory, one block per (head, row), and has no split-KV path. Decode has one: `splitkv_*` past the same bound.
- **What the guard gets wrong.** It applies to every pass, but the **fused prefill attention (`attn_fused*`) is the kernel
  every ordinary prefill of 512 tokens or more already uses** (`useAttnFused`), and its shared memory is constant in the number of
  keys: it stages 64 keys at a time (a tile, `BN`) and its footprint is a function of the head dimension alone. So a Claude Code
  first request (17,751 tokens) is declined by a check about a kernel it does not launch.
- **Cost, measured by KV0:** 17,755 tokens took 268.7 s to the first token on the per-token path (about 66 tokens a second),
  Qwen3-4B, f16 KV.
- **Which passes still need the exact kernel, and so keep the bound:**
  1. a pass the fused kernel does not serve: head dimension other than 64 or 128 (Gemma 2/3/4's 256, Phi-3's 96 and the like), an
     MLA layer, and any family on the exact kernels by design (Gated-DeltaNet, the Gemma 4 E-model, Qwen3-VL's DeepStack
     prefill);
  2. a tail other than an ordinary last-row prefill (`HiddenLast`, `ResidualAll`, verify), which needs decode-identical numerics;
  3. a pass of fewer than 16 rows (`attnFusedMinRows`): a prompt's last pass, when it is short;
  4. an image-block pass (`attn_img_batched`), which the fused kernel's tile aggregates cannot serve.
  Items 1, 2 and 4 stay declined, honestly, past 12,160 keys: a tiled exact kernel is a numerics project of its own (it must equal
  decode's split-KV bit for bit) and is not attempted here. Item 3 is a chunking defect, fixed below.
- **Families this fixes** (hd 64 or 128, dense or MoE, ordinary tail): Qwen2.5 and Qwen3 (all sizes), Llama, Mistral, gpt-oss
  (hd 64, sinks passed through), Phi-3-mini excepted (hd 96).

### 2.2 The change

1. The shared-memory guard asks whether the fused kernel serves the layer in this pass and, if it does, requires nothing of the span.
   It runs inside the pass, after `passPromptLen` and `forceExactKernels` are set, so it sees the same selection the launch will.
2. **The 16-row rule in the chunker** (the owner's decision of 2026-10-13, §8): a prefill never ends in a pass of fewer than 16 rows
   when it has more than one pass. `prefillChunked` moves the missing rows from the previous pass to the last one. This is what
   keeps the last pass of a long prompt on the fused kernel, and it is also the class-consistency rule KV0 measured (a pass of 15 rows or
   fewer is exact class, so a short tail made the whole prefill non-invariant). The decoder's own block loop and MC3's chunk loop
   keep a floor of 8 rows (`prefillTailMin`) today; the same rule is applied there through an optional method on the resident.
3. The guard in `decoder/resident_reuse.go` (`declineShortLeadReuse`) and the block key are KV1's, and are left to that session: the
   16-row condition for them is recorded in the task doc's KV3 section as a request to it.

### 2.3 Gates, registered before any code (2026-10-13)

**Identity (below the bound): bit-identical to today.**
- (a) *Guard equivalence.* For every layer geometry the fixtures have, every `startPos` and `M` with every layer's attended span at or
  under 12,160, and each fused-lever state (on, off, tail not ordinary, hd not served, M under 16), the new guard returns nil exactly
  when the old one did. Over the bound, the new guard returns an error exactly when the fused kernel does not serve a layer.
- (b) *Digests across builds.* A digest (SHA-256 over the last-token logits and every layer's K and V rows) of `PrefillLast` on the real
  Qwen2.5-Coder-1.5B at int4 (f16 KV, the default), on natural text, at prompt lengths 300, 3,900 and 12,000 tokens, equal between a
  build of `main` at `e9a0a2c4` and this branch. **Registered exception:** a prompt whose last pass would be 1 to 15 rows (4,100
  tokens at the 512-row chunk: 8 passes of 512 and a 4-row tail) changes under the 16-row rule, by design; its digest must instead
  equal the digest of the same prompt prefilled in one pass (KV0's invariance: whole = chunked on the fast class).
- (c) The existing CUDA identity suites pass unchanged: `TestPrefillLast_e2e`, `TestPrefillChunked_*`, `TestKV0_*`, the `attn_fused*`
  and flash-decode suites, `TestPrefillCoreAndDraftBlockCallTheShmemGuards`, and the tests of the files touched.

**Fidelity (above the bound): the batched pass against the per-token path** (the path the decline takes today, decode's own numerics),
on prompts the pass has not been tuned on.
- *Set.* Tiny fixture (`llama-attnfa-tiny` with `max_position_embeddings` raised to 32,768 in a temporary copy; hd 128, int4):
  random-token prompts of 12,400, 14,000 and 16,384 tokens, 3 seeds each (9 prompts). Real: Qwen2.5-Coder-1.5B int4, natural text
  (windows of `decoder/*.go` under its tokenizer) of 12,500, 16,384 and 20,000 tokens, 2 windows each (6 prompts).
- *Scoring.* Cosine of the last-token logits, and argmax. **Bar: cosine at least 0.99 on every prompt; argmax equal on every prompt
  except where the reference's top-1 minus top-2 logit is under 3% of |top-1| (a near tie, the project's rule).** The 0.99 is the lowest
  cosine KV0 measured between a fast-class prefill and decode on 600 tokens (0.9927); a deeper prompt is allowed no
  worse. The tiny fixture's random weights make its argmax meaningless: its argmax is reported and not graded; its cosine is graded.
- *Control (the comparison must be able to see a difference).* The same prompts with their last 8 tokens replaced must score under
  the bar against the unmodified per-token reference; if one does not, the set is void.
- *Cost.* Per-token reference at the 1.5B: estimated 100 to 200 tokens a second at this depth, so about 98,000 tokens of real
  prompts is 8 to 16 minutes: **the real set runs on the night queue**; by day only the tiny set and one 12,500-token real prompt
  (about 1.5 minutes).

**Speed: time to first token for a Claude Code-sized first request, new against old.** The request is KV0's recorded Claude Code first
request (17,755 tokens, Qwen3 rendering), replayed through `/v1/messages` (`max_tokens` 1, no streaming) against Qwen3-4B at
`-ctx 28672`, f16 KV: the arm "old" is the serve binary KV0 used (`serve-cuda-kv0`), the arm "new" is this branch. Three pairs,
alternating old and new, a fresh server per run, the timing lock held (night queue). Old is 268.7 s (KV0, one run). **Registered
bands (new, median of 3): PASS at 45 s or less (at least 6 times faster); AMBIGUOUS from 45 s to 90 s (parked, not shipped on this
evidence); FAIL above 90 s.** Basis: the 1.5B prefills 3,900 tokens in 965 ms (4,041 tokens a second, peer sweep cell d); the 4B has
about 2.7 times the weights, so about 1,500 tokens a second at that depth; allow 3 times for depth: about 36 s for 17.7k tokens. The same
runs record the swap growth (the never-swap reading).

**Estimates and the rule for this section.** Everything under "Identity" and the tiny fidelity set is a day check (seconds to a
minute or two); the real fidelity set and the speed gate go on the night queue under `night.py`, each with a pinned binary and a
run script.

## 3. KV3: admission in blocks on CUDA

### 3.1 The change and its gates, registered before code

**Facts (read).** CUDA prefills in passes of `prefillChunkRows` (512 by default, a multiple of B = 64; `GOINFER_PREFILL_CHUNK`
overrides it, and the windowed-KV chunk is capped at 513), allocating each pass's scratch (about 146 MB at 512 rows on the 7B)
and freeing it. Admission (`decoder/prefill_budget.go:Model.AdmitPrefillMemoryShare`) prices a resident request at the CPU batched
sweep's whole-prompt figure (`prefillScratchBytes`, 3.21 GB for a 20,954-token prompt: the I7 night's 413) unless the resident
reports a per-pass figure through `decoder.ResidentPrefillBlocks`, which Metal's KV-pre does and CUDA does not. That interface also
makes the decoder split the prompt itself and requires `PrefillTailExact`, which CUDA cannot claim (a pass of 15 rows or fewer is
exact class); CUDA already splits inside `prefillChunked`. So CUDA needs the pricing without the splitting.

**The change.**
1. `decoder` gains an optional interface for a resident that chunks its own prefill: it reports its chunk and its per-pass scratch,
   and `residentPrefillScratch` prices a request at that pass when the resident does not use the decoder's block loop.
2. `cudaResident` implements it: the chunk is `prefillChunkRows` (a multiple of 64; a knob that is not one is reported as is), and
   the scratch is the sum of the pass's device allocations for that many rows (every `af`/`ai` buffer of `prefillCore`, after the
   allocator's own rounding), not the whole prompt.
3. The 16-row tail rule (§2.2) reaches the decoder's loops through an optional method; CUDA says 16, everything else keeps 8.

**Gates.**
- **Identity.** Every CUDA identity suite unchanged (those listed in §2.3 (c), and the full `./cuda/` suite on the night queue). The
  change touches pricing only, plus the tail rule of §2.2 whose registered exception covers it.
- **Price accuracy.** `PrefillScratchBytes(rows)` is at least the device bytes the pass allocates, and within 10% above, on the dense
  text path (the tiny fixture and the real 1.5B at 512 rows), measured with the allocation accounting the CUDA tests use. A figure
  under the allocation is a failure: it is what admission trusts.
- **A request the old bound refused now answers.** With the host's available memory injected at a figure between the old price and the new
  one for a 20,954-token prompt (the injection the decoder tests use), the old bound returns the 413 text and the new one admits;
  the admitted request then prefills on the device and answers (the real 1.5B, `max_tokens` small). The same prompt without
  injection is the speed gate's request.
- **Never-swap flat.** Swap in use before the load and after the answer of the served 20k-token request differs by 64 MB or
  less (the I8 convention), in the night speed job.
- **Time to first token at K = 512 and K = 3,900 is 0.97 or better against main.** Two arms, `BENCH_ENGINES=goinfer,goinfer_old`,
  the TTFT harness `scripts/bench_peer_prefill.py`, the 1.5B, medians of paired blocks, on the night queue under the timing lock.
  Pass: the ratio old/new TTFT is at least 0.97 at both depths. Expected: 1.00 (the pass is unchanged below the tail rule).
