## Where it starts

## The levers, ranked by estimated payoff (estimates are priors, not results)

1. **Batched prefill for Gemma 4's MoE.** Expert-major: per layer, every expert the prompt routes to runs once over its
   rows, instead of 8 experts per token. Two steps: (a) lift the exclusion for a **resident** Gemma 4 MoE (the
   generic MoE's expert-major pass, D-B02's tiles, with Gemma 4's dense branch, router and join), gated on the tiny
   Gemma 4 fixture by day; (b) the **paged** pass (the audit's D-P01): stage each layer's routed experts once per
   prompt chunk through the pool. The audit's projection for the paged pass is 3–15× TTFT at 512 tokens (a prior,
   reported only; speed bands here follow the owner's rule: ship at ≥ 1.02×, park 1.00–1.02×, off below 1.00×).
2. **The page cache as the expert cache (zero copy).** Bind each routed expert's window of the mapped `.giw` as a
   no-copy buffer instead of copying it into a slot. S6 measured that Metal wires only the bound window and releases it
   when idle (`docs/measurements/m26-alias-fork-collapse-2026-09-24.md`), which overturns the 2026-08 finding that ruled
   whole-mapping no-copy out. If it holds per expert: no staging copy (24.4 ms a token today), no slot memory, the OS
   keeps hot experts in whatever RAM is free, and under pressure they are evicted clean rather than swapped.
   - **Probe first (by day, no model):** the cost of committing a command buffer that binds N fresh no-copy windows of
     an expert's size, with the pages in the page cache and with them cold, against `pread` of the same bytes; and
     whether the wired page count returns to baseline once idle. Also: whether the `.giw` lays each expert out on a
     16 KB boundary (no-copy needs page-aligned pointer and length).
   - Kill: wiring a hot expert window costs at least what `pread` into a slot does, or the wire does not release.
3. **Prefetch the next experts while the GPU runs.** Today each layer is router → copy → GPU, in series. While layer l
   runs, load layer l+1's likely experts (the previous token's set for that layer, or layer l+1's router applied early)
   into spare slots. Exact: the true router still picks; a wrong guess is loaded synchronously as now. Needs more slots
   than the router's 8. The 2026-08 Step-0 probe found synchronous paging a dead end and named this as the path
   (`metal-moe-paging-needs-speculation`).
4. **More slots.** `--moe-cache-experts` sizes the pool to live memory (`autoMoESlots`, up to 64); by day about 4.7 GB is
   live. An earlier Metal MoE slot sweep read +4.1% at 16 and +14.8% at 64 over 8. A night sweep at 8/16/32/64 on M26.
5. **Fewer round trips (M-11).** 61 submit-and-wait trips a token, 17.7% of it. C-B03's fence saves 88.5 µs a boundary
   (aikit probe), about 5 ms a token. Folding the LM head into the last layer's buffer removes one more.
6. **Long shots.** The n-gram drafter on copy-heavy output (2.08× on dense; on a paged MoE a verify routes more experts,
   so it may lose). A same-session peer run showing whether llama.cpp or Ollama can run M26 on this Mac at all.

| | pread into slots (today) | zero-copy bind | ratio |
|---|---|---|---|
| cold (first read from disk), ms a layer | 5.37 stage + 1.01 cb = 6.40 | 8.91 | 1.39 |
| hot (pages in RAM), ms a layer | 0.93 stage + 0.90 cb = 1.84 | 1.22 | 0.66 |

- Making 1,408 no-copy buffers took 5.1 ms; M26 would need 7,680 for the nibbles.
- **The wire, sustained (the GPU never idle, 5 s, a 2 GiB working set):**
  - persistent buffers: wired memory reached +2,016 MB within 1 s, the whole working set, and stayed there until the GPU
    went idle (+1 MB 2 s later). On M26 that wires most of the 16 GB.
  - a buffer made for each use and released when its command buffer completes: wired flat at +41 MB, 1.19 ms a round.
- So per-use binding is memory-safe, but it pays its wire (about 47 µs a buffer) on every routed expert, where the pool
  pays only on a miss. Against the hot rows above it breaks even at a pool hit rate of about 0.69.

## Step 4: prefill

### 4a: paged prompt tokens skip the LM head (built 2026-10-04, bit-identical)

The decoder's sequential prompt loop calls `ForwardNoLogits` for every prompt token but the last. On a paged MoE that
used to run the full head and discard the logits: on M26 a 262,144 × 2,816 int8 GEMV, about 0.74 GB a token.
`ForwardEmbNoLogitsPipe` now runs the paged forward with `pagedNoHead`, which returns before the final norm and head;
both pagers (Gemma 4's and the generic one). `TestPagedNoLogits_skipsHeadAndKeepsKV`: on the tiny Gemma 4 MoE and the
tiny Qwen3.5 MoE, paged at 2 slots, 4 prompt positions without the head then 4 positions' logits bit-identical to
Forward at every position; the head did not run (the host logits stay NaN). Removing the skip fails it.

### 4b: exact layer-major paged prefill — design and pre-registration (written 2026-10-04, before any graded run)

**The design.** M26's attention cannot take the f16 batched pass (head dim 256 and 512 by layer, K = V on global layers,
partial rotary, a 1,024 window), and Gemma 4's MoE is excluded from it. Instead, the prompt's rows are multiplexed
through the decode kernels, layer by layer:
- per chunk of rows and per layer: one command buffer runs each row's attention (`encodeAttentionWith`, the row's own
  position uniforms and attention plan) and `encodeG4Phase1`, between a restore of the row's residual and a stash of what
  phase 2 reads (`x`, `g4x1`, `mq`/`mSc`, `rIdx`/`rWgt`);
- the host reads every row's route, stages the union of routed experts into the pool once, and runs each row's
  `encodeG4Phase2Paged` and `encodeG4Join` from its stash, as many rows to a command buffer as the pool holds their
  experts at once, rows kept in order;
- every dispatch is the decode dispatch on the same inputs, so the K/V and the last row's logits are bit-identical to
  the sequential loop, by construction.

What it removes per prompt token: the two submit-and-wait trips per layer (16.6-17.5 ms a token at 8-24 slots) and the
per-token staging (25-35 ms), now once per chunk. What it keeps: the GPU's per-row GEMVs (37-39 ms a token).

### D-P01: the batched expert phase 2 — built, bit-identical; speed read pre-registered (written 2026-10-05, before it runs; owner: "lets build it and see how it performs")

**What is built** (`metal/prefill_g4batch.go`, `g4ExpertBatchOn`). In the layer-major pass, a slot group's phase 2 runs
expert by expert instead of row by row:
- `moe_batch_gemv<R,4>`: one routed expert's weights read once for up to 4 of the (row, expert) pairs the group routes
  to it. Each accumulator runs `sa_rows_acc`'s operations in its order, so every output equals the per-row kernel's.
- `mc3_swiglu_quant_rows` over every pair.
- The down projection the same way, storing each pair's raw sum.
- `moe_batch_combine`: a row's k experts added in route order with the per-row epilogue, `fma(wgt*acc, asc, out)` from
  zero.
- Then each row's join, unchanged.

Phase 1 stays per row; the host packs a group's activations, scales and router weights after phase 1 is waited.

**Gate (by day, tiny fixture): passes.** `TestG4ExpertBatch_matchesPerRow`: `gemma4-moe-tiny` as a metal `.giw`, paged at 2
and 3 slots; prompts of 5 and 12 rows and 9 rows on a 3-token prefix. The last row's logits, every K/V element and 3
decode steps are bit-identical between the batched and per-row phase 2. The batched path ran, and entries filled to 4
pairs at both slot counts. Three mutations each fail it:
- the combine in reverse route order (one K/V element's last bit);
- every pair staging the entry's first activation;
- gate|up reading its scale by pair instead of by row.

- **Async phase 2.** A paged MoE layer's phase 2 (experts and join) is committed and not waited: the host reads nothing
  back from it, the next layer's phase 1 runs after it on the same queue (Metal tracks the hazard on the residual), and
  the slot table the host rewrites for the next layer is written only after that phase 1 is seen complete. Half the
  token's 61 submit-and-wait round trips go. Both pagers. Bit-identical: every paged-against-resident gate passes.
- **Lever 3 (prefetch), as built.** Phase 1 of layer l also runs layer l+1's router on layer l's residual, and the host
  reads the guessed misses into layer l+1's pool in the background (`prefetchAsync` / `finishPrefetch`). Gated bit-exact
  (`TestG4Prefetch_bitExactAndRuns`). It loses because the guess is weak from the pre-FFN residual and the extra reads
  compete with the demand reads on the SSD: all 8 guessed meant ~1,300 extra reads per 40 tokens for ~190 fewer demand
  reads. A better guess (from after the layer's FFN) needs phase 2's wait back, which async phase 2 just showed costs
  ~13%. Kept off.
- **The fence, as built.** `paged_fence` (MSL 3.2, aikit's C-B03 probe's shape): the route copied through
  `coherent(system)` stores into a mirror, a system-scope fence, a sequence word the host spins on. Gated bit-exact and
  never stale (`TestPagedFence_bitExactAndNotStale`, and 0 fallbacks on M26). It loses: each fenced phase 1 took
  ~1.3-1.6 ms to be seen. The likely cost is the system-scope fence publishing a whole decode layer's writes, which the
  probe's one-word payload never priced. An inference, not measured. Kept off.
- **D-P01 (paged expert-major prefill).** The exact layer-major path (4b) is on and graded (1.385× at 128, 1.549× at
  512). Async phase 2 does not change it (its groups are waited, the pool shared within a layer). What it leaves is
  profiled below ("Layer-major prefill profile"): the routed experts' GPU time is about 27% of a prompt token, staging
  about the same, phase 1's per-row GPU work about 29%. A batched expert GEMM, one group's rows per expert in one
  dispatch, is the open question and is not built.
