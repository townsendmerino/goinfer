## §4 — Minor

One line each; grouped by area. A Minor here is something that will mislead the next change, a
comment that is now false, an error path that leaks, or a small inconsistency — none produces
wrong tokens on a default path.

### Serving

- **N-26** `internal/serveapp/banner.go:94` — `context:` prints `cfg.ctxSize` or "backend
  default", ignoring a per-model `ctx=` override and the fit-resolved cap; the `fit:` line below
  prints the real cap, so the banner disagrees with itself on an unpinned CUDA load.
  **DISPOSITION — `context:` FIXED 2026-09-14; the `fit:` half is still open, and the finding had it
  backwards.** `context:` now prints the resolved limit from `contextWindow` (the function `prepare`
  enforces and `/v1/models` publishes as `context_window`), says what set it, and takes the requested
  `-ctx` from the model's own resolved options, so a per-model `ctx=` is reported. Measured on the
  2070 SUPER (Qwen3-1.7B): `8192 tokens (backend default; model maximum 40960 — raise with --ctx)` on
  cuda-resident, and `40960 tokens (model maximum; --ctx 100000 is above it)` when that `-ctx` does not
  fit and the load falls back to cpu. **The `fit:` line does NOT print the real cap.** On the same
  default CUDA load it read "40960-token cap needs 8.8 GB KV" beside a resident cap of 8192, and with
  `-ctx 100000` it priced 100000 tokens. It reports `FitBudgetSummary`'s host-RAM pricing of a
  requested cap, not the enforced limit. So the banner still disagrees with itself, now in the other
  line. That is left open as its own item.
  **Batch C note (2026-09-16): the `fit:` half remains open, untouched this pass** — fixing it
  needs `FitBudgetSummary`'s pricing to key off the resolved/enforced cap `contextWindow` already
  computes rather than the raw requested one, a decoder-level pricing change too large for this
  batch's scope.
- **N-29** `internal/servecheck/cmd.go:21` vs `:102-106` — "Exits non-zero if any row fails" but
  every SKIP exits 0, including a server with zero models; a script sees 0 (V-17 fixed the text).
  **Status: DEFERRED to individual review.** Confirmed real (an all-skip run exits 0), but whether
  it SHOULD exit non-zero is a genuine design call this batch shouldn't make unilaterally: a
  zero-model check could be a deliberately narrow smoke test (server is up, nothing to check) or a
  real "nothing was verified" failure, and changing exit-code semantics risks breaking existing
  automation built against the current behavior either way.
- **N-33** `internal/serveapp/webui.go:109-85` — `sameOrigin` compares `Origin` host to `r.Host`; a
  DNS-rebinding page passes. The loopback no-key model already accepts drive-by API calls; matters
  for the pull route V-20 was about.
  **Status: DEFERRED to individual review.** Confirmed real: `r.Host` is client-supplied (the
  attacker's page's own Host header) and not a safe reference for a DNS-rebinding check. A correct
  fix needs to compare against the server's own actual configured bind address/allowlist instead
  of trusting `r.Host`, threading that value into `sameOrigin`'s construction — security-sensitive
  enough to deserve its own dedicated review and a real DNS-rebinding-shaped test, not a batch fix.
### CUDA

- **N-40** `cuda/lora.go:159-164` — `SetAdapter` treats any non-nil `r.setupErr` as "this upload
  failed": a stale error from `capVec` (`cuda/resident.go:2347-1899`, a production seam) is misattributed
  to the bind and cleared; an OOM panic inside `r.up32` skips `releaseLoraLayers2`, leaking `built[:i]`.
  **Status: partially FIXED elsewhere, remainder DEFERRED to individual review (2026-09-16).**
  Batch D (LoRA-leak-across-backends) re-verified this against current code: both of
  `SetAdapter`'s explicit error returns (the rank-range check and the `r.setupErr != nil` check)
  already call `r.releaseLoraLayers(built[:i+1])` before returning — the "same shape as
  Metal/WebGPU" leak this finding's own bundling anticipated is already closed here (no
  `releaseLoraLayers2` exists; that name is stale). Two real gaps remain, neither a batch-safe
  nit: (1) `r.setupErr` is a load-time-only field per `recordUpload`'s own doc comment ("Called
  only at load time"), but `capVec` (`cuda/resident.go`) also writes it via `recordUpload` from
  DECODE-time capture hooks inside `launchToken` — so a stale decode-time `capVec` failure can be
  wrongly attributed to and swallowed by a LATER `SetAdapter` call, exactly as described; fixing
  this needs deciding whether `capVec` should stop using `recordUpload` at all or `SetAdapter`
  needs a different signal, not obvious without deeper design work. (2) `up32`'s underlying
  `gpu.NewBufferLenOf` panics on OOM by design (`MustBuf`'s own doc comment); the executor's
  `runJob` panic boundary (C-24) already prevents this from crashing the process, but nothing
  inside `SetAdapter` itself releases `built[:i]` before that outer recover — a real leak on the
  OOM path specifically. A correct fix needs a local recover-cleanup-repanic inside `SetAdapter`,
  which is real GPU-panic-safety surgery this Mac cannot verify against real CUDA hardware
  (no CUDA device here) — deferred rather than shipped unverified.
- **N-43** `cuda/drafter.go:108-153` — a mid-loop `packWeight` failure returns with several
  `upW`/`up32` in the ledger, freed only at `Close`; `:208,324-330,471-548` — the drafter's `bGemvB`
  inherits `r.passPromptLen` from the target's LAST prefill, so whether it runs `gemm_w4a8_mma`
  depends on the previous prompt's length (lossless verify; a coupling nothing documents).
  **Status: split — leak half DEFERRED, coupling half FIXED (comment-only) 2026-09-16.** The leak
  is real (confirmed: every `r.upW`/`r.up32` call before a mid-loop `packWeight` failure stays
  allocated in the underlying `gpu.Device`'s ledger, freed only when the WHOLE resident model
  closes — for the rest of the process after any drafter weight-conversion failure, not just until
  some smaller scope). Releasing it correctly needs knowing whether `aikit/gpu`'s `Buffer` type
  supports safe INDIVIDUAL release ahead of the device's own single coordinated
  `ReleaseObjects()` call (the comment at `Close()` describes it as freeing "all of them in the
  correct order" as one operation) — a real question about a foreign package's API contract this
  session cannot verify (same `-tags cuda`-is-Linux-only limitation as N-41, compounded by not
  wanting to guess at a resource-lifecycle contract that could double-free). Deferred to individual
  review, matching N-40's own precedent for GPU-panic-safety surgery this Mac cannot check. The
  coupling is real but benign (confirmed: `passPromptLen` is set once at `prefillCore`'s top and
  never cleared, so `DraftBlock`'s `bGemvB` calls — which never go through `prefillCore` — read
  whatever the TARGET's last prefill left there; but speculative decoding's own verify step accepts
  or rejects each draft token against the target's real logits regardless of which kernel drafted
  it, so this can only shift acceptance rate, never correctness) — documented at both
  `passPromptLen`'s own field comment and `DraftBlock`'s doc comment; no behavior change.

### Constrain, tokenizer, chat, demos

- **N-79** `constrain/constrain.go:251-253`, `tokenizer/sentencepiece.go:822-830` — control tokens
  render as their literal surface, which is plain-string-legal inside a JSON string, so a
  constrained generation can emit a real control id mid-string; only masker-EOS ids are held back.
  "A grammar that forbids them masks them out" is true outside strings only.
  **Status: DEFERRED to individual review.** Confirmed real: `maskID` masks only `eosIDs`-until-
  `canEnd`; every other id (including a control/special token that is neither EOS nor a template
  stop id) is judged purely by `TryBytes`, and a control token's literal surface is ordinary
  printable text that is plain-string-legal JSON content. A real fix needs different semantics than
  `eosIDs` (masked only until `canEnd`) — a control token must be forbidden ALWAYS, including
  mid-string — which means a new "always-forbidden id set" threaded through `NewMasker` and every
  call site (`internal/serveapp/openai.go`, `internal/chatapp/main.go`,
  `demo/agent/agent/agent.go`), plus a tokenizer-side way to enumerate "special/control ids"
  uniformly across byte-level/SentencePiece/WordPiece modes (`isAdded` exists but is unexported and
  not obviously complete for this purpose). That is new plumbing, not a local patch — documented
  precisely at both cited locations (comment-only) rather than bolted on here.
### WebGPU

- **N-86** `gpu/backend.go:193-201` — `q4resident` (like `qresident`) is keyed by `&bQ4[0]` and never
  evicted; with paged experts every touched expert becomes a permanent device copy until
  `CreateBufferInit` fails, after which that expert runs on CPU while earlier ones stay resident.
  **Status: DEFERRED to individual review.** Confirmed real: `residentW4A8For` never evicts, and
  neither `q4resident` nor `qresident` clears anything before `Close()`. No existing LRU/eviction
  mechanism exists anywhere in the `gpu` module to mirror (checked); CUDA/Metal's own expert-cache
  precedents live in entirely different packages with different buffer-lifetime models. A correct
  fix needs real design work — choosing an eviction strategy, and proving it never evicts a buffer
  mid-use by an in-flight dispatch — not a local patch. Deferred rather than shipping an
  under-verified mitigation.
