### V-01 · Every GGUF `Transcode` fails its own self-check since M-12: the temp file is `<out>.tmp` and `decoder.Load` dispatches on the `.giw` suffix

- **Where (as found, now fixed — see Status):** `internal/prequant/prequant.go:91` (was
  `tmp := out + ".tmp"`, now the fixed line), `:111-114` (`selfCheck(tmp)` → remove → error),
  `:246-252` (`selfCheck` is `decoder.Load(path, Options{})`); `decoder/model.go:214`
  (`if strings.HasSuffix(dir, ".giw")` is the only entry to the bundle loader; anything else goes
  to `loadWeights`, which wants `.gguf` or a safetensors directory).
- **Mechanism:** `model.int4.giw.tmp` ends in neither `.giw` nor `.gguf`, so `Load` opens it as a
  directory, fails, `selfCheck` returns the error, the temp file is deleted and `Transcode` returns
  `self-check: …`. The rename is never reached. `transcodeDir` (safetensors) still writes in place
  and is unaffected.
- **Trigger:** `cmd/prequant <file.gguf>`; `serve --stream-weights -model x.gguf` with no existing
  sidecar (`EnsureCachedGIW` → `Transcode`), or any rebuild `cacheFresh` decides on. Boxes that
  already had sidecars before 51b47ab never call it, which is how it stayed green.
- **Checked:** no test performs a successful GGUF `Transcode` — the M-12 tests assert failure on a
  non-GGUF source and an AST shape; `stream_families_test.go` says the tiny fixtures refuse before
  the weights.
- **Fix:** name the temp `strings.TrimSuffix(out, ".giw") + ".tmp.giw"` (keeps the suffix, still
  never equals `out`), or detect the bundle by its `GINFW` magic in `Load`. Add a test that transcodes
  a real tiny GGUF end to end and loads the result.
- **Confidence:** high.
- **Status (2026-09-04): FIXED, exactly as prescribed.** `tmp` is now
  `strings.TrimSuffix(out, ".giw") + ".tmp.giw"` (`internal/prequant/prequant.go:91`). New gate:
  `TestTranscode_realGGUFSucceedsAndPublishedBundleLoads`
  (`internal/prequant/stream_test.go`, `GOINFER_HEAVY_TESTS=1`, a real tokenizer-bearing
  `qwen2.5-coder-0.5b-instruct-q4_k_m.gguf` — `glm-tiny.gguf` carries no tokenizer, so it can't
  drive the full bundle path this finding is about) drives `Transcode` end to end and loads the
  published bundle. Mutation-checked: reverting the fix line reproduces the exact predicted
  failure, `self-check: decoder: read config.json: open config.json: not a directory` (the temp
  file falling through to the safetensors-directory loader). Full `internal/prequant` suite green.

### V-02 · `serve -web` cannot render its page when `-api-key` is set — which is required off loopback

- **Where (as found at `a7ead30`):** `internal/serveapp/main.go:538`
  (`mux.HandleFunc("GET /{$}", auth(srv.handleWebUI))`); `internal/serveapp/helpers.go:103-119`

  the two `/web/models/*` routes and `/v1/*`.
- **Status (2026-09-04): FIXED, exactly as prescribed.** `GET /{$}` now registers
  `srv.handleWebUI` directly (`internal/serveapp/main.go:546`); `auth` stays on

  `TestWebUI_rootRouteIsUnauthenticated` (`internal/serveapp/webui_test.go`) asserts this

  which is exactly why the bug went unguarded before. Mutation-checked: re-wrapping the route in

### V-04 · R-02 commits on the cancel exit a real cancel almost never takes

- **Where (as found at `a7ead30`):** `decoder/model.go:1053-1033` (top-of-loop `select` on
  `ctx.Done` — returns without committing) vs `:1095-1107` (the send-select, where R-02 added the
  commit).
- **Mechanism:** an iteration is `top-of-loop check → sample (µs) → send → Forward (ms)`; a cancel
  that arrives during the forward — the dominant interval — is seen by the top-of-loop select. At
  that point the previous forward returned nil, `commit(next)` ran, and `generated` holds every
  forwarded token (the optFwd redo path completes its forward inside `optFwdStep` too), so the cache
  is exactly as consistent as at the completion commit. The disposition's stated problem stays in
  place for most cancels.
- **Fix:** `if useGPU { m.residentCommitIDs(prompt, generated) }` on that exit as well; it also
  makes `TestGenerateResident_cancelCommitsExactlyWhatWasEmitted` deterministic (V-10).
- **Status (2026-09-04): FIXED, exactly as prescribed.** The top-of-loop `ctx.Done()` exit now
  commits too (`decoder/model.go:1055`). Mutation-checked with the existing
  `TestGenerateResident_cancelCommitsExactlyWhatWasEmitted` run at `-count 100`: WITHOUT this fix
  the test fails intermittently (~35 of 100 runs, confirming the race V-10 describes is real, not
  theoretical); with it, 100/100 pass, and `-race -count 20` alongside the R-03 sibling test is
  clean. This closes V-10 too — both exits now commit identically, so which one a given cancel
  lands on no longer matters.

### V-05 · M-16 is fixed for decode only: batched prefill, speculative verify and the drafter still launch the single-block attention past 48 KB and fall silently to the sequential path

- **Where (as found at `a7ead30`):** `cuda/resident.go:2443-2443` (the fix — `splitKVRequired` + a
  named refusal, decode only); `cuda/prefill.go:357-383` (unguarded
  `SharedMemBytes: (maxNWin+128)*4`); `cuda/drafter.go:471-475` (same);
  `decoder/model.go:862-866` (a `PrefillLast` error falls through to the per-token loop with
  nothing logged); `grep splitKVRequired cuda/` finds only `resident.go` and its test.
- **Mechanism:** `prefillCore` is also the verify path (`ForwardN`). For `startPos+M > 12,160`
  the layer-0 launch is refused by the driver, the error propagates, and the callers rerun the
  prompt token by token — the "~9× slower sequential prefill, silently" the M-16 disposition says
  is gone. M-15's `kvCap = ctxCap` now lets a `--drafter` run reach the same boundary.
- **Trigger:** `-ctx 16384` on Qwen2.5-7B / Llama-3-8B with a >12,160-token prompt: decode works
  via split-KV, TTFT is the sequential path.
- **Fix:** the same `splitKVRequired` check in `prefillStaticDecline` (decline loudly) or a split-KV
  prefill kernel; the drafter likewise.
- **Status (2026-09-04): PARTIALLY FIXED — the decline-loudly option, but the decline still
  reaches no operator; see below.** A split-KV prefill kernel is a much bigger, riskier undertaking
  than the boundary this finding is actually about. New
  `checkPrefillShmem` (`cuda/prefill.go`) is `prefillStaticDecline`'s prompt-dependent twin —
  deliberately NOT added inside `prefillStaticDecline` itself, whose own doc comment states it
  covers exactly the MODEL-dependent guards and takes no `startPos`/`M`; adding a
  prompt-dependent check there would violate the split that lets `PrefillPath` answer at load time
  from the same code `prefillCore` enforces at call time. `checkPrefillShmem` is called from
  `prefillCore` right after the existing `checkCap`, iterates every layer computing `maxNWin`
  exactly as the launch site does (window-clamped per layer), and declines naming the layer, the
  bytes needed, and the device limit — wrapping `errPrefillDeclined` so the caller's existing
  fallback still works, just no longer silently. Since `prefillCore` serves both plain prefill and
  spec-decode verify (`ForwardN`), one fix covers both. The drafter's `DraftBlock` gets the same
  treatment via extracted `checkDrafterShmem(ctxLen, M)` — one check covers all its layers, since
  (unlike the target) no drafter layer has a per-layer window.

  `decoder/model.go:862-866`'s silent swallow of the `PrefillLast` error is deliberately NOT
  touched: it swallows every static decline too (MoE, K=V, non-uniform geometry — all pre-existing,
  accepted behavior), and logging only this one new class without addressing the general design
  would be inconsistent scope creep beyond what this finding names as the fix. **This is why V-05
  is PARTIAL, not FIXED**: the decline this finding's own fix constructs — naming the layer, the
  bytes needed, the device limit — is correct and reachable, but never reaches an operator, because
  `residentPrefillSeed` discards `perr` unconditionally. Filed as
  `docs/queue-engineering.md`'s **B20** rather than folded into a "26/26" line, per a second,
  independent review (Claude desktop app) that caught the overclaim: fixing operator visibility
  here is a real scope change (log level, per-reason dedupe, a machine-readable reason code so the
  caller can choose log-vs-silent per decline reason rather than blanket-logging everything
  `PrefillLast` declines), not a one-line addition to this finding's fix.

  **Verified on REAL CUDA hardware** (nobara, RTX 2070 SUPER) — the Mac doing the rest of this
  review has none. `TestAttnShmemLimit_matchesDevice` (pre-existing, M-16) queries the actual
  device and confirms `MAX_SHARED_MEMORY_PER_BLOCK = 49152 B`, exactly `singleBlockAttnShmemLimit`.
  New tests drive `checkPrefillShmem`/`checkDrafterShmem` directly (struct-only fixtures, no
  device needed, mirroring `TestPrefillPath_matchesPrefillCore`'s pattern) covering the boundary
  (12160 declines-not, 12161 declines), the per-layer window clamp, and the `ctxLen+M` split for
  the drafter. Mutation-checked TWICE: first pass (arithmetic-only tests) missed that removing
  `prefillCore`'s call to `checkPrefillShmem` still builds clean — an unused method is not a Go
  compile error the way an unused import is — and every existing test still passed, because none
  of them go through `prefillCore` at all. Added `TestPrefillCoreAndDraftBlockCallTheShmemGuards`,
  an AST-structural wiring guard (mirrors `TestWebUI_rootRouteIsUnauthenticated`'s pattern); it
  catches both the `prefillCore` and the `DraftBlock` wiring removal that the arithmetic tests
  missed. Full `cuda` package suite, gofmt, and vet all green on nobara with the real `cuda` build
  tag (not cross-compiled).
